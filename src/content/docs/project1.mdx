**SCHOOL IMAGE LAB**은 학교 안에서 반복해서 확인해야 하거나 놓치기 쉬운 작은 문제를 찾아, 이미지 분류 AI가 실제로 도움이 될지 직접 실험하는 프로젝트입니다.

이 프로젝트에서는 **문제 발견 → 데이터 설계·수집 → 모델 테스트·개선 → 구현·공유·판단**의 과정을 스스로 설명합니다.

<Callout kind="mission" title="이번 프로젝트에서 가장 중요한 질문">
**“학교의 어떤 문제에 이미지 분류 AI가 도움이 되며, 어디까지 믿고 사용할 수 있을까?”**를 끝까지 탐구합니다.
</Callout>

## 교과서와 활동지는 이렇게 사용합니다

- **교과서**에서는 각 단계의 핵심 개념과 판단 기준을 이해합니다.
- **활동지**에는 팀이 실제로 결정한 내용과 중요한 테스트 결과만 기록합니다.
- **TALK → DECIDE → TRY → TEST → RECORD**의 리듬으로 진행합니다.
- 활동지는 차시마다 새로 작성하지 않고 프로젝트가 끝날 때까지 이어서 완성합니다.

## STEP 1 · 문제를 발견하고 정의하기

### 학교생활의 문제부터 찾기

학교생활에서 사람이 반복해서 확인하는 일, 놓치기 쉬운 상태, 사진으로 확인하면 도움이 될 상황을 먼저 찾습니다.

예를 들어 “하교 전 교실 창문을 일일이 확인하는 불편을 줄이기 위해 열림과 닫힘을 구분한다”와 같이 문제와 사용자가 드러나도록 표현합니다.

### 굳이 AI가 필요할까?

표지판이나 체크리스트 같은 단순한 방법도 함께 살펴보고, 이미지 분류 AI가 필요한지 판단합니다.

| 확인할 질문 | 판단 기준 |
| --- | --- |
| 이미지 분류가 도움이 되는가? | 사람이 계속 직접 확인하기 어려운 상황인가? |
| 더 단순한 방법은 없는가? | 표지판·위치 변경·점검표·간단한 규칙으로 해결하기 어려운가? |
| 사진에 차이가 보이는가? | 사람이 사진만 보고도 두 상태의 차이를 설명할 수 있는가? |
| 틀렸을 때 안전한가? | 큰 피해가 없고 사람이 다시 확인할 수 있는가? |

<Callout kind="caution" title="AI를 안전하게 사용할 수 있는 주제를 선택합니다">
사람의 감정·성격·능력·의도처럼 사진에 직접 보이지 않는 것을 추측하거나, 결과가 사람에게 불이익을 줄 수 있는 주제는 선택하지 않습니다. 사람이 최종 확인할 수 있는 작고 안전한 문제부터 시작합니다.
</Callout>

### 클래스는 ‘보이는 기준’으로 정의하기

팀원 모두가 같은 기준으로 사진을 모을 수 있도록 클래스별로 눈에 보이는 기준을 정합니다.

| 불분명한 기준 | 더 구체적인 기준 |
| --- | --- |
| 정리됨 / 정리 안 됨 | 물건이 지정 위치에 있음 / 지정 위치를 벗어난 물건이 있음 |
| 창문 열림 / 닫힘 | 창틀 사이에 틈이 보임 / 창문이 끝까지 닫혀 틈이 보이지 않음 |
| 쓰레기통 가득 참 / 비어 있음 | 내용물이 기준선 위에 있음 / 기준선 아래에 있음 |

사진만 보고도 기준을 설명하기 어렵거나 사람마다 판단이 크게 다르다면 클래스 기준이나 주제를 다시 검토합니다.

### 활동지에는 무엇을 남길까?

다음의 **결정**을 기록합니다.

1. 누구의 어떤 문제인지
2. 현재 해결 방법과 한계
3. AI를 사용해볼 가치가 있는지
4. 두 클래스와 사진에서 보이는 차이
5. 이 문제를 선택한 이유

## STEP 2 · 모델이 배울 데이터를 설계하고 직접 수집하기

### AI는 우리가 보여준 사진에서 배웁니다

이미지 분류 모델은 사물의 의미를 사람처럼 이해하지 않습니다. 사진에서 반복해서 나타나는 시각적 특징을 찾아 분류에 사용합니다.

팔찌는 항상 손목에서, 시계는 항상 책상 위에서 촬영했다면 모델은 **손목과 책상 배경**을 주요 특징으로 배울 수 있습니다. 학습 화면에서는 잘 맞아도 배경이 달라지면 쉽게 틀릴 수 있습니다.

<Callout kind="concept" title="데이터에서 함께 살펴볼 네 가지">
**양**은 충분한가, **균형**은 두 클래스가 지나치게 차이 나지 않는가, **다양성**은 여러 촬영 조건을 담았는가, **정확성**은 사진과 라벨이 클래스 기준에 맞는가를 함께 확인합니다.
</Callout>

### 다양하게 찍는다는 것은 무엇일까?

실제 사용 환경을 고려해 거리·각도·밝기·배경·위치·촬영자를 바꾸어 촬영합니다.

| 바꿀 수 있는 조건 | 생각해볼 질문 |
| --- | --- |
| 거리 | 가까운 사진과 먼 사진이 모두 있는가? |
| 각도 | 정면·옆·위 등 여러 방향에서 촬영했는가? |
| 밝기 | 밝은 곳, 어두운 곳, 그림자가 있는 상황을 담았는가? |
| 배경·장소 | 한 장소나 배경에만 치우치지 않았는가? |
| 물체 위치·상태 | 위치, 방향, 크기, 가려짐이 달라지는가? |
| 촬영자 | 여러 팀원이 서로 다른 방식으로 촬영했는가? |

**모델이 실제로 사용될 때 달라질 가능성이 있는 조건**을 팀이 골라 데이터에 반영합니다.

### 학습용과 테스트용을 왜 나눌까?

- **학습용 데이터**: 모델이 특징을 찾는 데 사용하는 사진
- **테스트용 데이터**: 학습에 넣지 않고 새로운 상황에서도 작동하는지 확인하는 사진

테스트용 사진은 처음부터 따로 남겨두고 학습 데이터에 섞지 않습니다. 개선 전후를 비교할 때에는 가능하면 같은 테스트 사진이나 조건을 사용합니다.

<Callout kind="caution" title="사람의 권리를 지키며 데이터를 수집합니다">
다른 사람의 얼굴을 동의 없이 촬영하지 않습니다. 이름·학번·명찰 등 개인정보가 보이지 않게 하고, 얼굴이 우연히 포함된 사진도 확인합니다. 가능한 한 팀이 직접 촬영하며 인터넷 사진을 허락 없이 학습 데이터로 사용하지 않습니다.
</Callout>

### 활동지에는 무엇을 남길까?

1. 클래스별 목표 수, 실제 수집 수, 테스트용 사진 수
2. 다양하게 만든 촬영 조건 네 가지 이상
3. 아직 부족할 것 같은 조건
4. 개인정보·초상권·저작권을 보호하기 위해 실제로 한 행동
5. 데이터의 강점과 부족할 수 있는 부분

## STEP 3 · 모델을 테스트하고, 필요하면 데이터로 개선하기

### 첫 모델은 확인의 출발점입니다

첫 모델을 다양한 조건에서 테스트하여 **어떤 조건에서 잘되고 어떤 조건에서 흔들리는지** 알아냅니다.

<Steps>
<Step title="1차 모델 학습">클래스별 실제 학습 이미지 수를 확인하고 첫 모델을 만듭니다.</Step>
<Step title="새로운 사진으로 테스트">따로 남겨둔 테스트 사진과 실제 사용 상황을 생각한 사진을 보여줍니다.</Step>
<Step title="조건을 바꾸어 확인">거리·각도·밝기·배경·가려짐 등을 바꾸며 결과를 관찰합니다.</Step>
<Step title="대표 결과 세 개 기록">모델의 특징이 잘 드러나는 결과만 고릅니다.</Step>
<Step title="개선 여부 결정">문제가 있으면 중요한 원인 하나를 개선하고, 안정적이면 확인한 범위를 기록합니다.</Step>
</Steps>

### 확률이 높으면 정답일까?

모델의 **CLASS A 95%** 표시는 현재 입력이 학습한 두 클래스 중 어느 쪽과 더 비슷한지를 나타냅니다.

두 클래스 어디에도 속하지 않는 대상을 보여줘도 모델은 대개 둘 중 하나를 선택합니다. 결과를 볼 때는 모델이 판단하도록 만든 대상인지도 사람이 함께 확인해야 합니다.

### 테스트할 때 무엇을 바꿀까?

| 테스트 상황 | 확인하려는 것 |
| --- | --- |
| 먼 거리에서 촬영 | 대상이 작아져도 구분하는가? |
| 다른 교실이나 배경에서 촬영 | 배경이 달라져도 대상을 보는가? |
| 밝거나 어두운 시간에 촬영 | 조명 변화에 영향을 받는가? |
| 일부를 가린 상태로 촬영 | 핵심 특징이 일부만 보여도 구분하는가? |
| 어느 클래스에도 속하지 않는 대상 | 억지로 한 클래스로 분류하는가? |

예상과 같았던 결과, 예상 밖의 결과, 실제 사용에서 중요한 결과 중 **모델의 특징을 가장 잘 보여주는 세 가지**를 남깁니다.

### 문제가 발견되었다면

먼저 실패의 원인을 가정하고 그 원인에 맞게 데이터를 바꿉니다.

**발견한 문제 → 원인 가설 → 데이터 또는 기준 변경 → 2차 학습 → 같은 조건으로 다시 테스트 → 변화 비교**

| 발견한 문제 | 가능한 원인 | 개선 방법 |
| --- | --- | --- |
| 어두운 곳에서 A를 B로 분류 | 어두운 A 사진이 부족함 | 여러 밝기의 A 사진 추가 |
| 특정 배경에서 결과가 바뀜 | 배경을 주요 특징으로 학습했을 수 있음 | 두 클래스를 다양한 공통 배경에서 촬영 |
| 팀원마다 라벨이 다름 | 클래스 기준이 모호함 | 기준 수정 후 잘못된 사진 삭제 |
| 한 클래스만 자주 선택 | 데이터 수나 다양성이 불균형함 | 클래스별 데이터 구성 점검 |

가능하면 한 번에 가장 중요한 문제 하나를 바꾸고, 1차 모델과 2차 모델을 **같은 조건**에서 비교합니다.

### 처음부터 잘 작동했다면

학습에 쓰지 않은 사진을 사용했는지, 여러 조건을 바꾸었는지, 가장 까다로운 조건까지 확인했는지 살펴봅니다.

“잘 작동했다”는 말에는 **어떤 조건까지 확인했는지**가 함께 들어가야 합니다.

### 모델의 한계를 설명하기

잘 작동하지 않는 조건, 시험하지 못한 조건, 실제 사용에서 문제가 될 수 있는 상황을 구체적으로 밝힙니다.

### 활동지에는 무엇을 남길까?

1. 모델의 특징이 드러나는 대표 테스트 결과 세 개
2. 개선이 필요했는지에 대한 결정
3. 개선했다면 원인 가설, 바꾼 데이터, 전후 결과
4. 개선하지 않았다면 시험한 조건과 가장 까다로운 조건
5. 현재 모델의 한계 한 가지

## STEP 4 · 결과를 보여주고 AI 사용의 가치를 판단하기

### 웹페이지로 프로젝트 과정을 설명하기

AI 또는 코딩 에이전트의 도움을 받아 모델을 실행하고 프로젝트 과정을 소개하는 웹페이지를 만듭니다. 평가는 프로젝트의 내용과 탐구 과정에 집중합니다.

| 방문자가 궁금한 것 | 보여줄 내용 |
| --- | --- |
| 왜 만들었는가? | 학교의 문제와 대상 사용자 |
| 무엇을 구분하는가? | 두 클래스와 눈에 보이는 기준 |
| 실제로 작동하는가? | 카메라를 이용한 모델 테스트 |
| 무엇으로 학습했는가? | 데이터 수와 다양한 촬영 조건 |
| 무엇을 발견했는가? | 대표 테스트 결과 |
| 무엇을 바꾸었는가? | 문제가 있었다면 개선 전후 변화 |
| 어디까지 믿을 수 있는가? | 모델의 한계와 사람이 확인할 부분 |

활동지 부록의 프롬프트에 팀 내용을 넣어 기본 코드를 만들 수 있습니다. AI가 생성한 코드의 모델 링크와 내용이 맞는지 확인하고 실제 기기에서 작동하는지 시험합니다.

### AI와 함께 코딩할 때도 판단은 팀이 합니다

| AI가 도울 수 있는 일 | 팀이 직접 해야 하는 일 |
| --- | --- |
| 기본 코드와 화면 구성 만들기 | 프로젝트 내용과 사실 확인하기 |
| 디자인이나 오류 수정 방법 제안 | 모델 링크 확인하기 |
| 문장 정리와 코드 설명 | 카메라와 예측 실제 시험하기 |
| 반복 작업 줄이기 | 어떤 결과와 한계를 공개할지 결정하기 |

### 발표와 동료평가

활동지에 기록한 내용을 보며 **문제 → 데이터 → 첫 모델 → 테스트 → 발견 → 필요하면 개선 → 결과 → 한계**의 흐름으로 설명합니다.

다른 팀의 발표를 듣고 우리 팀의 생각을 바꾸거나 다시 보게 한 한 가지를 기록합니다.

### 마지막에 처음 질문으로 돌아가기

프로젝트를 실제로 해본 뒤에도 AI가 필요하다고 생각하나요?

- AI를 사용하면 실제로 도움이 되는가?
- 특정 조건에서만 제한적으로 도움이 되는가?
- 사람이 확인하는 보조 도구로 사용하는 것이 적절한가?
- 다른 해결 방법이 더 적절한가?

최종 판단은 **잘 작동한 조건과 한계**를 근거로 설명합니다.

<Callout kind="concept" title="프로젝트의 마지막 판단">
AI가 맡으면 도움이 되는 일과 사람이 최종적으로 판단해야 하는 일을 구분해 봅시다. AI가 도울 범위와 사람이 책임질 범위를 분명히 정합니다.
</Callout>

## 프로젝트 완료 기준

- 문제에서 출발해 AI가 필요한지 검토했다.
- 사진에서 확인할 수 있는 기준으로 클래스를 정의했다.
- 다양한 조건의 데이터를 직접 수집하고 테스트 자료를 분리했다.
- 새로운 조건에서 모델을 시험하고 대표 결과를 기록했다.
- 문제가 있었다면 원인을 생각하고 데이터를 바꾸어 다시 확인했다.
- 문제가 없었다면 어디까지 시험했는지와 남은 한계를 설명했다.
- 웹페이지로 모델과 탐구 과정을 보여주었다.
- AI가 도움이 되는 일과 사람이 판단할 일을 구분했다.
- 팀원별 프로젝트 기여를 기록했다.
