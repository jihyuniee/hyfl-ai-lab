웹앱을 조금 바꿀 때마다 전체 HTML을 다시 받아 복사하면, 코드가 중간에 끊기거나 최신 파일을 혼동할 수 있습니다. **GitHub에 있는 우리 팀의 최신 파일을 AI가 읽고 직접 수정하도록 연결**하면 반복 작업을 줄일 수 있습니다.

이 페이지는 **연결 기능을 사용할 수 있는 팀을 위한 선택 참고 자료**입니다. 지도·통계·검색 등 팀의 주제와 관계없이 활용할 수 있습니다. 기존 프로젝트의 주제, 공공데이터, 파일 구조를 그대로 이어 갑니다.

## 1. 무료 계정에서도 할 수 있을까?

**GitHub의 요금과 AI의 이용 조건은 따로 확인합니다.** 2026년 10월 27일 공식 안내를 확인한 기준이며, 수업할 때 아래 공식 링크와 실제 계정 화면을 다시 확인하세요.

| 구분 | 확인할 내용 |
| --- | --- |
| GitHub Free | **Public 저장소의 GitHub Pages**를 사용할 수 있습니다. HTML·CSS·JavaScript 웹앱의 공개 배포에 GitHub 유료 구독이 필수는 아닙니다. |
| ChatGPT Free·Go | 공식 요금 안내는 데스크톱 앱의 일부 코딩 기능과 순차 제공 조건을 명시합니다. **학생 모두가 브라우저에서 동일한 GitHub 수정 기능을 쓸 수 있다는 뜻은 아닙니다.** |
| ChatGPT Plus 등 지원 플랜 | 공식 안내에 웹 Codex 등 지원 범위가 나옵니다. 실제 이용에는 해당 화면의 사용 권한, GitHub 연결, 저장소 쓰기 권한도 필요합니다. 사용량 제한을 확인합니다. |
| 학교에서 제공하는 계정 | 학교가 허용한 Work·Codex·GitHub 연결 범위를 확인합니다. 개인 계정과 보이는 메뉴가 다를 수 있습니다. |

근거: [GitHub Pages 이용 조건](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site), [OpenAI의 현재 요금·기능 안내](https://learn.chatgpt.com/docs/pricing).

**이 실습을 위해 바로 결제할 필요는 없습니다.** 먼저 내 계정에 연결 기능이 있는지 확인하고, 없다면 7단계의 **수정 부분만 적용하기**로 같은 프로젝트를 계속 발전시킵니다. 단순히 GitHub 링크를 채팅에 붙여 넣는 것과, 저장소를 수정할 권한까지 연결하는 것은 다릅니다.

## 2. 처음 한 번: 우리 프로젝트를 GitHub에 올리기

이미 GitHub에 올려 배포 중인 팀은 **그 저장소와 배포 설정을 계속 사용**하고 3단계로 갑니다. 아래는 새 HTML 프로젝트의 기본 흐름입니다.

1. 정상 작동하는 원본을 따로 보관합니다. 공개할 수 있는 파일만 준비합니다.
2. GitHub에서 **New repository**로 팀의 **Public** 저장소를 만들고 README를 추가합니다.
3. **Add file → Upload files**에서 `index.html`을 저장소 맨 위에 올리고 저장합니다. 기본 브랜치에 올리는 경우 **Commit changes**로 저장합니다.
4. `index.html`이 CSS·JavaScript·이미지·JSON 등 다른 파일을 불러오면 **해당 파일과 폴더도 같은 구조로 함께 올립니다.** 이미 여러 파일로 만든 앱을 한 파일로 합치지 않아도 됩니다.
5. **Settings → Pages → Source: Deploy from a branch**를 고릅니다. **Branch: main / (root)**를 선택하고 **Save**합니다. 다른 브랜치를 쓴다면 실제 파일이 있는 브랜치를 선택합니다.
6. 배포가 끝나면 **Visit site**로 웹앱을 열고, 지금까지 만든 기능이 작동하는지 확인합니다.

자세한 화면별 순서는 [처음 GitHub Pages로 배포하기](/hyfl-ai-lab/project1/#github로-웹페이지-배포하기)와 [GitHub 공식 공개 위치 설정](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)을 참고하세요. 빌드가 필요한 프로젝트나 Vercel 등으로 이미 배포한 팀은 기존 방식을 유지합니다.

### 주소 두 개를 구분하세요

| 주소의 역할 | 형식을 보여 주는 예시 |
| --- | --- |
| AI에게 수정할 파일 위치를 알려 주는 **저장소 주소** | `https://github.com/my-team/our-webapp` |
| 사람이 실제 결과를 확인하는 **웹앱 주소** | `https://my-team.github.io/our-webapp/` |

예시 주소를 그대로 쓰지 말고 우리 팀의 주소를 적습니다. 첫 파일을 한 번 올린 후에는 **GitHub에 저장된 최신 파일을 작업 기준**으로 삼습니다. 예전에 내려받은 사본을 다시 올리면 이후 수정 사항을 덮어쓸 수 있습니다.

## 3. 내 계정에서 가능한 방식으로 연결하기

KOSIS MCP처럼 AI에 외부 도구를 연결한다는 생각은 비슷합니다. 이 활동에서는 연결된 도구가 **우리 저장소를 읽고, 수정한 파일을 GitHub에 저장할 수 있는지**가 중요합니다. 연결된 서비스와 권한에 따라 가능한 작업이 달라집니다. [OpenAI의 플러그인 안내](https://learn.chatgpt.com/docs/plugins)에서 현재 연결 방법을 확인할 수 있습니다. **A 또는 B 중 내 계정에서 제공되는 한 가지 방식**으로 연결합니다.

### A. ChatGPT의 Work와 GitHub 플러그인을 사용할 수 있다면

1. ChatGPT의 **Plugins / 플러그인**에서 GitHub를 찾습니다. 표시된다면 상세 화면의 **Apps**, 지원 작업, 요청 권한을 확인하고 설치합니다. **Apps / 앱** 메뉴로 표시되는 계정은 그곳에서 연결을 확인합니다.
2. 연결 안내에 따라 **내 GitHub 계정으로 로그인**합니다. 저장소를 선택할 수 있다면 이번 프로젝트 저장소를 선택합니다. 팀 저장소라면 내 GitHub 계정에도 해당 저장소를 수정할 권한이 있어야 합니다.
3. 연결을 마친 뒤 **새 Work 대화**를 엽니다. GitHub를 사용해 달라고 요청하거나, 지원되는 화면에서는 `@`로 GitHub를 선택합니다.
4. 아래 **저장소 연결 확인 요청**을 보내 실제 파일을 읽는지 확인합니다. 검색·읽기만 가능한 연결이라면 직접 수정·저장까지 된다고 가정하지 않습니다.

메뉴가 없거나 학교 계정에서 연결이 제한되어 있다면 아래 B를 사용할 수 있는지 확인합니다. 두 방식 모두 사용할 수 없다면 7단계로 진행하세요. **비밀번호나 GitHub 개인 액세스 토큰을 채팅에 붙여 넣어 연결하지 않습니다.** 계정 연결은 서비스의 로그인·승인 화면에서 진행합니다. [연결된 앱의 기능과 권한 확인](https://learn.chatgpt.com/docs/build-plugins#include-apps-in-your-plugin)

### B. 웹 Codex의 Cloud 작업을 사용할 수 있다면

현재 공식 안내의 기본 순서입니다. [Codex Cloud 환경 안내](https://learn.chatgpt.com/docs/environments/cloud-environments)와 자신의 화면을 함께 보세요.

1. 새 작업의 **Work in → Cloud → Select environment → Create environment**로 들어갑니다. 또는 **Settings → Codex Cloud → Environments**에서 환경을 만듭니다.
2. 연결 안내에 따라 GitHub를 연결하고 **우리 프로젝트 저장소**를 선택합니다.
3. **Get started**를 누르고 설정 결과를 확인합니다. 단순 HTML 프로젝트라면 기존 파일을 사용하는 프로젝트임을 설명합니다.
4. 준비가 끝나면 환경을 **Publish**하고 **Start a new task**로 작업을 시작합니다. 이미 환경이 있다면 그 환경을 선택합니다.
5. 아래 요청으로 실제 저장소와 기준 브랜치를 확인합니다.

여기서 **환경 Publish는 AI의 작업 환경을 준비하는 단계**입니다. 학생 웹앱이 GitHub Pages에 배포되었다는 뜻은 아닙니다. 코드 저장과 웹앱 배포는 5단계에서 따로 확인합니다.

<CopyPrompt title="저장소 연결 확인 요청" content={repositoryCheckPrompt} />

**직접 확인:** AI가 실제 파일 경로와 최신 커밋을 알려 주었고, 현재 연결로 어디까지 할 수 있는지 확인했습니다. 읽기 가능 여부만으로 저장 권한까지 확인된 것으로 보지 않습니다.

## 4. 제목 한 곳을 바꾸며 연결 시험하기

첫 요청은 **첫 화면 제목 한 곳 바꾸기**처럼 결과를 바로 확인할 수 있는 작은 변경으로 시작합니다. 먼저 현재 제목과 바꿀 제목을 정합니다. 전체 디자인을 한꺼번에 바꾸지 않아야 어떤 변경이 반영됐는지 확인하기 쉽습니다.

### 저장 방식은 두 가지가 있습니다

| 방식 | 학생이 확인할 것 |
| --- | --- |
| **PR 만들기** | 변경안을 별도로 준비하는 방식입니다. GitHub의 **Files changed**에서 바뀐 부분을 보고, 맞으면 **Merge pull request**로 합칩니다. |
| **배포 브랜치에 직접 커밋하기** | 허용된 연결과 권한으로 그 브랜치에 수정 이력을 저장합니다. 저장된 **커밋 링크와 변경 내용**을 확인합니다. |

**커밋(commit)**은 변경 이력 한 건, **브랜치(branch)**는 작업 흐름을 나눈 공간, **PR(pull request)**은 변경 내용을 다른 브랜치에 합치기 위한 제안입니다. 처음에는 PR의 바뀐 부분을 확인하며 진행해도 전체 HTML을 복사할 필요가 없습니다.

<CopyPrompt title="첫 수정: 제목 한 곳 바꾸기" content={firstRepositoryEditPrompt} />

**직접 확인:** 답변에 전체 코드만 나온 것이 아니라 GitHub에 실제 커밋이나 PR이 생겼습니다. 변경 내역에서 의도한 제목 한 곳이 바뀌었는지 봅니다.

## 5. 같은 웹앱 주소에 반영됐는지 확인하기

**AI가 코드를 수정한 것, GitHub에 저장된 것, 공개 웹앱에 반영된 것은 각각 확인해야 합니다.**

1. AI가 알려 준 **커밋 또는 PR 링크**를 열고, 저장소·파일·수정 내용이 우리 요청과 맞는지 확인합니다.
2. PR을 만들었다면 대상 브랜치가 맞는지 확인하고 병합합니다. `main`을 배포 브랜치로 설정했다면 **PR 생성만으로는 화면이 바뀌지 않으며, 변경이 `main`에 들어가야 합니다.**
3. 저장소 **Actions**에서 해당 변경의 배포가 완료됐는지 확인합니다. 기존 배포 서비스를 쓰는 팀은 그 서비스의 배포 상태를 확인합니다.
4. 처음 기록한 **같은 웹앱 주소**를 다시 열어 새 제목을 확인합니다. 새 사이트를 만들거나 주소를 다시 제출할 필요는 없습니다.
5. 기존 입력·검색·지도·버튼 중 우리 앱에 있는 기능도 눌러 봅니다. 제목을 바꾼 뒤 다른 기능이 망가지지 않았는지 확인합니다.

GitHub Pages는 설정된 소스 브랜치의 변경을 배포하며, 공식 안내상 반영에 최대 10분이 걸릴 수 있습니다. 화면이 바로 바뀌지 않으면 먼저 **저장한 브랜치와 배포 상태**를 확인하고 새로고침하세요. 근거: [공개 위치와 자동 배포](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site), [배포 후 확인](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site).

## 6. 이제 우리 팀의 기능을 계속 개선하기

첫 수정이 확인되면 같은 연결로 실제 기능을 개선합니다. 예를 들어 **휴대전화에서 버튼 겹침 해결**, **검색 결과가 없을 때 안내 추가**, **선택한 항목의 설명 개선** 등을 한 번에 하나씩 요청합니다. 데이터와 표시할 내용은 우리 팀의 문제 정의에 맞게 정합니다.

<CopyPrompt title="이후 기능 개선 요청" content={repositoryChangePrompt} />

AI가 파일을 직접 수정해도 요청을 잘못 이해하거나 기존 기능을 망가뜨릴 수 있습니다. 이 방식은 **전체 코드를 반복해서 옮기는 작업을 줄여 주며**, 원자료와 결과를 대조하고 사용자가 직접 실행해 보는 일은 계속 필요합니다.

팀원 여러 명이 작업한다면 한 사람이 수정·반영한 뒤 다른 사람이 최신 상태를 확인하고 다음 작업을 이어 가면 혼동이 줄어듭니다. 이전 대화의 기억만 믿지 않고 **매 요청에서 저장소의 최신 파일을 기준으로 작업**하게 합니다.

## 7. 연결이 안 되거나 수정 후 문제가 생기면

| 상황 | 확인하거나 진행할 방법 |
| --- | --- |
| GitHub 또는 Work·Cloud 메뉴가 없음 | 현재 요금제·기기·학교 설정을 확인합니다. 바로 결제하는 대신 아래 부분 수정 방법으로 계속할 수 있습니다. |
| 저장소가 보이지 않음 | 연결한 GitHub 계정, 선택한 저장소, 팀 저장소 권한을 확인합니다. |
| AI가 읽기는 하지만 저장하지 못함 | 쓰기 도구와 권한이 있는지 확인합니다. 코드 제안만 받은 상태를 커밋 완료로 기록하지 않습니다. |
| PR은 있는데 웹앱은 그대로임 | PR의 병합 여부와 Pages의 배포 브랜치를 확인합니다. |
| 배포 실패 또는 이전 화면이 보임 | 해당 변경의 Actions 결과, 실제 수정 파일, 브랜치와 웹앱 주소를 확인합니다. |
| 요청한 기능 외에 다른 기능이 사라짐 | 변경 내역을 보고 마지막 변경을 수정하거나 되돌립니다. 팀원의 이후 작업도 함께 확인합니다. |

### 직접 연결을 못 쓰는 경우: 바뀌는 부분만 적용하기

현재 파일을 첨부하되 사본의 비밀키·토큰은 제거하고, 아래처럼 **찾을 위치와 교체할 부분**을 요청합니다. 수정 전 원본을 보관하고, GitHub에서 해당 파일의 편집 버튼을 눌러 안내된 부분을 바꾼 뒤 **Commit changes**합니다. 파일 전체를 매번 다시 업로드하지 않아도 됩니다.

### 잘못된 변경 되돌리기

PR을 병합한 뒤 되돌려야 한다면 GitHub의 해당 PR에서 **Revert**로 되돌리기 PR을 만들고, 내용을 확인해 병합합니다. 버튼이 없거나 충돌이 생기면 선생님과 함께 확인하세요. 직접 커밋한 경우에는 AI에 **문제가 생긴 커밋 링크, 원래 동작, 유지할 이후 변경**을 알려 주고 해당 변경을 취소하는 새 커밋을 요청할 수 있습니다. 그 뒤 같은 배포 확인을 반복합니다. [GitHub의 PR 되돌리기 안내](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/reverting-a-pull-request)

## 8. 기존 활동지에 과정 남기기

별도 활동지를 만들지 않고 기존 팀 프로젝트 기록을 이어 씁니다.

| 활동지 위치 | 남길 내용 |
| --- | --- |
| **STEP 2-4 · 구현** | 수정 이유, 바꾼 기능, 사용한 요청, 커밋 또는 PR 링크 |
| **STEP 3-2 · 검증** | 실제 웹앱에서 확인한 입력·결과, 기존 기능 점검, 원자료와 대조한 내용 |
| **STEP 4 · AI 활용** | AI가 수정한 부분, 사람이 판단한 부분, 오류를 찾아 다시 수정한 사례 |

**완료 기준:** 우리 팀 저장소의 파일을 AI와 수정했고, 저장 이력을 찾을 수 있으며, 같은 웹앱 주소에서 변경 사항과 기존 기능을 확인했습니다. 특정 유료 도구 사용 여부가 완료 기준은 아닙니다.

<details>
<summary>교사용: 수업 전에 확인하면 좋은 것</summary>

대표 학생 계정과 실제 수업 기기에서 **연결 → 제목 한 곳 수정 → 커밋 또는 PR 확인 → 공개 화면 확인**까지 시험합니다. 교사 계정에서 되는 기능이 학생 계정에도 제공된다고 가정하지 않습니다. 직접 연결을 쓰는 팀과 부분 수정 방식으로 진행하는 팀 모두 같은 구현·검증 기준을 적용합니다.

공개 저장소에는 GitHub 토큰·서버용 비밀키·공개하면 안 되는 자료를 넣지 않게 안내합니다. 카카오 지도용 JavaScript 키처럼 브라우저 사용을 전제로 한 키는 해당 서비스의 도메인 제한과 이용 조건을 따릅니다. 앱의 기능을 고치는 활동과 새 인증·결제 체계를 만드는 활동을 혼동하지 않도록 합니다.
