```text
→ 한계와 사람의 책임
```

## 프로젝트를 보는 데이터 과학의 6단계

데이터 과학의 문제 해결 과정은 다음 여섯 단계로 정리할 수 있습니다. 이 단계는 한 번씩 순서대로 통과하는 직선이 아닙니다. 결과가 충분하지 않으면 데이터 수집이나 문제 정의로 되돌아가고, 질문에 따라 모델링이 필요하지 않을 수도 있습니다.

| 데이터 과학의 단계 | 이번 프로젝트에서 하는 일 | 사람이 판단할 것 |
| --- | --- | --- |
| 1. 문제 정의 | 관심을 데이터로 확인할 작은 질문으로 바꾼다 | 무엇을 왜 확인할 것인가? |
| 2. 데이터 수집 | MCP로 관련 공식 통계를 탐색하고 선택한다 | 이 지표가 질문에 맞는가? |
| 3. 전처리·탐색 | 조건을 바꾸어 비교하고 필요하면 원파일을 정리한다 | 무엇을 포함·제외할 것인가? |
| 4. 분석·모델링 | 표·그래프·관계 분석으로 패턴을 찾는다 | 어떤 분석이 질문에 맞는가? |
| 5. 평가 | 공식 통계와 교차 확인하고 다른 설명과 한계를 찾는다 | 결과를 어디까지 믿을 것인가? |
| 6. 활용 | 문제를 다시 정의하고 AI 서비스의 역할을 설계한다 | 결과를 누구의 어떤 결정에 쓸 것인가? |

```text
문제 정의 → 데이터 수집 → 전처리·탐색 → 분석·모델링 → 평가 → 활용
     ↑                 결과가 부족하면 앞 단계로 되돌아간다 ─────┘
```

<Callout kind="concept" title="MCP는 2단계의 방법을 바꾸지만 6단계를 없애지 않습니다">AI가 데이터를 찾아 표와 그래프를 만들어 주어도, 문제를 정의하고 적절한 지표를 선택하며 결과를 평가하고 실제 활용을 결정하는 과정은 남습니다. 오히려 기술적 작업이 빨라진 만큼 질문과 판단의 근거가 더 잘 보여야 합니다.</Callout>

이 구성은 [당곡고 데이터 과학 수업의 ‘문제 해결 6단계’와 질문 중심 접근](https://greatsong.github.io/ds-danggok-2026/lesson01.html)을 참고하여 우리 프로젝트에 맞게 재구성했습니다.

## 먼저 팀을 구성합니다

비슷한 관심 분야를 가장 먼저 맞추고, 팀 안에서는 서로 다른 강점이 최대한 섞이도록 3인 내외로 구성합니다.

| 주도 역할 | 주로 맡는 일 |
| --- | --- |
| 질문·데이터 탐색 | 확인 질문 설계, MCP 도구 선택, 관련 통계 탐색 |
| 근거·검증 | 출처·통계표·기간·단위 확인, 핵심 수치 교차 검증 |
| 서비스 기획·표현 | 사용자, 기능, 이용 장면, 발표 자료 구성 |

역할은 일을 나누기 위한 출발점일 뿐입니다. 중요한 질문·데이터 선택·검증 기준·인사이트·서비스 방향은 팀원이 함께 결정합니다.

## STEP 1 · 관심에서 문제 가설로

완성된 서비스 아이디어부터 정하지 않습니다. 먼저 교육·외국어·문화·경제·국제사회·심리·환경·안전·진로·학교생활처럼 팀이 끝까지 궁금해할 분야를 고릅니다.

<Steps>
<Step title="궁금한 문제와 사용자 정하기">우리 팀이 실제로 궁금해하는 문제와 그 문제를 겪는 사람을 구체적으로 정합니다.</Step>
<Step title="현재·목표·작은 문제 함께 쓰기">지금 상태, 바라는 상태, 그 차이를 줄이기 위해 먼저 확인할 작은 문제를 한 묶음으로 씁니다.</Step>
<Step title="데이터로 확인할 질문 만들기">대상·기간·지역·지표가 드러나는 질문 하나를 만듭니다. 분석 결과에 따라 질문은 바뀔 수 있습니다.</Step>
</Steps>

> 현재는 **[지금 상태]**이고, 목표는 **[바라는 상태]**이다. 그 차이를 줄이기 위해 먼저 **[데이터로 확인할 작은 문제]**를 살펴본다.

<Callout kind="concept" title="문제를 분해하는 힘">
AI에게 큰 문제 전체를 바로 해결해 달라고 하지 않습니다. 큰 문제를 작게 나누어야 어떤 부분은 데이터로 확인하고, 어떤 부분은 규칙이나 사람의 안내로 해결하며, 어떤 부분에만 AI가 필요한지 판단할 수 있습니다.
</Callout>

<Callout kind="caution" title="아직 서비스 이름을 정하지 않습니다">처음 생각한 해결책을 증명하기 위해 데이터를 찾지 않습니다. 분석 결과가 예상과 다르면 질문·문제 정의·서비스 방향을 바꾸는 것이 좋은 탐구입니다.</Callout>

### 이 순간의 AI 활용

AI에게 해결책을 바로 요청하지 말고 검색어와 확인 질문을 넓히게 합니다.

```text
우리 팀의 관심 분야는 [분야]이고, 현재 [현상]을 문제라고 생각하고 있어.
이 생각을 확인하거나 반박할 수 있는 공공데이터 검색어를 한국어와 영어로 제안해줘.
대상·기간·지역·지표가 드러나는 분석 질문 후보도 만들어줘.
아직 해결책은 제안하지 말고, 우리가 당연하다고 가정한 부분과 먼저 확인할 점을 알려줘.
```

## STEP 2 · MCP로 공식 데이터를 넓게 탐색하기

처음부터 파일 하나를 골라 분석하지 않습니다. 먼저 MCP를 이용해 어떤 공식 통계가 존재하는지 살펴보고, 우리 질문을 확인하거나 반박할 수 있는 지표를 비교합니다.

<Steps>
<Step title="도구 선택">KOSIS·HRDKorea 등 교사가 안내한 MCP 중 질문에 맞는 도구를 연결합니다.</Step>
<Step title="지표 후보 탐색">큰 질문을 작은 질문으로 나누고 관련 통계와 지표 후보를 세 개 이상 찾습니다.</Step>
<Step title="조회 조건 비교">대상·기간·지역·집단·단위·갱신일을 비교하여 질문에 맞는 통계를 선택합니다.</Step>
<Step title="질문 수정">원하는 자료가 없거나 지표의 의미가 예상과 다르면 확인 질문을 수정합니다.</Step>
<Step title="탐색 기록">질문, AI가 사용한 도구, 선택한 통계, 받아들인 이유와 제외한 이유를 남깁니다.</Step>
</Steps>

```text
[연결한 MCP]를 사용해 [우리의 문제 가설]을 확인하거나 반박할 수 있는
공식 통계를 찾아줘. 아직 서비스 아이디어는 제안하지 마.

1. 확인 질문을 작은 질문 세 개로 나눠줘.
2. 각 질문에 사용할 통계표와 지표 후보를 찾아줘.
3. 제공 기관·대상·기간·지역·단위·갱신 시점을 비교해줘.
4. 적합하지 않은 후보도 그 이유와 함께 보여줘.
5. 현재 공개된 데이터로 답할 수 없다면 질문을 어떻게 수정할지 제안해줘.
```

공공데이터만으로 모든 원인을 알 수는 없습니다. 필요하면 설문·인터뷰·관찰이나 신뢰할 수 있는 보고서를 보충 근거로 활용할 수 있습니다. 개인정보와 동의 문제를 먼저 확인합니다.

## STEP 3 · 조회하고 표현하고 검증하기

AI에게 표와 그래프를 요청할 수 있지만, 만들어진 결과보다 **어떤 통계의 어떤 조건을 사용했는지**가 먼저입니다.

| 알고 싶은 것 | 방법 | 주로 사용할 표현 |
| --- | --- | --- |
| 시간이 지나며 달라졌는가 | 연도·월별 집계와 추이 분석 | 선그래프 |
| 지역·집단에 차이가 있는가 | 합계·평균·비율 비교 | 막대그래프 |
| 값이 어떻게 퍼져 있는가 | 분포와 이상치 확인 | 히스토그램·상자그림 |
| 두 수치 변수가 함께 움직이는가 | 산점도와 상관계수 | 산점도 |
| 여러 변수 중 관계 후보는 무엇인가 | 상관행렬 | 히트맵 |

<Steps>
<Step title="조회 근거 표시">사용한 MCP 도구, 제공 기관, 통계표, 항목, 기간, 지역, 단위를 기록합니다.</Step>
<Step title="핵심 표 만들기">질문에 직접 답하는 값만 비교 가능한 표로 정리합니다.</Step>
<Step title="그래프 만들기">시간 변화·집단 비교·분포·관계 중 질문에 맞는 표현을 선택합니다.</Step>
<Step title="핵심 수치 확인">주장에 사용할 수치 두 개 이상을 기관의 원 통계표나 공식 페이지에서 다시 확인합니다.</Step>
<Step title="계산 검증">증감률·비율·평균처럼 AI가 계산한 값은 계산식과 사용 값을 확인합니다.</Step>
<Step title="파일 필요성 판단">추가 정제·결합·세부 분석이 필요할 때만 CSV·XLSX 원파일을 내려받습니다.</Step>
</Steps>

### 이 순간의 AI 활용

```text
[연결한 MCP]를 사용해 [분석 질문]을 확인하려고 해.
1. 사용할 도구·통계표·항목·단위·기간·지역을 먼저 제시해줘.
2. 결과를 비교 가능한 표로 정리해줘.
3. 질문에 맞는 그래프를 만들고 선택 이유를 설명해줘.
4. 원자료 값과 네가 계산한 값을 구분해줘.
5. 계산한 값은 계산식과 사용한 수치를 보여줘.
6. 데이터에서 직접 확인한 사실과 가능한 해석을 구분해줘.
7. 내가 공식 화면에서 다시 확인할 핵심 수치를 표시해줘.
```

### 언제 원파일을 내려받을까?

단순 조회와 비교는 MCP만으로도 충분할 수 있습니다. 다음 작업이 필요할 때는 CSV·XLSX 파일을 내려받아 Google Sheets나 생성형 AI의 파일 분석 기능을 사용합니다.

- 여러 기관의 자료를 하나의 기준으로 결합할 때
- 결측치·중복값·이상치와 행·열 구조를 직접 확인할 때
- 새로운 비율이나 변수를 계산할 때
- MCP가 제공하지 않는 형태의 그래프나 세부 분석이 필요할 때
- 같은 절차로 결과를 다시 만들 수 있도록 분석 과정을 남길 때

원파일을 사용하는 팀은 파일명·출처 URL·다운로드 날짜를 보존하고, 사용한 열·필터·삭제·변경·집계 기준을 기록합니다. **파일 분석은 모든 팀의 의무가 아니라 질문이 요구할 때 선택하는 분석 방법**입니다.

<Callout kind="checklist" title="결과물과 함께 나도 성장했는가?">
- AI가 어떤 도구와 통계를 선택했는지 설명할 수 있는가?
- AI의 결과에서 내가 직접 확인하거나 수정한 것은 무엇인가?
- MCP 없이 공식 통계 화면을 보더라도 기간·단위·항목을 확인할 수 있는가?

설명할 수 없는 결과는 그대로 제출하지 않습니다. AI에게 도구 선택과 조회 조건을 다시 보여 달라고 하고, 핵심 수치를 공식 통계와 대조한 뒤 팀의 설명으로 바꿉니다.
</Callout>

## STEP 4 · 인사이트를 도출하고 문제를 다시 정의하기

그래프가 올라가거나 내려갔다는 설명만으로는 인사이트가 아닙니다. 다음 네 층을 구분합니다.

| 층 | 질문 |
| --- | --- |
| 관찰한 사실 | 데이터에서 직접 확인한 수치·차이·변화는 무엇인가? |
| 가능한 해석 | 이 현상은 누구에게 어떤 의미가 있을 수 있는가? |
| 원인 가설 | 왜 나타났다고 생각하며 무엇을 더 확인해야 하는가? |
| 서비스 기회 | 어떤 사용자의 어떤 결정·행동·불편을 도울 수 있는가? |

> 데이터에서 **[현상]**을 발견했다. 이는 **[대상 사용자]**에게 **[의미·어려움]**과 관련될 수 있다. 가능한 원인은 **[가설]**이지만 현재 자료만으로 단정할 수 없다. 따라서 우리는 **[도울 필요가 있는 구체적인 상황]**을 최종 문제로 정의한다.

### 이 순간의 AI 활용

```text
다음은 우리 팀이 공식 통계와 그래프에서 직접 확인한 사실이야: [사실]
1. 이 사실에서 가능한 해석과 원인 가설을 구분해줘.
2. 우리가 빠뜨린 변수와 반대 설명을 제시해줘.
3. 현재 데이터만으로 말할 수 없는 내용을 표시해줘.
4. 서비스 아이디어보다 먼저, 영향을 받는 사용자와 구체적인 상황을 질문해줘.
```

<Callout kind="concept" title="데이터는 문제를 대신 결정하지 않습니다">데이터는 반복되는 현상과 차이를 보여주지만 그 현상이 왜 중요한지, 누구를 도와야 하는지, 어떤 가치를 우선할지는 사람이 맥락 속에서 판단합니다.</Callout>

## STEP 5 · AI가 정말 필요한지 판단하기

공공데이터는 이 문제가 실제로 나타나는지 확인하는 근거로 사용할 수 있습니다. 그러나 서비스를 실제로 작동시키려면 다른 데이터가 필요할 수 있습니다. 그 데이터를 현실적으로 구할 수 있는지, 개인정보나 동의 문제가 없는지만 확인합니다.

AI를 넣기 전에 묻습니다.

1. 규칙·검색·안내·체크리스트가 더 단순하고 안전하지 않은가?
2. AI는 이 문제의 어떤 부분을 구체적으로 도울 수 있는가?
3. 필요한 데이터를 현실적으로 구할 수 있는가?
4. AI가 틀리면 누가 확인하고 최종 판단하는가?

AI가 필요하지 않다는 결론도 좋은 문제 해결입니다.

## STEP 6 · 서비스 시나리오 설계하기

```text
사용자 상황 → 입력 데이터 → AI가 하는 일 → 서비스 출력
→ 사람이 확인·선택하는 일 → 기대 변화
```

| 설계 요소 | 반드시 답할 질문 |
| --- | --- |
| 사용자 | 누가 언제 사용하는가? |
| 입력 | 무엇을 입력받고 어디에서 얻는가? |
| AI의 역할 | 어떤 패턴을 찾아 무엇을 분류·예측·추천·생성하는가? |
| 출력 | 사용자는 어떤 결과를 보거나 듣는가? |
| 사람의 역할 | 무엇을 확인·수정·선택하고 누가 최종 책임지는가? |
| 안전장치 | 오류·편향·개인정보·저작권·악용을 어떻게 줄이는가? |

김현철 교수님의 설명처럼 AI는 빠른 분석과 패턴 인식에 강한 엔진이 될 수 있습니다. 그러나 방향과 목적을 정하고, 데이터 밖의 맥락을 읽고, 직관적 통찰로 결과를 검증하며, 가치와 책임을 판단하는 운전자는 사람입니다.

### 이 순간의 AI 활용

```text
우리의 최종 문제 정의는 [문제]이고 근거는 [분석 결과]야.
현재 해결 방법과 한계는 [내용]이야.
AI가 맡을 수 있는 역할 후보를 제안하되, 규칙 기반 방법으로 충분한 기능은 구분해줘.
필요한 데이터가 현실적으로 있는지 확인하고, 오류가 났을 때 사람이 확인할 지점과 개인정보·편향 위험을 검토해줘.
```

## STEP 7 · 피드백으로 수정하고 제안하기

최종 발표 전에 다른 팀은 다음 역할로 기획안을 검토합니다.

- 데이터 검증자: 분석 결과와 주장 사이에 비약이 없는가?
- 사용자 대변인: 실제 사용자의 상황과 필요가 반영되었는가?
- 안전 검토자: 오류·편향·개인정보·악용 가능성과 사람의 개입이 설계되었는가?

피드백을 받은 뒤 문제 정의·기능·데이터·AI 역할 중 한 가지 이상을 수정하고 전후 변화를 기록합니다.

## 최종 기획안 구성

최종 기획안은 모든 과정을 나열하는 문서가 아닙니다. 우리 팀의 문제와 데이터에서 발견한 사실, 해결 아이디어가 자연스럽게 이어지도록 여섯 가지 이야기로 구성합니다.

1. **어떤 문제를, 누구를 위해 해결하려고 했는가?** 현재 상태와 목표 상태를 함께 설명합니다.
2. **어떤 데이터를 사용했고, 무엇을 발견했는가?** 사용한 MCP·기관·통계표·조회 조건, 핵심 표나 그래프, 가장 중요한 발견을 제시합니다.
3. **분석 후 문제를 어떻게 다시 정의했는가?** 처음 생각과 달라진 점이 있다면 함께 설명합니다.
4. **왜 AI가 필요한가?** AI가 도울 부분과 사람이 판단할 부분을 설명합니다. AI가 필요하지 않다는 판단도 가능합니다.
5. **서비스는 어떻게 사용되는가?** 사용자가 서비스를 이용하는 장면과 기대되는 도움을 보여줍니다.
6. **한계와 사람의 책임은 무엇인가?** 예상되는 오류나 위험, 안전장치, 사람이 최종 확인할 부분을 설명합니다.

> **AI 협업 기록:** AI가 도와준 일과 우리 팀이 직접 판단·검증·수정한 일을 각각 한 가지씩 적습니다.

<Callout kind="rubric" title="프로젝트 완료 기준">
- 문제와 사용자를 구체적으로 정하고 데이터로 확인할 질문을 만들었다.
- 사용한 MCP와 공공데이터 출처·통계표·조회 조건을 밝히고 핵심 발견을 표나 그래프로 설명했다.
- 발표에 사용한 핵심 수치를 기관의 원 통계표에서 다시 확인했다.
- 사실과 해석을 구분하고 상관관계를 원인으로 단정하지 않았다.
- 분석 결과에 따라 문제를 다시 정의했다.
- AI가 필요한 이유와 사람이 판단할 부분을 설명했다.
- 서비스 이용 장면과 예상되는 한계·위험을 제시했다.
- AI가 도와준 일과 팀이 직접 검증·수정한 일을 구분했다.
</Callout>

<Callout kind="concept" title="발표에서 가장 듣고 싶은 문장">“우리는 이 서비스를 생각해냈습니다”가 아니라 **“이 데이터를 분석해 이런 현상을 발견했고, 그래서 이 사용자의 문제를 이렇게 다시 정의했습니다. AI에는 이 역할만 맡기고 사람은 이 판단과 책임을 가집니다.”**라고 설명합니다.</Callout>
