## 1. 지난 프로젝트와 이번 프로젝트는 무엇이 다를까?

School Image Lab에서는 데이터를 모아 모델을 학습시키고 분류 결과를 시험했습니다. 이번에는 공개된 데이터를 해석하고, 생성형 AI의 도움으로 데이터를 활용하는 웹앱을 만듭니다.

| 구분 | School Image Lab | 이번 데이터 웹앱 |
| --- | --- | --- |
| 데이터의 역할 | 모델이 패턴을 학습하는 사례 | 질문을 분석하고 앱의 검색·계산에 사용하는 자료 |
| AI 활용 | 분류 모델을 학습·테스트 | 데이터 이해, 코드 초안, 오류 수정의 도움 |
| 사람이 판단할 것 | 데이터 구성과 모델 오류 | 데이터 의미, 계산 기준, 코드 결과와 사용성 |

## 3. 실제 공공데이터를 준비하고 읽기

### 3-1. 출처와 조회 조건 확인

[NEIS 교육정보개방포털](https://open.neis.go.kr/)에서 **급식식단정보**를 검색합니다. 학교와 분석할 기간을 정하고, 조회 화면이나 제공 파일에 필요한 항목이 실제로 있는지 확인합니다. 화면에 표시된 일부 결과나 API 샘플 응답을 전체 기간의 자료로 착각하지 않습니다.

첫 실습은 같은 학교와 같은 기간의 공통 파일을 사용합니다. 직접 내려받거나 수업에서 배부한 원파일을 사용할 수 있지만, 어느 경우든 출처 페이지와 조회 조건을 직접 확인합니다. 인증키 발급과 API 자동 연결은 첫 실습의 필수가 아닙니다.

<Steps>
<Step title="원자료와 사본 분리">내려받은 원본은 그대로 보존하고, 분석용 사본을 만듭니다. 제공 형식은 데이터 화면에서 확인합니다.</Step>
<Step title="필요한 열 확인">급식일자·학교명·식사명·요리명에 해당하는 열을 찾습니다. 없는 항목은 AI에게 만들게 하지 않습니다.</Step>

</Steps>

| 분석용 열 | NEIS에서 대응할 수 있는 항목 | 확인할 것 |
| --- | --- | --- |
| 날짜 | 급식일자 / MLSV_YMD | YYYYMMDD 또는 YYYY-MM-DD. 없는 날짜를 채우지 않는다. |
| 학교명 | 학교명 / SCHUL_NM | 원하는 학교가 맞는가? |
| 식사명 | 식사명 / MMEAL_SC_NM | 조식·중식·석식을 구분한다. |
| 메뉴 | 요리명 / DDISH_NM | 한 행에 여러 메뉴가 포함될 수 있다. 원문과 알레르기 표시는 보존한다. |

학교에 따라 자료가 없거나 필요한 기간이 내려받아지지 않으면 기간을 조정합니다. 실제 자료를 확보하지 못한 상태를 ‘수집 완료’로 표시하지 않습니다.

<Steps>
<Step title="첫 파일 저장">생성된 전체 HTML 코드를 일반 텍스트 파일로 저장합니다. 코드 블록 표시인 세 개의 백틱은 넣지 않습니다. 파일 이름은 index.html, 인코딩은 UTF-8로 정합니다.</Step>
<Step title="확장자 확인">파일이 index.html.txt로 저장되지 않았는지 확인합니다. PC에서는 파일을 웹브라우저로 열어 실행합니다.</Step>
<Step title="실제 CSV 선택">앱의 파일 선택에서 준비한 CSV를 불러옵니다. 출처·조회 조건·확인일을 입력합니다. 출처 칸을 채웠다고 자동으로 검증되는 것은 아닙니다.</Step>
<Step title="같은 질문으로 실행">앞서 직접 센 것과 같은 학교·월·검색어를 선택합니다. 일수뿐 아니라 날짜와 메뉴 원문을 대조합니다.</Step>
<Step title="코드의 네 부분 찾기">AI에게 데이터 읽기·조건 처리·계산·결과 표시 부분을 설명하게 한 뒤, 내가 바꿔 볼 위치를 표시합니다.</Step>
</Steps>

실행이 막히면 기본 index.html을 사용해 같은 CSV로 다시 시도합니다. AI가 작성한 첫 버전은 별도로 남기고, 기본 예시로 돌아온 이유를 적습니다. 코드를 전부 외우는 것이 아니라 **어떤 데이터가 어떤 기준을 거쳐 어떤 결과가 되는지** 설명하는 것이 목표입니다.

### 4-3. GitHub Pages로 공유하기

지난 프로젝트에서 사용한 배포 방식을 이어 씁니다. 기존 School Image Lab 저장소를 덮어쓰지 말고 새 저장소를 만듭니다.

<Steps>
<Step title="새 저장소 만들기">GitHub의 New repository에서 meal-data-lab 같은 이름으로 저장소를 만듭니다. 학교가 허용한 계정을 사용하고 공개 범위를 확인합니다.</Step>
<Step title="index.html 올리기">Add file → Upload files 또는 Create new file로 index.html을 저장소 최상위에 저장하고 Commit changes를 누릅니다. 파일 선택 방식이면 실제 CSV는 저장소에 올리지 않아도 됩니다.</Step>
<Step title="게시 위치 설정">Settings → Pages → Build and deployment에서 Source를 Deploy from a branch로 정합니다. Branch는 main, 폴더는 /(root)를 선택하고 Save를 누릅니다.</Step>
<Step title="배포 확인">Actions에서 배포 상태를 확인한 뒤 Pages에 표시된 주소를 엽니다. iPad에서는 파일 미리보기 대신 배포된 주소를 Safari에서 열어 확인합니다.</Step>
</Steps>

GitHub Pages의 사이트와 공개 저장소에는 누구나 접근할 수 있습니다. 개인정보, 인증키, 이용 조건상 재배포할 수 없는 파일은 올리지 않습니다. 학교 네트워크에서 로그인이 막히면 임의로 우회하지 않고 수업에서 정한 실행 방식으로 테스트 기록을 먼저 완성합니다.

## 5. ‘작동한다’와 ‘맞는다’를 구분하기

실제 CSV에서 직접 센 결과를 정답 기준으로 삼습니다. 첫 번째 정상 사례만 통과해도 검증이 끝난 것은 아닙니다.

| 테스트 | 입력·상황 | 확인할 것 |
| --- | --- | --- |
| 정상 검색 | 실제 자료에 있는 메뉴 | 날짜·일수가 원자료와 일치하는가? |
| 빈 검색어 | 검색어를 지운다 | 선택 범위의 전체 중식일을 보여 주는가? |
| 없는 메뉴 | 자료에 없는 문자열 | 0일과 검색 결과 없음 안내가 나오는가? |
| 월 변경 | 다른 월을 선택한다 | 선택한 월의 기록만 남는가? |
| 중복·잘못된 기록 | 같은 날짜 중복, 누락, 잘못된 날짜 | 중복을 하루로 세고 제외 이유를 알리는가? |
| 잘못된 파일 | 필수 열이 없는 CSV | 오류를 안내하고 이전 결과를 남기지 않는가? |

<details>
<summary>가상 점검 데이터의 정답 · 먼저 직접 세고 확인하기</summary>

이 정답은 교과서의 **가상학교 6개 기록**에만 해당합니다. 실제 학교의 급식 결과가 아닙니다.

| 조건 | 전체 중식일 | ‘카레’ 포함 중식일 |
| --- | --- | --- |
| 전체 월 | 5일 | 3일 |
| 2025-09 | 3일 | 2일 |
| 2025-10 | 2일 | 1일 |

2025-09-01의 두 기록을 하루로 묶습니다. 없는 문자열을 검색하면 0일이어야 합니다. 앱 안의 점검 버튼 또는 check-data.csv로 이 기준을 확인한 뒤 실제 공공데이터로 바꿉니다.

</details>

```text
[오류 수정 요청]
지금 코드와 재현 조건은 다음과 같아: [파일·학교·월·검색어]
기대 결과: [원자료에서 직접 확인한 날짜·일수]
실제 결과: [화면에 나온 결과 또는 오류 메시지]
기대 결과의 근거: [원자료의 기록·계산 기준]
가능한 원인부터 설명하고 해당 부분만 수정해줘.
다른 정상 기능은 유지하고, 같은 문제가 해결됐는지 확인할 테스트를 알려줘.
```

## 6. 개인·짝 미션 · 기능 하나 바꾸기

정상 실행본을 먼저 별도 파일로 보관합니다. 다음 중 하나처럼 **사용자의 행동이나 결과가 달라지는 수정**을 선택합니다. 제목·색상 변경만으로는 이 미션을 완료한 것이 아닙니다.

| 수정 후보 | 추가로 결정할 기준 |
| --- | --- |
| 검색된 중식일의 비율 표시 | 분모는 검색 전 선택 범위의 전체 중식일. 0으로 나누지 않는다. |
| 월별 비교 표 또는 막대그래프 | 월별 전체 중식일을 함께 보여 주고, 빈도가 선호도는 아님을 표시한다. |
| 내가 발견한 불편 개선 | 왜 필요한지, 입력·처리·출력이 어떻게 바뀌는지 설명한다. |

<CopyPrompt title="기능 하나 수정하는 프롬프트" content={improvePrompt} />

수정 뒤에는 새 기능뿐 아니라 앞서 통과한 검색·중복·오류 테스트도 다시 실행합니다. 두 버전을 비교하며 ‘바뀐 이유 → 바뀐 기능 → 확인한 근거’를 기록합니다.
