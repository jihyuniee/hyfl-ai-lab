GitHub에 저장한 우리 팀의 웹앱을 AI와 수정하고, 같은 배포 주소에서 결과를 확인합니다. 프로젝트의 주제·공공데이터·기존 파일 구조를 이어 사용하는 선택 참고 자료입니다.

🎯 작업 순서

프로젝트 업로드 → AI에 저장소 연결 → 수정 요청 → 변경 이력 확인 → 배포 브랜치에 반영 → 같은 웹앱 주소에서 검증

1. 준비하기

섹션 제목: “1. 준비하기”
  • 우리 팀의 현재 프로젝트 파일과 정상 작동하는 원본
  • 프로젝트 저장소를 수정할 권한이 있는 GitHub 계정
  • GitHub 파일 읽기·쓰기 기능을 제공하는 ChatGPT Work 연결 또는 웹 Codex Cloud 작업 환경
  • 우리 팀의 저장소 주소, 작업 브랜치, 실제 웹앱 주소

사용할 기능과 권한은 계정의 연결 화면에서 확인합니다. 공개 저장소에는 공개할 수 있는 코드와 자료를 준비하고, 비밀번호·서버용 비밀키·GitHub 토큰은 별도로 보관합니다. OpenAI의 연결 기능 안내

2. 프로젝트를 GitHub에 올리고 배포하기

섹션 제목: “2. 프로젝트를 GitHub에 올리고 배포하기”

이미 배포 중인 팀은 현재 저장소와 배포 설정을 사용하며 3단계로 이동합니다. 새 HTML 프로젝트는 다음 순서로 준비합니다.

  1. GitHub의 New repository에서 팀의 Public 저장소를 만들고 README를 추가합니다.
  2. Add file → Upload files에서 index.html을 저장소 맨 위에 올립니다. 연결된 CSS·JavaScript·이미지·JSON도 기존 폴더 구조대로 함께 올립니다.
  3. 파일을 올릴 브랜치를 확인하고 Commit changes로 저장합니다.
  4. Settings → Pages → Source: Deploy from a branch를 선택합니다. Branch: main / (root)를 선택하고 Save합니다. 다른 브랜치를 사용한다면 파일이 있는 브랜치를 지정합니다.
  5. 배포가 완료되면 Visit site로 웹앱을 열고 기존 기능을 확인합니다. 빌드가 필요한 프로젝트나 다른 배포 서비스를 사용하는 팀은 기존 배포 절차를 따릅니다.

GitHub Pages의 공개 브랜치·폴더 설정

기록할 주소형식 예시
코드가 저장된 저장소 주소https://github.com/my-team/our-webapp
실행 결과를 확인하는 웹앱 주소https://my-team.github.io/our-webapp/

표의 예시를 우리 팀의 실제 주소로 바꿔 기록합니다. 이후 작업은 GitHub에 저장된 최신 파일을 기준으로 진행합니다.

섹션 제목: “3. AI에 우리 저장소 연결하기”

섹션 제목: “A. ChatGPT Work의 GitHub 연결”

  2. 내 GitHub 계정으로 로그인하고 사용할 프로젝트 저장소를 선택합니다. 팀 저장소의 수정 권한도 확인합니다.
  3. 새 Work 대화에서 GitHub를 사용하도록 요청합니다. @ 선택을 지원하는 화면에서는 GitHub를 선택할 수 있습니다.
  4. 아래 요청문으로 저장소 파일과 현재 사용할 수 있는 읽기·수정·저장 기능을 확인합니다.

B. 웹 Codex의 Cloud 작업 환경

섹션 제목: “B. 웹 Codex의 Cloud 작업 환경”
  1. Work in → Cloud → Select environment → Create environment 또는 Settings → Codex Cloud → Environments에서 환경을 만듭니다.
  2. GitHub 계정을 연결하고 우리 프로젝트 저장소를 선택합니다.
  3. Get started를 누르고 설정 결과를 확인합니다. 프로젝트가 단순 HTML이라면 현재 파일을 사용하는 프로젝트임을 설명합니다.
  4. 준비된 환경을 Publish하고 Start a new task로 시작합니다. 기존 환경이 있으면 해당 환경을 선택합니다.

환경 Publish는 AI 작업 환경을 저장합니다. 웹앱 배포는 코드 변경을 배포 브랜치에 반영한 뒤 5단계에서 확인합니다. Codex Cloud 환경 안내

저장 방식확인할 내용

직접 커밋하기선택한 브랜치에 변경 이력을 저장합니다. 커밋 링크에서 수정한 파일과 내용을 확인합니다.

5. 배포 결과 확인하기

섹션 제목: “5. 배포 결과 확인하기”
  1. 커밋 또는 PR 링크에서 저장소·파일·수정 내용을 확인합니다.
  2. PR 방식이면 대상 브랜치를 확인하고 Merge pull request로 병합합니다. Pages의 배포 브랜치가 main이면 변경 내용이 main에 들어간 뒤 배포됩니다.
  3. Actions에서 해당 변경의 배포 완료를 확인합니다. 다른 배포 서비스를 사용하는 팀은 해당 서비스의 배포 상태를 확인합니다.
  4. 처음 기록한 같은 웹앱 주소를 열어 새 제목을 확인합니다.
  5. 기존 입력·검색·지도·버튼 중 우리 앱에 있는 기능도 실행합니다. 데이터 처리 기능을 수정했다면 원자료와 결과를 대조합니다.

GitHub Pages의 변경 반영에는 최대 10분이 걸릴 수 있습니다. 화면 갱신을 확인할 때는 저장한 브랜치와 배포 상태를 먼저 확인하고 새로고침합니다. GitHub의 배포 후 확인 안내

섹션 제목: “7. 파일 편집과 변경 복구하기”

파일을 직접 편집할 때는 현재 파일을 첨부하고 아래 요청문으로 수정 위치와 교체할 코드를 확인합니다. GitHub에서 해당 파일의 편집 버튼을 눌러 수정한 뒤 Commit changes로 저장하고 5단계를 수행합니다.

수정 위치와 코드 조각 요청 표시된 부분을 우리 팀의 내용으로 바꾸세요.
프롬프트 구조와 각 부분이 필요한 이유 보기

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

과업·필수 기능은 만들어야 할 결과와 빠뜨리면 안 되는 동작을 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

첨부한 최신 파일에서 수정할 위치와 교체할 코드를 알려줘.

수정할 파일: {{index.html 또는 실제 파일 이름}}
현재 동작: {{입력·클릭 순서와 결과}}
기대하는 동작: {{바라는 결과}}
유지할 기능: {{정상 작동하는 기능}}

1. 원인과 수정할 파일
2. 정확히 찾을 수 있는 기존 코드와 주변 문구
3. 삽입·교체·삭제할 범위와 완전한 코드 조각
4. 수정 후 확인할 동작

제공한 파일을 근거로 필요한 부분을 작성하고, 추가로 필요한 자료가 있으면 해당 파일이나 범위를 알려줘. 키·토큰 값은 마스킹해줘.

병합한 PR을 되돌릴 때는 해당 PR의 Revert로 되돌리기 PR을 만들고, 변경 내용을 확인해 병합합니다. 충돌이 생기면 선생님과 함께 확인합니다. GitHub의 PR 되돌리기 안내
