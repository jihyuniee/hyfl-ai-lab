7. DATA TO WEB APP

TEAM PROJECT · PUBLIC DATA × GENERATIVE AI
오늘의 질문공공데이터로 살펴본 작은 불편을, 다른 사람이 실제로 써 볼 수 있는 웹앱으로 바꿀 수 있을까?

🎯 DATA TO WEB APP

학교·생활·관심 분야의 작은 문제를 공공데이터로 탐색·분석합니다. 분석 결과를 바탕으로 핵심 기능 하나를 설계하고, 생성형 AI와 웹앱을 제작하여 다른 사람이 사용해 보게 한 뒤 검증·개선합니다.

1. 이번 프로젝트에서 반드시 하는 것

섹션 제목: “1. 이번 프로젝트에서 반드시 하는 것”
공통 필수선택 확장
실제 공공데이터를 확보하고 출처·조건·한계를 확인한다.다른 데이터 결합, API를 통한 자동 갱신
질문에 맞는 간단한 비교·계산과 해석을 수행한다.더 정교한 분석·시각화
공공데이터가 핵심 검색·비교·계산·시각화에 사용되는 웹앱을 만든다.AI 모델 학습·추론, 생성형 AI 응답 기능
생성형 AI의 도움을 받되 결과를 직접 검증한다.추가 기능·서비스 운영 설계
다른 사람이 써 보게 하고 한 가지 이상 수정한다.학교 공식 서비스로의 도입 검토

최종 앱 안에 AI 기능을 반드시 넣지는 않습니다. AI를 활용해 개발한 일반 검색 앱도 가능합니다. 반대로 공개 데이터를 학습 자료로 삼는 모델은 입력·정답·평가 자료가 실제로 확보된 팀의 심화 주제입니다. 모델 학습이나 유료 API 연결 자체가 가산점의 근거가 되지는 않습니다.

진로 연계도 필수가 아닙니다. 아직 진로가 정해지지 않았다면 학교나 생활의 불편에서 출발합니다. 다만 공공데이터와 무관한 앱을 먼저 정한 뒤 통계를 억지로 덧붙이지 않습니다.

📚 기획서는 사라지는 것이 아니라 제작의 앞 단계가 됩니다

아이디어를 적고 끝내지 않습니다. 필요한 기능 하나를 실제 데이터로 구현하여, 처음의 판단과 설계가 적절했는지 확인합니다. 목표는 학교 전체를 운영할 완성형 플랫폼이 아니라 작은 수업용 웹앱입니다.

2. 팀 구성과 역할

섹션 제목: “2. 팀 구성과 역할”

3인 내외로 팀을 구성합니다. 비슷한 관심을 바탕으로 하되 서로 다른 강점이 섞이도록 합니다.

주도 역할주로 맡는 일
질문·데이터사용자와 질문, 자료 후보와 출처, 정리 기준
분석·검증비교·계산, 핵심 수치 대조, 예외 테스트
구현·사용성AI와 코드 초안·수정, 화면과 사용 흐름, 배포

역할은 독점 업무가 아닙니다. 팀원 모두 실제 데이터를 읽고, 적어도 하나의 결과 대조나 기능 테스트를 직접 수행합니다. 중요한 데이터 선택·문제 재정의·기능 범위·수정 사항은 함께 결정합니다. 한 사람이 코드를 맡고 나머지는 발표 자료만 만드는 방식으로 끝내지 않습니다.

STEP 1 · 궁금증에서 작은 문제로

섹션 제목: “STEP 1 · 궁금증에서 작은 문제로”

먼저 학교생활·문화·언어·경제·환경·안전·지역사회·진로 등 팀이 계속 궁금해할 분야를 정합니다. 대상 사용자와 불편을 구체적으로 적고, 현재 상태와 원하는 상태를 비교합니다.

현재 [사용자]는 [상황]에서 [작은 불편]을 겪을 수 있다. 우리는 [대상·기간·지역·지표를 포함한 질문]을 데이터로 확인하고 싶다.

사용자의 불편은 인터뷰나 관찰로 추가 확인할 수 있습니다. 수업에 불필요한 이름·연락처·성적·건강 정보는 수집하지 않습니다. 공공데이터에서 현상을 확인했다고 모든 사용자가 같은 불편을 겪는다고 단정하지 않습니다.

주제의 크기를 줄이는 예

섹션 제목: “주제의 크기를 줄이는 예”
처음 생각작은 첫 기능의 후보확보해야 할 데이터
급식 문제를 해결하자기간·검색어로 식단 기록을 찾는다.실제 학교·날짜·식사·메뉴 기록
문화생활을 돕자지역·기간 조건에 맞는 공개 행사 정보를 찾는다.행사명·기간·지역·이용 조건
지역 시설 이용을 돕자공개 자료의 조건에 맞는 시설 후보를 비교한다.시설명·주소·운영정보 등 실제 제공 항목
관심 분야의 변화를 알리자지역·연도를 바꾸며 같은 지표를 비교한다.비교 가능한 공식 통계표

위 항목은 후보입니다. 필요한 열과 기간이 실제로 공개되어 있는지 먼저 확인합니다. 운영시간 자료만으로 실시간 빈자리를 안내하거나, 식단 자료만으로 선호도를 예측한다고 약속하지 않습니다.

STEP 2 · 실제 공공데이터 확보하기

섹션 제목: “STEP 2 · 실제 공공데이터 확보하기”

공식 포털에서 관련 자료 후보를 비교하고, 사용할 자료를 직접 열어 봅니다. 검색 결과 제목이나 AI의 설명만으로 데이터 확보를 마치지 않습니다.

  1. 출처 확인

    기관·데이터 이름·원문 주소·이용 조건·기준 시점과 조회 조건을 기록합니다.

  2. 실제 내용 열기

    파일 또는 API 응답의 일부 기록을 확인합니다. 샘플 응답과 전체 자료를 구분합니다.

  3. 항목 적합성 판단

    질문과 앱 기능에 필요한 행·열·단위가 있는지 확인합니다. 없는 항목은 생성하지 않습니다.

  4. 기계가 처리할 자료 준비

    첫 버전은 CSV 등 실제 파일로 시작할 수 있습니다. 필요한 경우 원표의 일부를 이용 조건에 맞게 옮기되, 전사 범위와 대조 기록을 남깁니다.

  5. 질문 조정

    자료가 없거나 비교 기준이 다르면 기간·지역·질문·기능을 수정합니다.

⚠️ 문제를 이해하는 통계와 기능을 작동시키는 자료는 다를 수 있습니다

예를 들어 문화활동 참여율은 현황 분석에 사용할 수 있지만 특정 날짜의 행사를 안내하려면 개별 행사 자료가 더 필요합니다. 두 자료가 같아야 하는 것은 아니지만, 이번 앱의 핵심 기능에는 실제 공공데이터가 사용되어야 합니다.

STEP 3 · 정리·분석하고 처음 생각 다시 보기

섹션 제목: “STEP 3 · 정리·분석하고 처음 생각 다시 보기”

원본은 보존하고 사본에서 정리합니다. 필터, 삭제, 날짜·단위 변환, 중복 처리, 집계 기준을 기록합니다. 누락은 자동으로 0이 되지 않으며, 비슷한 항목을 묶었다면 그 기준을 설명해야 합니다.

복잡한 통계 기법이 필수는 아닙니다. 날짜별 개수, 조건별 비교, 단순한 비율이나 변화도 질문에 적절하면 분석이 됩니다. 표나 그래프 중 질문에 맞는 표현을 선택하고 핵심 값 두 개 이상을 원자료와 직접 대조합니다.

☑️ 제작에 들어가기 전 통과 기준

  • 실제 데이터 일부를 열어 보고 출처와 이용 조건을 확인했다.
  • 질문에 대한 작은 분석과 핵심 값 대조를 마쳤다.
  • 입력·처리·출력으로 핵심 기능 하나를 설명할 수 있다.
  • 데이터에 없는 기능을 약속하지 않았다.
  • 테스트할 입력과 기대 결과를 원자료에서 준비했다.

STEP 5 · 생성형 AI와 최소 기능 구현하기

섹션 제목: “STEP 5 · 생성형 AI와 최소 기능 구현하기”

공통 실습에서 사용한 ‘데이터 읽기 → 조건 → 계산 → 출력’ 구조를 재사용할 수 있습니다. 새 자료의 열과 의미에 맞게 바꾸는 이유를 설명합니다.

처음에는 파일 기반 앱으로 충분합니다. 데이터 파일을 사용자가 선택하는 방식인지, 이용 조건을 확인한 공개 자료를 앱에 포함하는 방식인지 정합니다. 파일 선택 방식이라면 테스트할 사람에게 합법적으로 공유할 수 있는 동일 자료와 출처 안내를 별도로 제공합니다.

정상 작동한 버전을 보관하고 한 번에 기능 하나씩 변경합니다. AI가 제안한 추가 기능을 모두 넣을 필요는 없습니다. 더 화려해지는 것보다 결과가 정확하고 설명 가능한지가 먼저입니다.

선택 확장으로 AI 기능을 넣는다면

섹션 제목: “선택 확장으로 AI 기능을 넣는다면”

분류·예측·생성 기능이 실제로 실행되는지, 일반 규칙과 어떻게 다른지 설명합니다. 필요한 데이터·서비스 이용 조건·비용·검증 방법을 먼저 확인합니다. 공개 HTML이나 GitHub 저장소에 인증키를 넣지 않습니다. 안전한 키 관리나 서버 구성이 준비되지 않았다면 API 연결 없이 범위를 줄입니다.

STEP 6 · 정확성과 사용성을 따로 테스트하기

섹션 제목: “STEP 6 · 정확성과 사용성을 따로 테스트하기”

데이터 테스트는 계산·필터가 맞는지 확인합니다. 사용자 테스트는 다른 사람이 원하는 결과를 찾을 수 있는지 확인합니다. 친구가 ‘좋다’고 말했다고 정확성 검증이 끝나는 것은 아닙니다.

누락·중복 또는 잘못된 파일
다른 사용자의 이용수행할 과제찾을 수 있어야 할 결과막힌 장면

다른 팀이나 친구에게 앱과 필요한 자료를 주고, “설명 없이 조건을 바꿔 결과를 찾아보세요”처럼 작은 과제를 제시합니다. 개인정보는 기록하지 않고 불편한 장면과 의견만 남깁니다.

오류나 불편을 바탕으로 한 가지 이상을 수정합니다. 수정 후 새 기능뿐 아니라 이전에 통과한 테스트도 다시 확인합니다.

STEP 7 · 시연·발표·개별 성찰

섹션 제목: “STEP 7 · 시연·발표·개별 성찰”

최종 제출물은 작동하는 웹앱, 데이터 분석·기획 기록, 검증·개선 기록입니다. 앱은 접속 가능한 주소 또는 실행 가능한 파일과 실행 안내로 제출합니다. 공개 배포는 이용 조건과 학교 운영 기준에 따릅니다.

제출 내용포함할 것
앱과 실행 안내URL 또는 실행 파일, 실제 데이터 준비·선택 방법, 사용 순서
데이터·분석·기획출처와 이용 조건, 원본·사본 구분, 정리 기준, 핵심 표·그래프, 한 장 기획서
검증·개선기대 결과와 실제 결과, 사용자 의견, 수정 전후와 재검증
AI 협업·개별 기여채택·수정·거절한 제안, 직접 판단한 이유, 각자의 수행 기록

발표에서는 다음 이야기가 이어지도록 합니다.

프로젝트 완료 기준

섹션 제목: “프로젝트 완료 기준”

📊 화려함보다 데이터·판단·검증을 봅니다

  • 구체적인 사용자와 작은 질문을 정했다.
  • 실제 공공데이터의 출처·기간·단위·이용 조건·한계를 설명했다.
  • 질문에 맞는 분석을 하고 핵심 값 두 개 이상을 원자료와 대조했다.
  • 사실·해석·원인 가설을 구분하고 필요에 따라 문제를 수정했다.
  • 공공데이터가 실제 기능에 사용되는 작은 웹앱을 구현했다.
  • AI의 개발 도움과 앱에서 실행되는 기능을 정확히 구분했다.
  • 정상·빈 결과·예외 테스트와 사용자 테스트를 수행했다.
  • 한 가지 이상 수정하고 재검증했다.
  • 각 팀원이 직접 판단·검증한 내용을 설명했다.

진로 이름, 기능 수, 유료 도구 사용, 모델 학습 여부가 완성도를 대신하지 않습니다. 수업에서는 탐구한 결과를 작은 기능으로 구현하고 확인하는 데까지 책임집니다. 학교 공식 서비스 운영은 보안·유지보수·데이터 갱신을 별도로 검토해야 하는 다음 단계입니다.
