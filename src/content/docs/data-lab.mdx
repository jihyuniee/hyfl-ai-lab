## 1. 오늘 만들 수 있는 작은 앱

급식 API에서 받는 값은 같아도 앱의 기능은 다르게 만들 수 있습니다. 오늘은 작게 시작하고, 실행 결과를 보며 필요한 부분만 고칩니다.

| 만들 기능 | 사용자가 화면에서 고르는 값 | 앱 안에서 한 번 더 찾는 값 | 화면에 보여 줄 결과 |
| --- | --- | --- | --- |
| 날짜별 급식 카드 | 날짜 또는 기간, 식사구분 | 없음 | 날짜, 식사명, 메뉴, 칼로리 |
| 메뉴 이름 검색 | 기간, 식사구분 | 메뉴 검색어 | 해당 메뉴가 나온 날짜, 식사명, 메뉴 |
| 알레르기 번호 찾기 | 기간, 식사구분 | 알레르기 번호 | 해당 번호가 들어간 메뉴와 날짜 |
| 칼로리 기준으로 찾기 | 기간, 식사구분 | 칼로리 기준값 | 기준보다 높은 날짜, 칼로리, 메뉴 |
| 날짜별 영양정보 보기 | 날짜 또는 기간, 식사구분 | 없음 | 날짜, 식사명, 영양정보 |

예를 들어 “급식에 케이크가 언제 나왔는지 찾고 싶다”면 API 주소에 <code>케이크</code>를 직접 넣는 것이 아닙니다. 먼저 날짜나 기간으로 급식 데이터를 받아 온 뒤, 앱이 <code>DDISH_NM</code> 안에서 <code>케이크</code>라는 글자를 찾아 보여 줍니다.

<Callout kind="concept" title="요청인자와 앱 필터 구분하기">요청인자는 API 서버에 보내는 조건입니다. 메뉴 검색어, 알레르기 번호, 칼로리 기준처럼 API 문서에 요청인자로 없는 조건은 서버에 바로 보내지 않고, 받아 온 데이터 안에서 앱이 다시 골라냅니다.</Callout>

## 2. 활동지 STEP 6을 HTML 화면으로 옮기기

지난 시간 활동지 마지막 표에서 체크한 JSON 이름표가 오늘 HTML 화면의 재료입니다. 전부 넣으려고 하기보다, 내가 만들 기능에 필요한 값부터 화면에 보여 줍니다.

| JSON 이름표 | HTML 화면에서는 | 구현 예시 |
| --- | --- | --- |
| <code>MLSV_YMD</code> | 급식 날짜 | 카드 제목 또는 날짜 배지 |
| <code>MMEAL_SC_NM</code> | 조식, 중식, 석식 표시 | 식사구분 배지 |
| <code>DDISH_NM</code> | 메뉴 목록, 알레르기 번호 | 줄바꿈 된 메뉴 목록 |
| <code>CAL_INFO</code> | 칼로리 | 작은 정보칸, 높은 순서 정렬 기준 |
| <code>NTR_INFO</code> | 영양정보 | 필요할 때 펼쳐 보는 정보 |
| <code>RESULT.MESSAGE</code> | 데이터가 없을 때 안내 문구 | 조건에 맞는 급식이 없습니다 |

활동지의 “다음 시간에 만들고 싶은 기능 한 줄”은 앱의 목표가 됩니다. 예를 들어 <code>케이크가 나온 날 찾기</code>라고 썼다면, 사용자는 기간과 검색어를 입력하고 화면에서는 케이크가 들어간 날짜와 메뉴를 보여 주면 됩니다.

## 3. 요청인자와 출력값 먼저 고르기

HTML을 만들기 전에 세 가지를 정하면 프롬프트가 훨씬 정확해집니다. 첫째, 코드에 고정할 값입니다. 둘째, 사용자가 화면에서 직접 고를 값입니다. 셋째, 활동지에서 체크한 값 중 화면에 보여 줄 출력값입니다.

| 구분 | 값 | 앱에서 쓰는 방식 |
| --- | --- | --- |
| 고정할 기본 인자 | <code>KEY</code>, <code>Type</code>, <code>pIndex</code>, <code>pSize</code> | 코드 안에 기본값으로 넣음 |
| 고정할 학교 정보 | <code>ATPT_OFCDC_SC_CODE</code>, <code>SD_SCHUL_CODE</code> | 우리 학교 앱이면 보통 고정 |
| 사용자가 고를 요청인자 | <code>MLSV_YMD</code>, <code>MLSV_FROM_YMD</code>, <code>MLSV_TO_YMD</code>, <code>MMEAL_SC_CODE</code> | 날짜, 기간, 식사구분 입력칸으로 만듦 |
| 앱 안에서 필터링할 값 | 메뉴 검색어, 알레르기 번호, 칼로리 기준값 | 데이터를 받은 뒤 JavaScript로 조건에 맞는 것만 고름 |
| 화면 출력값 | 활동지에서 체크한 JSON 이름표 | 카드, 표, 목록으로 보여 줌 |

식사구분 코드는 보통 <code>1</code> 조식, <code>2</code> 중식, <code>3</code> 석식으로 사용합니다. 전체를 보고 싶을 때는 <code>MMEAL_SC_CODE</code>를 요청 주소에서 빼고 조회할 수 있습니다.

| 앱 아이디어 | 사용자 선택 화면 | 먼저 보여 줄 출력값 | 추가로 보여 줄 수 있는 값 |
| --- | --- | --- | --- |
| 오늘의 급식 카드 | 날짜, 식사구분 | 메뉴, 칼로리 | 영양정보 |
| 메뉴 검색 앱 | 기간, 식사구분, 검색어 | 검색어가 들어간 날짜와 메뉴 | 총 몇 번 나왔는지 |
| 알레르기 확인 앱 | 기간, 식사구분, 알레르기 번호 | 해당 번호가 들어간 메뉴 | 해당 메뉴 강조 표시 |
| 칼로리 비교 앱 | 기간, 식사구분, 기준 칼로리 | 기준보다 높은 날짜와 칼로리 | 높은 순서 정렬 |
| 영양정보 앱 | 날짜 또는 기간, 식사구분 | 영양정보 | 메뉴와 함께 보기 |

## 4. API 키가 코드에서 쓰이는 위치

HTML 앱은 JavaScript 코드 안에서 API 주소를 만들고 데이터를 요청합니다. 지난 시간에 확인한 값이 코드의 재료가 됩니다.

~~~js
const API_KEY = "수업용_인증키";
const OFFICE_CODE = "B10";
const SCHOOL_CODE = "7010259";
const API_URL = "https://open.neis.go.kr/hub/mealServiceDietInfo";
~~~

사용자가 화면에서 날짜, 기간, 식사구분을 선택하면 앱은 그 값을 API 요청 주소에 넣습니다. 서버가 JSON 응답을 보내면 앱은 <code>row</code> 안에서 활동지에 체크한 <code>MLSV_YMD</code>, <code>DDISH_NM</code>, <code>CAL_INFO</code> 같은 값을 찾아 화면에 표시합니다.

~~~js
const params = new URLSearchParams({
  KEY: API_KEY,
  Type: "json",
  pIndex: "1",
  pSize: "100",
  ATPT_OFCDC_SC_CODE: OFFICE_CODE,
  SD_SCHUL_CODE: SCHOOL_CODE,
  MLSV_FROM_YMD: "20261001",
  MLSV_TO_YMD: "20261031",
});
~~~

<Callout kind="caution" title="수업용 API 키 사용 범위">수업용 API 키는 교사가 안내한 범위에서 사용합니다. 오늘 제출 파일은 교실 안에서 확인하고, 공개 GitHub Pages나 공개 저장소에 올릴 때는 실제 키를 가리거나 다른 방식을 사용합니다.</Callout>

## 6. 실행하며 관찰하기

웹앱을 실행한 뒤, 아래 항목을 직접 확인합니다.

| 확인할 기능 | 테스트 방법 |
| --- | --- |
| API 요청 | 조회 버튼을 눌렀을 때 데이터가 불러와지는지 확인 |
| 요청인자 반영 | 날짜, 기간, 식사구분을 바꾸면 다른 데이터가 나오는지 확인 |
| 앱 필터 반영 | 메뉴 이름, 알레르기 번호, 칼로리 기준이 결과에 반영되는지 확인 |
| 활동지 체크값 표시 | 체크한 JSON 이름표가 화면에 보이는지 확인 |
| 결과 없음 | 찾는 값이 없을 때 안내 문구가 나오는지 확인 |
| 출처 표시 | 화면 아래에 NEIS 급식식단정보 출처가 보이는지 확인 |

테스트할 때는 브라우저에서 본 JSON 원문과 앱 화면 결과를 비교합니다. 날짜와 메뉴가 맞으면 데이터 연결이 된 것입니다.

## 7. 바이브코딩 수정 요청하기

바이브코딩은 작게 만들고, 실행하고, 고쳐 가는 반복입니다. AI에게 요청할 때는 현재 상태, 바꾸고 싶은 점, 유지할 기능, 테스트 방법을 함께 적습니다.

| 요청에 넣을 내용 | 예시 |
| --- | --- |
| 현재 상태 | 메뉴 검색은 되지만 결과가 너무 길게 보임 |
| 바꾸고 싶은 점 | 결과를 날짜별 카드로 정리 |
| 유지할 기능 | API 요청, 메뉴 줄바꿈, 출처 표시 |
| 테스트 방법 | 같은 기간에서 같은 검색어로 다시 확인 |

<CopyPrompt title="앱을 한 번 수정하는 프롬프트" content={revisePrompt} />

수정 요청은 한 번에 하나씩 하는 것이 좋습니다. 예를 들어 먼저 “결과 카드로 보여 주기”를 고치고, 그다음 “칼로리 높은 순서로 정렬하기”를 요청합니다. 수정 뒤에는 같은 조건으로 다시 실행합니다.

## 8. 오류가 날 때 설명하기

오류가 나면 화면에 나온 메시지, 입력한 값, 기대한 결과를 함께 적습니다. “안 돼요”보다 “어떤 조건에서 어떤 결과가 나왔는지”를 알려 주면 AI가 원인을 찾기 쉽습니다.

<CopyPrompt title="오류를 설명하고 고치는 프롬프트" content={errorPrompt} />

자주 만나는 상황은 다음과 같습니다.

| 상황 | 먼저 확인할 것 |
| --- | --- |
| 데이터가 안 나옴 | API 키, 학교 코드, 날짜 범위, 인터넷 연결 |
| 결과가 비어 있음 | 실제로 해당 기간에 메뉴가 있는지 JSON 원문 확인 |
| 메뉴 검색이 안 됨 | 검색어를 API 요청 주소에 넣었는지, 받은 <code>DDISH_NM</code>에서 필터링했는지 확인 |
| 칼로리 비교가 이상함 | <code>1196.2 Kcal</code>에서 숫자만 꺼냈는지 확인 |
| 메뉴 줄바꿈이 안 됨 | <code>&lt;br/&gt;</code>를 줄바꿈으로 바꾸는 코드 확인 |
| 화면이 불편함 | 먼저 보여 줄 정보와 버튼 위치 설명 |

## 9. 작업 방식 선택하기

오늘은 누구나 할 수 있는 방식으로 시작합니다. 도구가 준비된 팀은 연결형 방식으로 확장할 수 있습니다.

| 방식 | 오늘 할 일 | 어울리는 상황 |
| --- | --- | --- |
| 기본 방식 | AI가 준 코드를 복사해 <code>index.html</code>에 붙여 넣고 브라우저로 실행 | 짧은 시간에 첫 앱을 확인할 때 |
| 수정 반복 방식 | 실행 결과를 보고 AI에게 한 부분씩 수정 요청 | 기능을 조금씩 바꿔 보고 싶을 때 |
| 연결형 방식 | GitHub, Codespaces, Claude Code, Codex 같은 도구로 파일을 직접 수정 | 팀 프로젝트에서 여러 번 고칠 때 |

연결형 방식은 계정, 권한, 저장소 설정이 필요할 수 있습니다. 오늘은 <code>index.html</code> 파일을 완성하고 실행 결과를 확인하는 것을 목표로 합니다.

오늘의 급식 앱은 팀 프로젝트의 작은 연습입니다. 최종 프로젝트에서는 문제를 정하고, 데이터 길을 선택하고, 사용자가 실제로 쓸 수 있는 웹앱으로 발전시킵니다.

| 출발점 | 데이터 활용 방식 | 앱형 프로젝트 예시 |
