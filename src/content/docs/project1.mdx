**SCHOOL IMAGE LAB**은 학교 안에서 반복해서 확인해야 하거나 놓치기 쉬운 작은 문제를 찾아, 이미지 분류 AI가 실제로 도움이 될지 직접 실험하는 프로젝트입니다.

이 프로젝트에서는 **문제 발견 → 데이터 설계·수집 → 모델 테스트·개선 → 구현·공유·판단**의 과정을 스스로 설명합니다.

<Callout kind="mission" title="이번 프로젝트에서 가장 중요한 질문">
**“학교의 어떤 문제에 이미지 분류 AI가 도움이 되며, 어디까지 믿고 사용할 수 있을까?”**를 끝까지 탐구합니다.
</Callout>

## 교과서와 활동지는 이렇게 사용합니다

- **교과서**에서는 각 단계의 핵심 개념과 판단 기준을 이해합니다.
- **활동지**에는 팀이 실제로 결정한 내용과 중요한 테스트 결과만 기록합니다.
- **TALK → DECIDE → TRY → TEST → RECORD**의 리듬으로 진행합니다.
- 활동지는 차시마다 새로 작성하지 않고 프로젝트가 끝날 때까지 이어서 완성합니다.

### 일반적인 기계학습 문제 해결 과정과 연결하기

기계학습 프로젝트는 보통 **문제 정의 → 데이터 수집·준비 → 학습 방법 선택과 모델 학습 → 평가·개선 → 활용·배포**의 순환 과정으로 진행됩니다. 실제 프로젝트에서는 평가 결과에 따라 문제나 데이터 단계로 되돌아가므로 한 번만 지나가는 직선 과정은 아닙니다.

| 일반적인 과정 | 이 프로젝트에서 수행하는 단계 |
| --- | --- |
| 문제 정의와 기계학습의 필요성 판단 | STEP 1 · 사용자·문제·대안·클래스 정의 |
| 데이터 수집과 준비 | STEP 2 · 학습용·테스트용 데이터 설계·수집, 라벨 확인 |

| 오류 분석과 개선 | STEP 3 · 원인 가설, 데이터·기준 수정, 재학습과 비교 |

</Callout>

## STEP 1 · 문제를 발견하고 정의하기

### 학교생활의 문제부터 찾기

학교생활에서 사람이 반복해서 확인하는 일, 놓치기 쉬운 상태, 사진·소리·자세를 통해 확인하면 도움이 될 상황을 먼저 찾습니다.

예를 들어 “하교 전 교실 창문을 일일이 확인하는 불편을 줄이기 위해 열림과 닫힘을 구분한다”와 같이 사용자, 상황, 문제와 목적이 드러나도록 표현합니다.

### 주제 후보를 비교하고 선택하기

처음 떠오른 주제를 바로 확정하기 전에 팀원들이 각자 아이디어를 내고 후보를 두세 개 만듭니다. 다음 기준으로 비교하여 팀이 함께 탐구할 문제를 선택합니다.

| 살펴볼 기준 | 확인할 질문 |
| --- | --- |
| 실제성 | 우리 학교에서 직접 경험하거나 관찰한 문제인가? |
| 구체성 | 누구에게 언제 필요한 문제인지 설명할 수 있는가? |
| 결과의 쓰임 | 모델이 분류한 뒤 사용자가 취할 행동이 있는가? |
| 분류 가능성 | 두 상태의 차이를 눈·귀·자세로 분명하게 확인할 수 있는가? |
| 실행 가능성 | 학교에서 안전하게 데이터를 모으고 여러 번 테스트할 수 있는가? |
| 팀의 흥미 | 팀원들이 역할을 나누어 끝까지 재미있게 탐구하고 싶은가? |

특히 **“모델이 A라고 판단하면 사용자는 무엇을 하게 되는가?”**를 질문해 봅니다. 분류 결과가 알림, 확인, 정리, 안내와 같은 실제 행동으로 이어지는지 살펴보면 프로젝트의 필요성을 더 분명하게 판단할 수 있습니다.

### 문제를 한 문장으로 구체화하기

다음 문장에 맞추어 팀의 문제를 설명해 봅니다.

> **[누구]가 [어떤 상황]에서 겪는 [어떤 문제]를 줄이기 위해 [무엇]과 [무엇]을 구분한다.**

예를 들어 “마지막으로 교실을 나가는 사람이 하교 전에 창문을 다시 확인하는 수고를 줄이기 위해 창문의 열림과 닫힘을 구분한다”라고 표현할 수 있습니다.

### 굳이 AI가 필요할까?

표지판이나 체크리스트 같은 단순한 방법도 함께 살펴보고, 분류 AI를 사용해볼 가치가 있는지 판단합니다.

| 확인할 질문 | 판단 기준 |
| --- | --- |
| 분류 AI가 도움이 되는가? | 사람이 계속 직접 확인하기 어려운 상황인가? |
| 더 단순한 방법은 없는가? | 표지판·위치 변경·점검표·간단한 규칙으로 해결하기 어려운가? |
| 입력에서 차이가 확인되는가? | 사람이 사진·소리·자세만 보고도 두 상태의 차이를 설명할 수 있는가? |
| 틀렸을 때 안전한가? | 큰 피해가 없고 사람이 다시 확인할 수 있는가? |

<Callout kind="caution" title="AI를 안전하게 사용할 수 있는 주제를 선택합니다">
주제는 입력에서 직접 확인할 수 있고, 사람이 최종 확인할 수 있으며, 수업 시간에 안전하게 실험할 수 있는 문제로 정합니다. 사람의 감정·성격·능력·의도를 추측하거나 결과가 사람에게 불이익을 줄 수 있는 주제는 제외합니다.
</Callout>

### 문제에 맞는 입력 방식 선택하기

이 프로젝트는 이미지 분류를 기본으로 진행합니다. 문제를 판단하는 데 소리나 자세가 더 중요한 팀은 수업에서 사용할 수 있는지 확인한 뒤 티처블 머신의 음성 또는 포즈 분류를 선택할 수 있습니다.

| 입력 방식 | 적합한 문제 | 확인할 점 |
| --- | --- | --- |
| 이미지 분류 | 물건·공간·상태처럼 화면에 보이는 차이 | 거리·각도·밝기·배경이 달라져도 구분되는가? |
| 음성 분류 | 특정 소리의 발생 여부나 소리 종류 | 대화와 개인정보가 녹음되지 않는가? 배경 소음에서도 구분되는가? |
| 포즈 분류 | 몸의 위치와 형태로 확인할 수 있는 자세 | 참여자의 동의를 받았는가? 사람마다 자세가 달라도 구분되는가? |

음성·포즈 분류의 대상은 소리나 자세에서 직접 확인할 수 있는 상태로 정합니다. 특정 학생 식별과 태도·감정·능력 평가는 주제에서 제외합니다. 음성과 포즈 데이터에 사람이 포함될 때에는 참여자의 동의를 받고 안전하게 재현할 수 있는 상황에서 수집합니다.

<Callout kind="concept" title="활동지는 선택한 입력 방식에 맞게 읽습니다">
음성 분류를 선택한 팀은 활동지의 ‘사진·촬영·이미지 수’를 ‘소리·녹음·음성 샘플 수’로, 포즈 분류를 선택한 팀은 ‘사진·촬영·이미지 수’를 ‘자세·촬영·포즈 샘플 수’로 바꾸어 생각하며 작성합니다.
</Callout>

### 클래스는 ‘확인할 수 있는 기준’으로 정의하기

팀원 모두가 같은 기준으로 데이터를 모을 수 있도록 클래스별로 사진·소리·자세에서 직접 확인할 수 있는 기준을 정합니다.

| 불분명한 기준 | 더 구체적인 기준 |
| --- | --- |
| 정리됨 / 정리 안 됨 | 물건이 지정 위치에 있음 / 지정 위치를 벗어난 물건이 있음 |
| 창문 열림 / 닫힘 | 창틀 사이에 틈이 보임 / 창문이 끝까지 닫혀 틈이 보이지 않음 |
| 조용함 / 시끄러움 | 정한 기준 소리가 들리지 않음 / 정한 기준 소리가 반복해서 들림 |
| 준비 자세 / 동작 자세 | 팀이 정한 관절 위치와 몸의 방향이 보임 / 다음 동작의 관절 위치와 방향이 보임 |

사람마다 판단이 크게 다르거나 입력만으로 기준을 설명하기 어렵다면 클래스 기준이나 주제를 다시 검토합니다.

### 활동지에는 무엇을 남길까?

다음의 **결정**을 기록합니다.

1. 누구의 어떤 문제인지
2. 현재 해결 방법과 한계
3. AI를 사용해볼 가치가 있는지
4. 선택한 입력 방식과 두 클래스의 차이
5. 이 문제를 선택한 이유

## STEP 2 · 모델이 배울 데이터를 설계하고 직접 수집하기

### AI는 우리가 보여준 사진에서 배웁니다

이미지 분류 모델은 학습 사진에서 반복해서 나타나는 시각적 특징을 찾아 분류에 사용합니다.

팔찌는 항상 손목에서, 시계는 항상 책상 위에서 촬영했다면 모델은 **손목과 책상 배경**을 주요 특징으로 배울 수 있습니다. 학습 화면에서는 잘 맞아도 배경이 달라지면 쉽게 틀릴 수 있습니다.

<Callout kind="concept" title="데이터에서 함께 살펴볼 네 가지">
**양**은 충분한가, **균형**은 두 클래스가 지나치게 차이 나지 않는가, **다양성**은 여러 촬영 조건을 담았는가, **정확성**은 사진과 라벨이 클래스 기준에 맞는가를 함께 확인합니다.
</Callout>

균형은 클래스별 수만 같게 만드는 일이 아닙니다. 각 클래스가 실제 사용 환경에서 만날 사람·장소·밝기·배경·기기 조건을 고르게 담고 있는지도 함께 확인합니다.

### 다양하게 찍는다는 것은 무엇일까?

실제 사용 환경을 고려해 거리·각도·밝기·배경·위치·촬영자를 바꾸어 촬영합니다.

| 바꿀 수 있는 조건 | 생각해볼 질문 |
| --- | --- |
| 거리 | 가까운 사진과 먼 사진이 모두 있는가? |
| 각도 | 정면·옆·위 등 여러 방향에서 촬영했는가? |
| 밝기 | 밝은 곳, 어두운 곳, 그림자가 있는 상황을 담았는가? |
| 배경·장소 | 한 장소나 배경에만 치우치지 않았는가? |
| 물체 위치·상태 | 위치, 방향, 크기, 가려짐이 달라지는가? |
| 촬영자 | 여러 팀원이 서로 다른 방식으로 촬영했는가? |

**모델이 실제로 사용될 때 달라질 가능성이 있는 조건**을 팀이 골라 데이터에 반영합니다.

### 학습용과 테스트용을 왜 나눌까?

- **학습용 데이터**: 모델이 특징을 찾는 데 사용하는 사진
- **테스트용 데이터**: 학습에 넣지 않고 새로운 상황에서도 작동하는지 확인하는 사진

테스트용 사진은 처음부터 학습 데이터와 분리합니다. 개선 전후를 비교할 때에는 가능하면 같은 테스트 사진이나 조건을 사용합니다.

<Callout kind="caution" title="사람의 권리를 지키며 데이터를 수집합니다">
사람의 얼굴을 촬영할 때에는 먼저 동의를 받습니다. 이름·학번·명찰 등 개인정보를 제외하고, 얼굴이 우연히 포함된 사진도 확인합니다. 학습 데이터는 가능한 한 팀이 직접 촬영한 자료와 사용 허가를 받은 자료로 구성합니다.
</Callout>

### 활동지에는 무엇을 남길까?

1. 클래스별 목표 수, 실제 수집 수, 테스트용 사진 수
2. 다양하게 만든 촬영 조건 네 가지 이상
3. 아직 부족할 것 같은 조건
4. 개인정보·초상권·저작권을 보호하기 위해 실제로 한 행동
5. 데이터의 강점과 부족할 수 있는 부분

## STEP 3 · 모델을 테스트하고, 필요하면 데이터로 개선하기

### 첫 모델은 확인의 출발점입니다

### 바이브 코딩: AI에게 코드를 맡기는 것이 아니라 함께 만들어가기

생성형 AI와 사용자의 협업은 **배우와 감독의 관계**에 비유할 수 있습니다. 배우는 감독이 제시한 인물·상황·장면·표현 조건에 따라 연기의 방향을 구체화합니다. 생성형 AI도 프롬프트에 제시된 사용자·목적·기능·조건을 문맥으로 사용하여 결과를 생성합니다.

대규모 언어 모델(LLM)은 입력된 문맥을 바탕으로 다음에 이어질 가능성이 높은 토큰을 차례로 생성하여 응답을 만듭니다. 프롬프트에 포함된 정보는 모델이 결과를 생성할 때 사용하는 문맥이 됩니다. 요구가 모호하거나 필요한 정보가 빠진 경우에는 여러 가능한 해석 중 하나가 결과에 반영됩니다.

프롬프트에 사용자·목적·모델 종류·주소·기능·사용 환경·파일 형식을 구체적으로 적으면 가능한 해석의 범위가 줄어듭니다. 결과의 정확성과 작동 여부는 **생성된 코드를 실행하고 검증하는 과정**에서 확인합니다.

좋은 프롬프트는 길기만 한 글이 아니라 **필요한 정보를 구분하여 빠짐없이 전달하는 작업 지시서**에 가깝습니다.

| 프롬프트의 요소 | AI에게 알려줄 내용 | 이 내용이 필요한 이유 |
| --- | --- | --- |
| 역할 | “웹 개발자처럼 작성해줘” | 어떤 관점과 전문성을 사용할지 정한다. |
| 맥락 | 프로젝트의 문제, 사용자, 클래스, 모델 주소 | 우리 팀의 상황과 다른 내용을 지어내지 않게 한다. |
| 과업 | 모델을 실행하는 체험 웹페이지 만들기 | 무엇을 완성해야 하는지 분명히 한다. |
| 기능 조건 | 카메라·마이크, 확률 표시, 오류 안내 | 반드시 작동해야 할 기능을 빠뜨리지 않게 한다. |
| 디자인 조건 | 스마트폰 반응형, 간결한 화면 | 사용 환경과 화면의 방향을 정한다. |
| 출력 형식 | 하나의 완성된 `index.html` | GitHub에 올릴 수 있는 형태로 결과를 받는다. |
| 검증 기준 | 모델 링크·클래스·권한·모바일 작동 확인 | 완성 기준에 따라 결과의 작동 여부를 확인한다. |

<Callout kind="concept" title="좋은 프롬프트는 첫 번째 디렉팅입니다">
코드 생성과 수정은 **실행 → 관찰 → 문제를 구체적으로 설명 → 수정 요청 → 다시 확인**의 순서로 진행합니다. 실행 환경과 관찰한 현상을 프롬프트에 포함하면 LLM이 관련된 코드의 범위를 좁혀 수정안을 생성하는 데 필요한 문맥이 제공됩니다.

### GitHub Pages로 웹페이지 배포하기

내 컴퓨터에서만 열리던 `index.html`을 다른 사람도 인터넷 주소로 열 수 있게 만드는 과정을 **배포**라고 합니다. GitHub Pages는 GitHub 저장소에 있는 HTML·CSS·JavaScript 파일을 정적 웹사이트로 공개하는 서비스입니다.

<Callout kind="caution" title="공개하기 전에 먼저 확인합니다">
GitHub Pages로 공개한 웹사이트는 인터넷에서 누구나 볼 수 있습니다. 이름·학번·얼굴·주소·전화번호·비밀번호·API 키처럼 공개하면 안 되는 정보가 코드와 화면에 들어 있지 않은지 확인합니다. 티처블 머신 모델에 얼굴이나 개인정보가 포함되지 않았는지도 다시 확인합니다.
</Callout>

**준비물**

- GitHub 계정
- 우리 팀이 실행하고 수정까지 마친 `index.html`

<Steps>
<Step title="1. 새 저장소 만들기">GitHub에 로그인하고 오른쪽 위의 **+ → New repository**를 선택합니다. 저장소 이름은 영문·숫자·하이픈을 사용해 정하고, GitHub 무료 계정에서는 Pages를 사용하기 쉽도록 **Public**을 선택합니다. **Add a README file**을 켠 뒤 저장소를 만듭니다.</Step>
<Step title="2. index.html 올리기">저장소의 파일 목록 위에서 **Add file → Upload files**를 선택합니다. `index.html`을 올리고 **Commit changes**를 누릅니다. 파일은 폴더 안이 아니라 저장소의 맨 위에 있어야 합니다.</Step>
<Step title="3. Pages 켜기">저장소 위쪽의 **Settings**로 이동합니다. 보이지 않으면 더보기 메뉴에서 찾습니다. 왼쪽 **Pages**를 선택하고, **Build and deployment → Source**에서 **Deploy from a branch**를 선택합니다.</Step>
<Step title="4. 공개할 위치 정하기">Branch를 **main**, 폴더를 `/(root)`로 선택하고 **Save**를 누릅니다. GitHub가 자동으로 사이트를 빌드하고 배포합니다.</Step>
<Step title="5. 주소 확인하기">배포가 끝난 뒤 같은 Pages 화면의 **Visit site**를 누릅니다. 프로젝트 사이트의 기본 주소는 보통 `https://깃허브아이디.github.io/저장소이름/` 형식입니다.</Step>
</Steps>

배포에는 몇 분 이상 걸릴 수 있습니다. 아직 주소가 열리지 않으면 잠시 기다린 뒤 Pages 화면과 저장소의 **Actions** 탭에서 배포 진행 상태 또는 오류를 확인합니다.

| 화면이 나오지 않을 때 확인할 것 | 확인 방법 |
| --- | --- |
| 파일 이름 | 소문자로 정확히 `index.html`인지 확인합니다. `Index.html`과 `index.htm`은 다른 이름입니다. |
| 파일 위치 | `main` 브랜치의 저장소 맨 위, 즉 선택한 `/(root)`에 있는지 확인합니다. |
| Pages 설정 | Source가 **Deploy from a branch**, Branch가 **main / (root)**인지 확인합니다. |
| 배포 상태 | **Actions** 탭에서 Pages 배포가 완료되었는지 확인합니다. |
| 접속 주소 | 끝에 저장소 이름이 포함된 정확한 주소인지 확인합니다. |
| 입력 장치 | 사이트에서 카메라·마이크 권한을 허용했는지 확인합니다. |

수정한 웹페이지를 같은 주소에 반영하려면 저장소의 기존 `index.html`을 새 파일로 교체하고 다시 **Commit changes**합니다. GitHub Pages가 변경된 내용을 다시 배포하므로 주소를 새로 만들 필요는 없습니다.

> **최종 제출:** 완성된 GitHub Pages 주소를 복사하여 구글 클래스룸 과제의 비공개 댓글에 작성합니다.

### 모델에서 컴퓨팅 시스템으로 확장하기

컴퓨팅 시스템은 외부의 데이터를 **입력**받고, 프로그램에 따라 **처리**한 뒤, 처리 결과를 **출력**합니다. 웹페이지, 피지컬 컴퓨팅 시스템, 인공지능 에이전트는 모두 이 기본 구조로 설명할 수 있습니다.

<FlowDiagram items={[
	{ ko: '입력', en: 'Input' },
	{ ko: '처리', en: 'Process' },
	{ ko: '출력', en: 'Output' },
]} />

| 시스템 | 입력 | 처리 | 출력 |
| --- | --- | --- | --- |
| 이번 웹페이지 | 카메라·마이크로 이미지·소리 입력 | 분류 모델의 예측과 JavaScript 실행 | 화면에 클래스와 확률 표시 |
| 피지컬 컴퓨팅 | 센서·버튼·카메라·마이크로 실제 환경의 상태 입력 | 프로그램이 입력값을 처리하고 동작 결정 | LED·스피커·모터 등으로 정보 전달 또는 물리적 작동 |
| 인공지능 에이전트 | 센서로 환경 인식 | 인식한 정보와 목표를 바탕으로 행동 결정 | 액추에이터를 통해 환경에 행동 |

세 경우의 차이는 기본 구조가 아니라 **입력·처리·출력의 구체적인 구성과 목적**에 있습니다. 피지컬 컴퓨팅에서는 입력과 출력이 실제 환경의 센서와 장치에 연결됩니다. 인공지능 에이전트에서는 출력된 행동이 환경에 영향을 주고, 변화한 환경이 다시 센서를 통해 다음 입력으로 들어옵니다.

인공지능 에이전트의 출력은 환경에 변화를 만들 수 있으며, 변화한 환경은 다시 센서를 통해 다음 입력으로 들어옵니다. 이 과정은 **입력 → 처리 → 출력 → 새로운 입력**의 순환 구조로 이어집니다.

이번 프로젝트의 분류 모델은 이 구조에서 **처리**의 일부를 담당합니다. 분류 모델은 입력 데이터의 클래스를 예측합니다. 하나의 시스템으로 확장하려면 입력을 받는 장치, 모델의 예측을 사용할 조건과 동작을 정하는 프로그램, 결과를 전달하거나 행동을 실행하는 출력 장치가 함께 필요합니다.

예를 들어 분리수거 모델에 카메라와 LED를 연결하면 촬영한 물체에 알맞은 분리수거함의 불을 켤 수 있습니다. 모터까지 연결하면 해당 분리수거함의 뚜껑을 여는 시스템으로 확장할 수도 있습니다. 다만 모델은 학습하지 않은 물체도 기존 클래스 중 하나로 분류할 수 있으므로, 확률만으로 모든 장치를 자동 작동하게 할지 사람이 확인하게 할지도 함께 설계해야 합니다.

웹페이지 구현을 마친 뒤, 우리 팀의 모델을 실제 환경에서 작동하는 컴퓨팅 시스템으로 확장하는 방법을 설계합니다.
</Callout>

| 그 정보를 받기 위한 센서 또는 입력 장치는 무엇인가? |  |
| 모델의 분류 결과에 따라 어떤 행동을 결정할 것인가? |  |

| 모델의 예측이 불확실하거나 틀렸을 때 사람이 확인할 지점은 어디인가? |  |

> **한 문장으로 정리하기:** 우리 팀의 모델에 **________ 센서·입력 장치**와 **________ 출력 장치·액추에이터**를 연결하면, **________________________________ 시스템**으로 확장할 수 있다.

*/}

### AI와 함께 코딩할 때도 판단은 팀이 합니다

| AI가 도울 수 있는 일 | 팀이 직접 해야 하는 일 |

| HTML·CSS·JavaScript 초안 만들기 | 프로젝트의 목적과 기능 정하기 |
| 화면 구성과 오류 수정 방법 제안 | 프롬프트에 정확한 맥락과 조건 넣기 |
| 반복되는 코드 작성과 설명 | 모델 링크·클래스·내용 확인하기 |

### 마지막에 처음 질문으로 돌아가기

프로젝트를 실제로 해본 뒤에도 AI가 필요하다고 생각하나요?

- AI를 사용하면 실제로 도움이 되는가?
- 특정 조건에서만 제한적으로 도움이 되는가?
- 사람이 확인하는 보조 도구로 사용하는 것이 적절한가?
- 다른 해결 방법이 더 적절한가?

최종 판단은 **잘 작동한 조건과 한계**를 근거로 설명합니다.

<Callout kind="concept" title="프로젝트의 마지막 판단">
AI가 맡으면 도움이 되는 일과 사람이 최종적으로 판단해야 하는 일을 구분해 봅시다. AI가 도울 범위와 사람이 책임질 범위를 분명히 정합니다.
</Callout>

## 프로젝트 완료 기준

- 문제에서 출발해 AI가 필요한지 검토했다.
- 사진에서 확인할 수 있는 기준으로 클래스를 정의했다.
- 다양한 조건의 데이터를 직접 수집하고 테스트 자료를 분리했다.
- 새로운 조건에서 모델을 시험하고 대표 결과를 기록했다.
- 문제가 있었다면 원인을 생각하고 데이터를 바꾸어 다시 확인했다.
- 문제가 없었다면 어디까지 시험했는지와 남은 한계를 설명했다.
- 웹페이지로 모델과 탐구 과정을 보여주었다.
- 생성형 AI에 맥락·과업·조건·출력 형식·검증 기준을 담아 요청하고 결과를 수정했다.
- 모델에 입력·출력 장치를 연결한 컴퓨팅 시스템의 확장 가능성을 설명했다.
- AI가 도움이 되는 일과 사람이 판단할 일을 구분했다.
- 팀원별 프로젝트 기여를 기록했다.
