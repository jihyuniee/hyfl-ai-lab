3. School Image Lab

MINI PROJECT 1 · TEAM LAB · 5~7차시
오늘의 질문학교 안에서 사진으로 상태를 구분하면 도움이 될 문제는 무엇일까?

SCHOOL IMAGE LAB은 학교 안에서 반복해서 확인해야 하거나 놓치기 쉬운 작은 문제를 찾아, 이미지 분류 AI가 실제로 도움이 될지 직접 실험하는 프로젝트입니다.

이 프로젝트에서는 문제 발견 → 데이터 설계·수집 → 모델 테스트·개선 → 구현·공유·판단의 과정을 스스로 설명합니다.

🎯 이번 프로젝트에서 가장 중요한 질문

“학교의 어떤 문제에 이미지 분류 AI가 도움이 되며, 어디까지 믿고 사용할 수 있을까?”를 끝까지 탐구합니다.

교과서와 활동지는 이렇게 사용합니다

섹션 제목: “교과서와 활동지는 이렇게 사용합니다”
  • 교과서에서는 각 단계의 핵심 개념과 판단 기준을 이해합니다.
  • 활동지에는 팀이 실제로 결정한 내용과 중요한 테스트 결과만 기록합니다.
  • TALK → DECIDE → TRY → TEST → RECORD의 리듬으로 진행합니다.
  • 활동지는 차시마다 새로 작성하지 않고 프로젝트가 끝날 때까지 이어서 완성합니다.

프로젝트 전체 흐름

섹션 제목: “프로젝트 전체 흐름”
1문제 발견·정의

사용자와 문제, 클래스 정하기

2데이터 설계·수집

다양한 사진과 테스트 자료 준비하기

3학습·테스트·개선

조건을 바꾸어 시험하고 판단하기

4구현·공유·판단

웹으로 보여주고 AI의 가치 판단하기

STEP 1 · 문제를 발견하고 정의하기

섹션 제목: “STEP 1 · 문제를 발견하고 정의하기”

학교생활의 문제부터 찾기

섹션 제목: “학교생활의 문제부터 찾기”

학교생활에서 사람이 반복해서 확인하는 일, 놓치기 쉬운 상태, 사진·소리·자세를 통해 확인하면 도움이 될 상황을 먼저 찾습니다.

예를 들어 “하교 전 교실 창문을 일일이 확인하는 불편을 줄이기 위해 열림과 닫힘을 구분한다”와 같이 사용자, 상황, 문제와 목적이 드러나도록 표현합니다.

주제 후보를 비교하고 선택하기

섹션 제목: “주제 후보를 비교하고 선택하기”

처음 떠오른 주제를 바로 확정하기 전에 팀원들이 각자 아이디어를 내고 후보를 두세 개 만듭니다. 다음 기준으로 비교하여 팀이 함께 탐구할 문제를 선택합니다.

살펴볼 기준확인할 질문
실제성우리 학교에서 직접 경험하거나 관찰한 문제인가?
구체성누구에게 언제 필요한 문제인지 설명할 수 있는가?
결과의 쓰임모델이 분류한 뒤 사용자가 취할 행동이 있는가?
분류 가능성두 상태의 차이를 눈·귀·자세로 분명하게 확인할 수 있는가?
실행 가능성학교에서 안전하게 데이터를 모으고 여러 번 테스트할 수 있는가?
팀의 흥미팀원들이 역할을 나누어 끝까지 재미있게 탐구하고 싶은가?

특히 “모델이 A라고 판단하면 사용자는 무엇을 하게 되는가?”를 질문해 봅니다. 분류 결과가 알림, 확인, 정리, 안내와 같은 실제 행동으로 이어지는지 살펴보면 프로젝트의 필요성을 더 분명하게 판단할 수 있습니다.

문제를 한 문장으로 구체화하기

섹션 제목: “문제를 한 문장으로 구체화하기”

다음 문장에 맞추어 팀의 문제를 설명해 봅니다.

[누구]가 [어떤 상황]에서 겪는 [어떤 문제]를 줄이기 위해 [무엇]과 [무엇]을 구분한다.

예를 들어 “마지막으로 교실을 나가는 학생이 하교 전에 창문을 다시 확인하는 수고를 줄이기 위해 창문의 열림과 닫힘을 구분한다”라고 표현할 수 있습니다.

굳이 AI가 필요할까?

섹션 제목: “굳이 AI가 필요할까?”

표지판이나 체크리스트 같은 단순한 방법도 함께 살펴보고, 분류 AI를 사용해볼 가치가 있는지 판단합니다.

확인할 질문판단 기준
분류 AI가 도움이 되는가?사람이 계속 직접 확인하기 어려운 상황인가?
더 단순한 방법은 없는가?표지판·위치 변경·점검표·간단한 규칙으로 해결하기 어려운가?
입력에서 차이가 확인되는가?사람이 사진·소리·자세만 보고도 두 상태의 차이를 설명할 수 있는가?
틀렸을 때 안전한가?큰 피해가 없고 사람이 다시 확인할 수 있는가?

⚠️ AI를 안전하게 사용할 수 있는 주제를 선택합니다

주제는 입력에서 직접 확인할 수 있고, 사람이 최종 확인할 수 있으며, 수업 시간에 안전하게 실험할 수 있는 문제로 정합니다. 사람의 감정·성격·능력·의도를 추측하거나 결과가 사람에게 불이익을 줄 수 있는 주제는 제외합니다.

문제에 맞는 입력 방식 선택하기

섹션 제목: “문제에 맞는 입력 방식 선택하기”

이 프로젝트는 이미지 분류를 기본으로 진행합니다. 문제를 판단하는 데 소리나 자세가 더 중요한 팀은 교사와 가능성을 확인한 뒤 티처블 머신의 음성 또는 포즈 분류를 선택할 수 있습니다.

입력 방식적합한 문제확인할 점
이미지 분류물건·공간·상태처럼 화면에 보이는 차이거리·각도·밝기·배경이 달라져도 구분되는가?
음성 분류특정 소리의 발생 여부나 소리 종류대화와 개인정보가 녹음되지 않는가? 배경 소음에서도 구분되는가?
포즈 분류몸의 위치와 형태로 확인할 수 있는 자세참여자의 동의를 받았는가? 사람마다 자세가 달라도 구분되는가?

음성·포즈 분류의 대상은 소리나 자세에서 직접 확인할 수 있는 상태로 정합니다. 특정 학생 식별과 태도·감정·능력 평가는 주제에서 제외합니다. 음성과 포즈 데이터에 사람이 포함될 때에는 참여자의 동의를 받고 안전하게 재현할 수 있는 상황에서 수집합니다.

📚 활동지는 선택한 입력 방식에 맞게 읽습니다

음성 분류를 선택한 팀은 활동지의 ‘사진·촬영·이미지 수’를 ‘소리·녹음·음성 샘플 수’로, 포즈 분류를 선택한 팀은 ‘사진·촬영·이미지 수’를 ‘자세·촬영·포즈 샘플 수’로 바꾸어 생각하며 작성합니다.

클래스는 ‘확인할 수 있는 기준’으로 정의하기

섹션 제목: “클래스는 ‘확인할 수 있는 기준’으로 정의하기”

팀원 모두가 같은 기준으로 데이터를 모을 수 있도록 클래스별로 사진·소리·자세에서 직접 확인할 수 있는 기준을 정합니다.

불분명한 기준더 구체적인 기준
정리됨 / 정리 안 됨물건이 지정 위치에 있음 / 지정 위치를 벗어난 물건이 있음
창문 열림 / 닫힘창틀 사이에 틈이 보임 / 창문이 끝까지 닫혀 틈이 보이지 않음
조용함 / 시끄러움정한 기준 소리가 들리지 않음 / 정한 기준 소리가 반복해서 들림
준비 자세 / 동작 자세팀이 정한 관절 위치와 몸의 방향이 보임 / 다음 동작의 관절 위치와 방향이 보임

사람마다 판단이 크게 다르거나 입력만으로 기준을 설명하기 어렵다면 클래스 기준이나 주제를 다시 검토합니다.

활동지에는 무엇을 남길까?

섹션 제목: “활동지에는 무엇을 남길까?”

다음의 결정을 기록합니다.

  1. 누구의 어떤 문제인지
  2. 현재 해결 방법과 한계
  3. AI를 사용해볼 가치가 있는지
  4. 선택한 입력 방식과 두 클래스의 차이
  5. 이 문제를 선택한 이유

STEP 2 · 모델이 배울 데이터를 설계하고 직접 수집하기

섹션 제목: “STEP 2 · 모델이 배울 데이터를 설계하고 직접 수집하기”

AI는 우리가 보여준 사진에서 배웁니다

섹션 제목: “AI는 우리가 보여준 사진에서 배웁니다”

이미지 분류 모델은 학습 사진에서 반복해서 나타나는 시각적 특징을 찾아 분류에 사용합니다.

팔찌는 항상 손목에서, 시계는 항상 책상 위에서 촬영했다면 모델은 손목과 책상 배경을 주요 특징으로 배울 수 있습니다. 학습 화면에서는 잘 맞아도 배경이 달라지면 쉽게 틀릴 수 있습니다.

📚 데이터에서 함께 살펴볼 네 가지

양은 충분한가, 균형은 두 클래스가 지나치게 차이 나지 않는가, 다양성은 여러 촬영 조건을 담았는가, 정확성은 사진과 라벨이 클래스 기준에 맞는가를 함께 확인합니다.

다양하게 찍는다는 것은 무엇일까?

섹션 제목: “다양하게 찍는다는 것은 무엇일까?”

실제 사용 환경을 고려해 거리·각도·밝기·배경·위치·촬영자를 바꾸어 촬영합니다.

바꿀 수 있는 조건생각해볼 질문
거리가까운 사진과 먼 사진이 모두 있는가?
각도정면·옆·위 등 여러 방향에서 촬영했는가?
밝기밝은 곳, 어두운 곳, 그림자가 있는 상황을 담았는가?
배경·장소한 장소나 배경에만 치우치지 않았는가?
물체 위치·상태위치, 방향, 크기, 가려짐이 달라지는가?
촬영자여러 팀원이 서로 다른 방식으로 촬영했는가?

모델이 실제로 사용될 때 달라질 가능성이 있는 조건을 팀이 골라 데이터에 반영합니다.

학습용과 테스트용을 왜 나눌까?

섹션 제목: “학습용과 테스트용을 왜 나눌까?”
  • 학습용 데이터: 모델이 특징을 찾는 데 사용하는 사진
  • 테스트용 데이터: 학습에 넣지 않고 새로운 상황에서도 작동하는지 확인하는 사진

테스트용 사진은 처음부터 학습 데이터와 분리합니다. 개선 전후를 비교할 때에는 가능하면 같은 테스트 사진이나 조건을 사용합니다.

⚠️ 사람의 권리를 지키며 데이터를 수집합니다

사람의 얼굴을 촬영할 때에는 먼저 동의를 받습니다. 이름·학번·명찰 등 개인정보를 제외하고, 얼굴이 우연히 포함된 사진도 확인합니다. 학습 데이터는 가능한 한 팀이 직접 촬영한 자료와 사용 허가를 받은 자료로 구성합니다.

활동지에는 무엇을 남길까?

섹션 제목: “활동지에는 무엇을 남길까?”
  1. 클래스별 목표 수, 실제 수집 수, 테스트용 사진 수
  2. 다양하게 만든 촬영 조건 네 가지 이상
  3. 아직 부족할 것 같은 조건
  4. 개인정보·초상권·저작권을 보호하기 위해 실제로 한 행동
  5. 데이터의 강점과 부족할 수 있는 부분

STEP 3 · 모델을 테스트하고, 필요하면 데이터로 개선하기

섹션 제목: “STEP 3 · 모델을 테스트하고, 필요하면 데이터로 개선하기”

첫 모델은 확인의 출발점입니다

섹션 제목: “첫 모델은 확인의 출발점입니다”

첫 모델을 다양한 조건에서 테스트하여 어떤 조건에서 잘되고 어떤 조건에서 흔들리는지 알아냅니다.

  1. 1차 모델 학습

    클래스별 실제 학습 이미지 수를 확인하고 첫 모델을 만듭니다.

  2. 새로운 사진으로 테스트

    따로 남겨둔 테스트 사진과 실제 사용 상황을 생각한 사진을 보여줍니다.

  3. 조건을 바꾸어 확인

    거리·각도·밝기·배경·가려짐 등을 바꾸며 결과를 관찰합니다.

  4. 대표 결과 세 개 기록

    모델의 특징이 잘 드러나는 결과만 고릅니다.

  5. 개선 여부 결정

    문제가 있으면 중요한 원인 하나를 개선하고, 안정적이면 확인한 범위를 기록합니다.

확률이 높으면 정답일까?

섹션 제목: “확률이 높으면 정답일까?”

모델의 CLASS A 95% 표시는 현재 입력이 학습한 두 클래스 중 어느 쪽과 더 비슷한지를 나타냅니다.

두 클래스 어디에도 속하지 않는 대상을 보여줘도 모델은 대개 둘 중 하나를 선택합니다. 결과를 볼 때는 모델이 판단하도록 만든 대상인지도 사람이 함께 확인해야 합니다.

테스트할 때 무엇을 바꿀까?

웹페이지는 무엇으로 만들어질까?

섹션 제목: “웹페이지는 무엇으로 만들어질까?”

파이썬으로 데이터 처리나 프로그램의 동작을 작성할 수 있듯이, 웹페이지도 브라우저가 해석할 수 있는 형식으로 작성해야 합니다. 기본적인 웹페이지에는 HTML·CSS·JavaScript가 서로 다른 역할로 함께 사용됩니다.

구성 요소정확한 역할이번 페이지에서 하는 일
HTML제목·문단·버튼·카메라 영역처럼 웹페이지의 내용과 구조를 표시하는 마크업 언어모델 제목, 설명, 시작 버튼, 결과가 나타날 자리를 만든다.
CSS글꼴·색·간격·배치·화면 크기 대응처럼 웹페이지의 표현과 디자인을 정하는 스타일 언어스마트폰에서도 보기 편하도록 크기와 배치를 꾸민다.
JavaScript사용자의 입력과 사건에 반응하고 데이터를 처리하여 웹페이지의 동작과 상호작용을 만드는 프로그래밍 언어버튼 클릭, 카메라·마이크 실행, 모델 불러오기, 예측 결과 갱신을 처리한다.

HTML이 ‘뼈대’, CSS가 ‘겉모습’, JavaScript가 ‘움직임’이라는 비유를 사용할 수 있지만 실제로는 위 표처럼 역할을 구분합니다. HTML도 버튼이나 입력 요소를 포함할 수 있고 CSS도 간단한 시각 효과를 만들 수 있지만, 모델을 불러오고 결과를 계속 바꾸는 핵심 동작은 JavaScript가 담당합니다.

웹 서버는 주소의 끝에 파일명이 생략되었을 때 관례적으로 index.html을 첫 화면으로 찾습니다. 이번 활동에서는 관리하기 쉽도록 HTML 안의 <style> 영역에 CSS를, <script> 영역에 JavaScript를 함께 넣어 하나의 index.html 파일로 만듭니다. 실제 웹사이트에서는 기능과 규모에 따라 HTML·CSS·JavaScript 파일을 각각 나누기도 합니다.

📚 파일 이름 뒤의 확장자

index.html에서 .html은 이 파일이 HTML 형식의 문서임을 나타내는 확장자입니다. 브라우저는 HTML을 읽어 화면의 구조를 만들고, 그 안에 연결되거나 포함된 CSS와 JavaScript를 함께 해석하여 웹페이지를 표시하고 작동시킵니다.

생성형 AI와 사용자의 협업은 배우와 감독의 관계에 비유할 수 있습니다. 배우는 감독이 제시한 인물·상황·장면·표현 조건에 따라 연기의 방향을 구체화합니다. 생성형 AI도 프롬프트에 제시된 사용자·목적·기능·조건을 문맥으로 사용하여 결과를 생성합니다.

대규모 언어 모델(LLM)은 입력된 문맥을 바탕으로 다음에 이어질 가능성이 높은 토큰을 차례로 생성하여 응답을 만듭니다. 프롬프트에 포함된 정보는 모델이 결과를 생성할 때 사용하는 문맥이 됩니다. 요구가 모호하거나 필요한 정보가 빠진 경우에는 여러 가능한 해석 중 하나가 결과에 반영됩니다.

프롬프트에 사용자·목적·모델 종류·주소·기능·사용 환경·파일 형식을 구체적으로 적으면 가능한 해석의 범위가 줄어듭니다. 결과의 정확성과 작동 여부는 생성된 코드를 실행하고 검증하는 과정에서 확인합니다.

좋은 프롬프트는 길기만 한 글이 아니라 필요한 정보를 구분하여 빠짐없이 전달하는 작업 지시서에 가깝습니다.

디자인 조건스마트폰 반응형, 간결한 화면사용 환경과 화면의 방향을 정한다.

# 만들어야 할 결과

티처블 머신 모델이 실제로 작동하는 반응형 체험 웹페이지를 만들어주세요. 사용자가 다음 과정을 경험할 수 있어야 합니다.

1. 어떤 문제를 위해 만든 모델인지 이해한다.
2. 모델이 무엇을 구분하는지 확인한다.
3. 버튼을 눌러 카메라 또는 마이크 사용을 시작한다.
4. 실시간 입력으로 모델을 시험한다.
5. 클래스별 확률과 가장 높은 예측 결과를 확인한다.
6. 모델의 결과를 사람이 다시 확인해야 하는 이유를 이해한다.

# 반드시 구현할 기능

1. 제공한 모델 주소에서 필요한 모델 파일과 메타데이터를 올바르게 불러오세요.
2. 모델 종류에 맞는 TensorFlow.js와 티처블 머신 공식 라이브러리를 사용하세요.
3. 페이지가 열리자마자 카메라나 마이크를 실행하지 말고 사용자가 시작 버튼을 눌렀을 때 권한을 요청하세요.
4. 모델을 불러오는 동안 진행 상태를 한국어로 보여주세요.
5. 입력 장치를 시작하고 중지할 수 있게 하고, 버튼을 반복해서 눌러 장치가 중복 실행되지 않게 해주세요.
6. 모든 클래스의 확률을 0%~100%의 백분율과 가로 막대로 표시하세요.
7. 가장 높은 확률의 클래스를 크게 강조하되, 가장 높은 확률이 반드시 정답은 아니라는 안내를 넣으세요.
8. 예측값이 계속 바뀌어도 화면 요소의 위치가 심하게 움직이지 않게 해주세요.
9. 모델 로딩 실패, 잘못된 모델 주소, 입력 장치 권한 거부, 장치를 사용할 수 없는 경우에 사용자가 다음 행동을 알 수 있는 한국어 오류 안내를 보여주세요.

GitHub Pages로 웹페이지 배포하기

섹션 제목: “GitHub Pages로 웹페이지 배포하기”

내 컴퓨터에서만 열리던 index.html을 다른 사람도 인터넷 주소로 열 수 있게 만드는 과정을 배포라고 합니다. GitHub Pages는 GitHub 저장소에 있는 HTML·CSS·JavaScript 파일을 정적 웹사이트로 공개하는 서비스입니다.

⚠️ 공개하기 전에 먼저 확인합니다

GitHub Pages로 공개한 웹사이트는 인터넷에서 누구나 볼 수 있습니다. 이름·학번·얼굴·주소·전화번호·비밀번호·API 키처럼 공개하면 안 되는 정보가 코드와 화면에 들어 있지 않은지 확인합니다. 티처블 머신 모델에 얼굴이나 개인정보가 포함되지 않았는지도 다시 확인합니다.

준비물

  • GitHub 계정
  • 우리 팀이 실행하고 수정까지 마친 index.html

  1. 1. 새 저장소 만들기

    GitHub에 로그인하고 오른쪽 위의 + → New repository를 선택합니다. 저장소 이름은 영문·숫자·하이픈을 사용해 정하고, GitHub 무료 계정에서는 Pages를 사용하기 쉽도록 Public을 선택합니다. Add a README file을 켠 뒤 저장소를 만듭니다.

  2. 2. index.html 올리기

    저장소의 파일 목록 위에서 Add file → Upload files를 선택합니다. index.html을 올리고 Commit changes를 누릅니다. 파일은 폴더 안이 아니라 저장소의 맨 위에 있어야 합니다.

  3. 3. Pages 켜기

    저장소 위쪽의 Settings로 이동합니다. 보이지 않으면 더보기 메뉴에서 찾습니다. 왼쪽 Pages를 선택하고, Build and deployment → Source에서 Deploy from a branch를 선택합니다.

  4. 4. 공개할 위치 정하기

    Branch를 main, 폴더를 /(root)로 선택하고 Save를 누릅니다. GitHub가 자동으로 사이트를 빌드하고 배포합니다.

  5. 5. 주소 확인하기

    배포가 끝난 뒤 같은 Pages 화면의 Visit site를 누릅니다. 프로젝트 사이트의 기본 주소는 보통 https://깃허브아이디.github.io/저장소이름/ 형식입니다.

배포에는 몇 분 이상 걸릴 수 있습니다. 아직 주소가 열리지 않으면 잠시 기다린 뒤 Pages 화면과 저장소의 Actions 탭에서 배포 진행 상태 또는 오류를 확인합니다.

화면이 나오지 않을 때 확인할 것확인 방법
파일 이름소문자로 정확히 index.html인지 확인합니다. Index.html과 index.htm은 다른 이름입니다.
파일 위치main 브랜치의 저장소 맨 위, 즉 선택한 /(root)에 있는지 확인합니다.
Pages 설정Source가 Deploy from a branch, Branch가 main / (root)인지 확인합니다.
배포 상태Actions 탭에서 Pages 배포가 완료되었는지 확인합니다.
접속 주소끝에 저장소 이름이 포함된 정확한 주소인지 확인합니다.
입력 장치사이트에서 카메라·마이크 권한을 허용했는지 확인합니다.

수정한 웹페이지를 같은 주소에 반영하려면 저장소의 기존 index.html을 새 파일로 교체하고 다시 Commit changes합니다. GitHub Pages가 변경된 내용을 다시 배포하므로 주소를 새로 만들 필요는 없습니다.

최종 제출: 완성된 GitHub Pages 주소를 복사하여 구글 클래스룸 과제의 비공개 댓글에 작성합니다.

모델에서 컴퓨팅 시스템으로 확장하기

섹션 제목: “모델에서 컴퓨팅 시스템으로 확장하기”

지금 만든 웹페이지에서는 카메라나 마이크가 입력 장치가 되고, 화면이 결과를 보여주는 출력 장치가 됩니다. 그러나 같은 모델도 다른 장치와 연결하면 실제 공간에서 작동하는 피지컬 컴퓨팅 시스템으로 확장할 수 있습니다.

역할연결할 수 있는 장치하는 일
입력카메라, 마이크, 버튼, 빛·거리·온도·움직임 센서실제 환경의 상태를 데이터로 받는다.
판단우리가 학습한 분류 모델과 프로그램의 조건입력을 분류하고 다음 동작을 정한다.
출력화면, LED, 스피커, 진동 장치결과를 사람이 보고·듣고·느끼게 한다.
작동모터, 서보모터, 잠금장치 등의 액추에이터뚜껑을 열거나 물체를 움직이는 실제 행동을 만든다.

예를 들어 분리수거 모델에 카메라와 LED를 연결하면 촬영한 물체에 알맞은 분리수거함의 불을 켤 수 있습니다. 모터까지 연결하면 해당 분리수거함의 뚜껑을 여는 시스템으로 확장할 수도 있습니다. 다만 모델은 학습하지 않은 물체도 기존 클래스 중 하나로 분류할 수 있으므로, 확률만으로 모든 장치를 자동 작동하게 할지 사람이 확인하게 할지도 함께 설계해야 합니다.
