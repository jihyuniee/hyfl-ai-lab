공공데이터포털 인증키로 데이터 받기

인증키를 받았다면, 원하는 조건을 넣어 기관에 데이터를 요청하는 차례입니다. 이 안내에서는 신청한 API의 설명 화면을 찾고, 요청주소를 만들어 실행한 뒤, 응답에서 우리 팀에 필요한 값 하나를 확인합니다.

🎯 오늘의 목표 · 실제 응답 한 번 받기

신청한 API 찾기 → 요청주소와 필수값 확인 → 주소창에서 실행 → 받은 값 하나 읽기. 성공했다면 “어떤 조건을 보냈고, 어떤 값을 받았는지” 설명해 보세요. 앱 연결은 확인한 응답을 바탕으로 이어갑니다.

구분쉽게 말하면아래 기상청 예제에서는
인증키요청하는 이용자를 확인하는 값키를 인증 항목에 넣습니다.
요청주소자료를 달라고 보낼 곳getUltraSrtNcst라는 실황 조회 기능의 주소
요청변수내가 보내는 조건의 이름과 값날짜·시각·격자, 예: nx=60
응답기관이 요청을 처리한 뒤 돌려주는 내용처리 결과와 기온·습도 등의 자료, 또는 오류 안내
① 포털 화면 찾기② 요청주소 만들기③ 받은 응답 읽기

아래 기상청 예제는 요청 방법을 익히는 사례입니다. 우리 팀이 신청한 API의 요청주소·변수 이름·응답 항목을 확인하며 같은 순서로 진행하세요. CSV·XLSX 등 파일 자료를 확보한 팀은 기존 파일 분석·구현을 이어갑니다.

1. 활용신청 다음에 펼칠 화면

섹션 제목: “1. 활용신청 다음에 펼칠 화면”

공공데이터포털의 인증키 화면과 API 사용 설명 화면을 함께 펼쳐 둡니다. API 명세서·활용가이드는 “어느 주소에 어떤 값을 보내면 무엇을 받을 수 있는지” 적힌 사용설명서입니다.

먼저, 내가 신청한 API 찾기

섹션 제목: “먼저, 내가 신청한 API 찾기”
  1. 로그인한 뒤 마이페이지의 Open API·활용신청 현황에서 신청한 서비스 이름과 승인 상태를 확인합니다. 메뉴가 단계별로 보이는 경우 마이페이지 → 데이터 활용 → Open API → 활용신청 현황으로 이동합니다.
  2. 서비스 이름과 제공기관을 확인하고 그 API의 상세 페이지를 엽니다. 설명 화면을 찾기 어려우면 포털의 공공데이터 → 데이터목록에서 같은 서비스 이름을 검색해 오픈API 항목을 엽니다.
  3. 상세 페이지에서 참고문서·활용가이드를 찾습니다. ZIP 파일이면 내려받아 압축을 풀고 사용설명서와 코드표를 확인합니다.

기상청 상세 페이지에서 실제로 찾을 위치

섹션 제목: “기상청 상세 페이지에서 실제로 찾을 위치”

기상청 단기예보 조회서비스를 열고 다음 순서로 찾아보세요. 화면에서 글자를 찾기 어려우면 Ctrl+F로 참고문서, 활용 정보, 요청주소를 검색합니다.

화면에서 찾을 곳할 일확인할 결과
이 페이지의 구성 → 참고문서활용가이드를 내려받습니다.상세기능 설명과 요청·응답 예시를 읽을 수 있습니다.
활용 정보 → 상세기능API 서비스 목록에서 초단기실황조회를 고르고 조회하기를 누릅니다.선택한 기능의 설명과 요청변수 표가 나타납니다.
API 기본 정보 → 요청주소기능까지 들어 있는 주소를 복사합니다.주소 끝에 getUltraSrtNcst가 있습니다.
요청변수(Request Parameter)필수인 행의 영문 이름·형식·샘플을 찾습니다.날짜·시각·격자 등 내가 보내야 할 값이 보입니다.
출력결과(Response Element)받고 싶은 항목의 이름과 뜻을 찾습니다.기온은 category와 obsrValue를 함께 읽는다는 것을 확인합니다.

여기서 조회하기는 선택한 기능의 사용 설명을 보는 단계입니다. 실제 데이터는 뒤에서 완성한 요청주소를 실행하거나, 제공되는 OpenAPI 호출 기능을 사용해 받습니다. 출력결과 표와 문서의 샘플은 응답 형식을 설명하는 예시이며, 방금 내 조건으로 받은 자료는 호출 후 응답에서 확인합니다.

다른 기관의 화면에서는 같은 역할의 항목 이름이 조금씩 다를 수 있습니다. 아래 표로 대응해 보세요.

포털·명세서의 표현뜻과 가져올 내용
참고문서·활용가이드API 사용 명세서입니다. 내려받아 필요한 기능의 설명·요청 예시·응답 예시를 읽습니다. 첨부 ZIP이면 압축을 풀어 문서와 코드표도 확인합니다.
상세기능·오퍼레이션(operation)같은 API 안에서 할 수 있는 조회 작업입니다. 원하는 자료를 주는 기능 하나를 선택합니다.
서비스 URL·End Point기관의 API가 있는 기본 주소입니다. 상세기능 경로를 더해야 하는지 예시와 비교합니다.
요청주소선택한 기능까지 포함한 주소일 수 있습니다. 포털이 완성된 요청주소를 주면 기능 이름을 또 붙이지 않습니다.
요청변수·요청인자기관으로 보낼 값입니다. 변수 이름·필수 여부·길이·형식·예시를 확인합니다.
출력결과·응답메시지기관에서 받을 값입니다. 항목 이름·목록 위치·단위·정상/오류 코드를 확인합니다.

예를 들어 보낼 값은 ‘격자와 시각’이고 받을 값은 ‘기온·습도 등’일 수 있습니다. 입력과 출력은 같은 이름으로 일대일 대응하지 않습니다. 문서에 없는 검색 조건을 마음대로 추가하지 않습니다.

2. 기상청 예제로 요청 기능 정하기

섹션 제목: “2. 기상청 예제로 요청 기능 정하기”

이 예제는 공공데이터포털에서 발급받은 키로 기상청 단기예보 조회서비스의 초단기실황조회(getUltraSrtNcst)를 요청합니다. 서비스 이름에 ‘예보’가 있지만 이 기능은 관측된 실황을 조회합니다. 미래 기온 예보를 받는 기능과 구분하세요.

기상청 예제를 직접 실행하려면 이 서비스의 활용신청 승인을 확인합니다. 우리 팀이 다른 API를 신청했다면 그 API의 요청주소와 조건으로 진행하세요.

같은 기상청이라도 공공데이터포털 apis.data.go.kr의 serviceKey와 기상청 API허브의 authKey는 다른 인증 체계입니다. 활용가이드에 API허브 예제가 함께 있더라도 주소와 키를 섞지 않습니다. 아래는 공공데이터포털 방식으로 통일합니다.

목적선택할 기능보내는 조건받을 항목앱에서 보여 줄 값
한 지역·기준시각의 기온 확인getUltraSrtNcst격자 nx,ny, 날짜 base_date, 시각 base_timecategory가 T1H인 항목의 obsrValue기온(℃), 관측 기준시각, 격자

지역 이름 대신 격자 좌표를 보냅니다. 포털 참고문서의 격자 자료에서 지역에 맞는 nx,ny를 찾습니다. 서울특별시 대표 격자 예시는 60, 127입니다. 모든 서울 동네가 같은 격자라는 뜻은 아니며, 위도·경도 값을 그대로 넣지 않습니다.

요청변수구분값의 예·형식필요한 이유
serviceKey필수YOUR_API_KEY요청자의 이용 권한 확인
pageNo필수1받을 페이지
numOfRows필수1000한 페이지에서 받을 개수. 실제 전체 건수와 받은 범위도 확인
dataType선택JSON (기본 XML)이번 실습은 읽을 형식을 JSON으로 지정
base_date필수선택한 날짜의 YYYYMMDD관측 기준 날짜
base_time필수선택한 정시의 HH00, 예: 0900관측 기준 시각(한국 시각)
nx, ny필수60, 127조회할 예보 격자 X·Y

현재 시각과 자료가 준비된 기준시각은 다를 수 있습니다. 초단기실황은 base_time에 정시를 넣습니다. 첫 연습에서는 현재 한국 시각보다 한 시간 앞선 정시로 시험해 보세요. 예를 들어 오전 10시 25분에 실행한다면 같은 날짜의 0900, 오전 0시 25분이라면 전날 날짜의 2300으로 조건을 잡아 봅니다. 실제 제공 시각·범위는 공식 활용가이드와 응답을 확인합니다. 아래 날짜 자리표시자는 조회 가능한 실제 날짜로 바꿉니다.

3. 요청 URL을 한 부분씩 만들기

섹션 제목: “3. 요청 URL을 한 부분씩 만들기”

① 기본 주소

② 상세기능을 한 번 붙인 요청주소

③ ? 뒤에 첫 조건, & 뒤에 다음 조건을 붙입니다. 이름=값에서 왼쪽은 문서에 나온 정확한 변수 이름, 오른쪽은 넣을 값입니다. 대소문자·버전·철자를 유지합니다.

요청변수 표의 한 행을 주소로 옮기는 방법입니다. 예를 들어 nx라는 항목에 60을 보내려면 nx=60이라고 씁니다. 앞에 이미 다른 조건이 있으면 &nx=60으로 이어 붙입니다.

설명서에서 읽은 내용주소에 넣는 모양뜻
항목 이름 nx, 넣을 값 60&nx=60격자 X 좌표를 60으로 지정
항목 이름 ny, 넣을 값 127&ny=127격자 Y 좌표를 127로 지정
항목 이름 base_time, 넣을 값 0900&base_time=090009시를 기준시각으로 지정
항목 이름 dataType, 넣을 값 JSON&dataType=JSONJSON 형식으로 받기

?는 조건이 시작되는 자리에 한 번, &는 조건과 조건 사이에, =는 이름과 값 사이에 들어갑니다. 국문 항목명은 뜻을 읽을 때, 영문 항목명은 요청을 만들 때 사용합니다. 필수 항목을 먼저 채우고, 선택 검색 조건은 기본 요청이 된 다음 하나씩 더합니다.

위 ...는 구조 설명용이며 실행 주소가 아닙니다. 아래 완성형에서 키·날짜·시각·격자를 바꿉니다.

  • YOUR_API_KEY: 교사가 안내한 개인 실습 환경에서 직접 적용합니다. AI 대화·공개 문서·저장소에는 넣지 않습니다.
  • YYYYMMDD: 현재 제공되는 범위에서 선택한 실제 날짜로 바꿉니다.
  • HH00: 자료가 준비된 정시 네 자리로 바꿉니다. 예를 들어 오전 9시는 0900입니다.
  • 60,127: 격자 자료에서 확인한 우리 지역 값으로 바꿉니다.

이 주소는 “내 인증키로, 이 날짜·시각의 격자 60·127에 해당하는 실황을, JSON 형식으로, 첫 페이지에서 최대 1000개 보내 주세요”라는 요청입니다. numOfRows=1000은 요청하는 페이지 크기이며, 실제로 몇 항목을 받았는지는 응답에서 확인합니다.

Encoding과 Decoding 중 무엇을 넣나요?

섹션 제목: “Encoding과 Decoding 중 무엇을 넣나요?”

두 표시는 같은 인증키를 URL에서 표현하는 방식입니다. 지금 사용하는 도구에 맞춰 한 번만 인코딩합니다.

지금 하는 작업사용할 값
위와 같은 완성 URL 문자열의 YOUR_API_KEY를 직접 교체공식 예시에 맞는 한 번 인코딩된 값을 넣습니다. 포털에서 Encoding 키를 제공하면 그 값을 확인합니다.
포털의 Swagger 입력칸에서 호출해당 공식 안내에 따라 일반 인증키(Decoding)를 넣습니다.
URLSearchParams처럼 자동으로 URL 변환하는 코드Decoding 값을 넣고 도구가 한 번 인코딩하도록 합니다.

이미 Encoding된 값을 자동 인코딩 도구에 다시 넣으면 %2B가 %252B처럼 바뀔 수 있습니다. 인증 오류가 나면 실행 도구의 입력 안내와 실제 요청주소를 비교합니다. 표와 샘플코드의 항목 표기가 다를 때도 해당 서비스의 공식 실행 화면·샘플 요청을 함께 확인하세요. 공공데이터포털의 실행 화면 안내 · URLSearchParams의 인코딩 설명

이번처럼 GET이고 인증·조건이 URL 쿼리에 들어가는 요청은 완성형을 줄바꿈 없는 한 줄로 브라우저 주소창에 붙여 넣어 실행할 수 있습니다. 헤더 인증이나 POST가 필요한 다른 API는 주소창만으로 같은 요청을 만들 수 없습니다. 기관 테스트 도구와 해당 명세의 방법을 사용하세요. 키가 들어간 주소는 공유·캡처·공개 북마크로 남기지 않습니다.

직접 응답 받기: 복사 → 값 교체 → 주소창 → Enter

섹션 제목: “직접 응답 받기: 복사 → 값 교체 → 주소창 → Enter”
  1. 위 완성형 요청주소를 메모장 등 개인 편집 화면에 복사합니다.
  2. YOUR_API_KEY, YYYYMMDD, HH00을 실제 값으로 바꾸고 격자를 확인합니다. ?, &, =와 항목 이름은 유지합니다.
  3. https://부터 마지막 값까지 주소 전체를 한 줄로 복사합니다.
  4. 브라우저 맨 위 주소창을 선택합니다. 컴퓨터에서는 Ctrl+L을 누른 뒤 붙여 넣고 Enter를 누릅니다.
  5. 화면에 나온 JSON 또는 XML 내용을 읽습니다. 파일로 내려받아졌다면 텍스트 편집기로 열어 내용을 확인합니다. 이 내용이 기관에서 보낸 응답입니다. 아래 단계에서 정상 데이터인지, 자료가 없는지, 오류 안내인지 구분합니다.
포털에 ‘OpenAPI 실행 준비’ 버튼이 보이는 경우

공식 Swagger 실행 화면이 제공되는 API는 화면에서 요청을 시험할 수 있습니다.

  1. 사용할 API 기능을 선택하고 OpenAPI 실행 준비를 누릅니다.
  2. required 또는 필수 표시가 있는 입력칸에 값을 넣습니다. 이 안내의 serviceKey 입력칸에는 일반 인증키(Decoding)를 사용합니다.
  3. OpenAPI 호출을 누릅니다.
  4. 생성된 Request URL과 호출 후 표시되는 Response body를 읽습니다. Example Value는 형식 예시이고, 호출 결과는 응답 영역에서 확인합니다.

우리 팀의 다른 API로 주소를 만들 때

공식 활용가이드의 요청주소·요청변수·출력결과 부분을 AI에 함께 보여 주세요. 아직 찾지 못한 항목은 그렇게 적어도 됩니다. 아래 요청문은 명세에서 필요한 내용을 찾아 설명하고, 실제 키를 넣을 자리만 남긴 요청주소를 만들도록 돕습니다.

명세서로 요청 URL 만들기 표시된 부분을 우리 팀의 내용으로 바꾸세요.

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

공공데이터포털에서 인증키를 받았고, 이제 실제 응답을 한 번 받아 보려고 해. 공식 명세를 읽어 요청주소를 만드는 과정을 처음 배우는 학생에게 설명해줘.
API 이름·제공 기관: {{정확한 이름}}
공식 활용 명세서: {{파일 첨부 또는 링크와 해당 요청·응답 설명 발췌}}

인증값: YOUR_API_KEY (실제 키를 요구하지 말고 자리표시자를 유지)

1. 먼저 내가 필요한 데이터를 주는 상세기능, 요청주소·방식·인증 위치를 공식 문서에서 찾아줘. 내가 아직 못 찾은 항목은 문서의 어느 제목·표에서 확인할지 안내해줘. 문서를 읽을 수 없으면 필요한 부분의 발췌나 화면을 요청하고 내용을 지어내지 마.
2. GET 주소창 요청이 가능한 방식인지 먼저 판단해줘. 필수 요청변수부터 영문 이름 / 내가 넣을 값 / 뜻을 표로 정리해줘. 지역 코드·날짜·시간 등 모르는 실제 값은 확인이 필요하다고 표시해줘. 선택 조건은 구분해줘.
3. 요청변수 표의 한 행이 이름=값으로 바뀌는 예를 보여줘. 기본 주소에 기능 경로, ? 뒤 첫 조건, & 뒤 다음 조건을 더하는 순서를 설명하고, 마지막에는 한 줄 요청 URL을 제공해줘. 완성된 요청주소에 기능 경로를 중복해서 붙이지 마.
4. 실제 인증키는 YOUR_API_KEY로 남겨 두고, 지금 쓰는 도구에 맞는 Encoding/Decoding 안내와 내가 직접 바꿀 자리만 알려줘. 다른 발급기관의 주소와 키를 섞지 마.
5. 완성한 주소를 어디에 붙이고 어떻게 실행할지 알려줘. POST나 헤더 인증이 필요하면 공식 실행 도구의 방법을 안내해줘. 호출 전 문서의 샘플과 호출 후 실제 응답을 구분해줘.
6. 응답에서 정상/자료없음/오류를 구분할 항목과 실제 값 하나를 찾는 순서를 알려줘. 설명용 샘플은 샘플이라고 표시하고, 실행하지 않은 요청을 성공했다고 하지 마. 나는 주소와 값을 확인한 뒤 직접 실행할게.

4. 받은 응답에서 기온 찾기

섹션 제목: “4. 받은 응답에서 기온 찾기”

글자와 중괄호가 길게 나와도, 그 안에 데이터가 들어 있습니다. JSON은 이름과 값을 짝지어 적는 형식입니다. { ... }는 관련 항목을 묶고, [ ... ]는 여러 항목을 목록으로 담습니다. 기상청 예제에서는 다음 순서로 읽습니다.

순서화면에서 찾아볼 것판단할 내용
① 처리 결과Ctrl+F로 resultCode 찾기이 API의 정상 코드 00인지 확인하고 resultMsg도 읽습니다.
② 실제 목록totalCount, items, item 찾기자료가 있는지, 몇 항목을 받았는지 확인합니다.
③ 필요한 값T1H를 찾아 같은 항목의 obsrValue 읽기T1H는 기온 항목이며 obsrValue가 값입니다.
④ 요청과 대조baseDate, baseTime, nx, ny내가 보낸 날짜·시각·격자가 맞는지 확인합니다.

HTTP 상태와 응답 본문의 기관 처리 결과도 구분합니다. HTTP 200이어도 본문에 오류가 담길 수 있습니다. 이 API는 response.header.resultCode와 resultMsg를 확인한 다음 실제 목록을 읽습니다. 03은 자료없음, 10은 요청변수 오류, 11은 필수값 누락, 22는 요청 제한, 30은 미등록 키를 뜻하는 이 서비스의 코드 예입니다. 다른 기관에서는 그 명세서의 정상·오류 기준을 확인합니다.

아래는 구조 설명용으로 만든 모의 JSON입니다. 실제 조회 결과도, 현재 날씨도 아닙니다. 실제 응답 구조와 값은 직접 요청한 결과와 비교합니다.

  1. response → header에서 처리 결과를 읽습니다.
  2. response → body → items → item에서 기록 목록을 찾습니다.
  3. category=T1H를 요청 URL에 임의로 추가하는 것이 아니라 받은 목록에서 고릅니다. 목록의 첫 항목이라고 기온은 아닙니다. category === "T1H"인 항목을 찾습니다.
  4. 그 항목의 obsrValue가 기온 값이며 단위는 ℃입니다. REH는 습도(%), RN1은 1시간 강수량(mm)처럼 항목별 단위가 다릅니다.
  5. baseDate, baseTime, nx, ny가 내가 요청한 조건과 맞는지 비교합니다. 요청의 base_date와 응답의 baseDate는 이름부터 다릅니다.

예시의 "category": "T1H", "obsrValue": "18.2"는 “기온 항목의 값이 18.2℃”라는 뜻입니다. base_time=0900처럼 내가 보낸 조건과 obsrValue처럼 기관이 돌려준 값을 구분해 설명해 보세요. 위 숫자는 읽는 연습을 위한 모의 값입니다.

실제 항목 수와 페이지도 확인합니다. pageNo=1은 첫 페이지, numOfRows는 요청한 페이지 크기, totalCount는 조건에 맞는 전체 건수입니다. 지금 받은 목록의 길이가 전체 건수보다 작으면 다음 페이지가 필요할 수 있습니다. 첫 페이지만 읽은 경우에는 그 범위에서 확인한 결과로 기록합니다.

☑️ 여기까지 되면 첫 응답 확인 완료

우리 팀이 직접 받은 응답을 보며 세 가지를 설명합니다: ① 보낸 조건 한 가지 ② 실제 받은 항목 이름과 값 한 가지 ③ 그 값의 의미·단위. 기록은 기존 활동지의 자료 확보·검증 부분에 짧게 이어 적습니다.

obsrValue가 -999 등 공식 결측 범위(−900 이하 또는 +900 이상)에 해당하면 실제 기온으로 표시하지 않고 관측값 없음으로 안내합니다.

초단기예보처럼 다른 기능의 fcstValue·예보 날짜를 이 실황 예제에 섞지 않습니다. 이 예제는 obsrValue와 관측 기준시각을 사용합니다.

키부터 재발급하거나 전체 코드를 다시 만들지 말고, 가장 먼저 확인할 항목 하나와 재시험 순서를 알려줘. 인코딩은 현재 도구와 공식 예시에 맞춰 확인하고 중복 인코딩하지 마. no-cors나 임의 공개 프록시를 우회책으로 쓰지 마. 실제 키를 요구하지 마.

6. 확인한 값을 앱에 표시하기

섹션 제목: “6. 확인한 값을 앱에 표시하기”

연결 순서는 화면 입력 → 요청변수 만들기 → 요청 실행 → HTTP·기관 결과 확인 → 필요한 항목 선택 → 화면 표시입니다. 조건이 바뀌면 새 요청이 필요할 수도 있고, 이미 받은 목록에서 고르면 될 수도 있습니다. 명세가 지원하는 요청조건과 앱 안의 필터를 구분합니다.

예를 들어 앞에서 확인한 실황 목록에서 기온을 고르는 코드는 다음과 같습니다. raw는 직접 받은 정상 JSON을 읽은 객체이며, 아래 코드 자체가 API에 요청을 보내지는 않습니다.

실제 앱에서는 이 코드 전에 HTTP·기관 오류와 빈 목록도 처리해야 합니다. 값 하나를 꺼내는 부분과 데이터 요청 부분을 나누어 확인하면 문제가 생긴 위치를 찾기 쉽습니다.

참고 · 같은 요청을 코드로 옮길 때

아래는 앞에서 주소창에 보낸 같은 GET 요청을 서버 코드로 옮기는 원리입니다. 브라우저 HTML에 붙여 넣는 코드가 아닙니다. process.env를 읽고 fetch를 실행하는 서버 환경이 이미 준비된 경우의 예시이며, 이 안내가 서버나 키 설정을 만들어 주지는 않습니다. 공개 앱의 서버 연결은 선생님과 확인합니다.

baseDate·baseTime·nx·ny에는 앞서 직접 확인한 조건을 전달합니다. 서버는 허용할 입력·호출량·오류·시간 제한도 별도로 처리해야 합니다. 요청 URL에는 키가 들어가므로 로그나 오류 화면에 전체 주소를 출력하지 않습니다. 인증 오류가 XML 등으로 왔다면 JSON 처리 오류만 보고 판단하지 말고, 키를 가린 원문 형식을 확인합니다. 정상 응답을 받으면 앞의 T1H 선택 과정으로 화면에 필요한 값을 연결합니다.

직접 실행해 보는 화면 예제

섹션 제목: “직접 실행해 보는 화면 예제”
  1. 정상 응답을 확인했다면 응답 본문 JSON만 weather.json으로 저장합니다. 요청주소나 인증키는 파일에 넣지 않습니다.
  2. 저장한 응답을 표시하는 HTML 내려받기로 파일을 저장한 뒤 브라우저에서 엽니다.
  3. 조회한 시각을 적고 weather.json을 선택합니다. 기온·관측 기준시각·격자를 원문과 대조합니다.
  4. 다른 격자나 준비된 다른 기준시각으로 요청해 저장한 JSON을 선택하고, 조건에 맞는 표시인지 확인합니다. 실제 값이 우연히 같을 수도 있으므로 값이 바뀌었는지만 보지 않습니다.

이 HTML은 실제 응답을 파일로 읽는 예제이며 API를 자동 호출하지 않습니다. ‘저장된 자료, 실시간 아님’과 출처를 표시합니다. 자료가 없거나 오류인 JSON을 넣었을 때 안내도 확인하세요. 자료의 이용 조건을 지키고, 임의의 예시값을 실제 기온처럼 표시하지 않습니다.

기존 앱에 요청 기능까지 연결할 때

섹션 제목: “기존 앱에 요청 기능까지 연결할 때”

현재 앱 파일·공식 명세·키를 가린 정상 응답을 함께 준비합니다. 앱이 이미 허용된 방식으로 데이터를 요청한다면 그 구조를 유지하며 응답을 화면에 연결합니다. 공개 앱에서 비밀키를 사용하려면 서버에서 키를 보관하고 호출하는 구성이 필요할 수 있습니다. GitHub Pages는 정적 파일을 제공하며 비밀키를 숨겨 주거나 서버 코드를 실행해 주지 않습니다. 서버 연결이 준비되지 않았다면 파일 기반 화면으로 확인한 범위를 남기고 선생님과 다음 설정을 확인합니다.

정상 응답을 기존 앱에 연결하기 표시된 부분을 우리 팀의 내용으로 바꾸세요.

수정 파일·바뀐 이유·직접 시험할 조건·미확인 부분을 정리해줘. 실제로 실행하지 않은 결과는 확인했다고 말하지 마.

8. 짧게 바꿔 보고 확인하기

섹션 제목: “8. 짧게 바꿔 보고 확인하기”

원래 활동지의 자료 확보·구현·검증 기록에 필요한 내용을 이어 적습니다. 추가 제출물은 없습니다.

  • 요청 URL에서 기본 주소·상세기능·인증·조회조건을 구분해 설명할 수 있나요?
  • 필수값과 형식, 선택값을 생략했을 때의 기본값을 명세에서 확인했나요?
  • 실제 응답의 목록 경로·필드·단위를 확인하고 원문 한 건과 화면 값을 비교했나요?
  • 조건 하나만 바꿔 다시 요청하고, 응답의 지역·기준시각과 필요한 항목을 비교했나요?
  • 실패했다면 실제 오류로 원인을 좁혔나요? 아직 확인하지 못한 내용도 구분했나요?
  • 앱에 실제 자료·출처·관측 기준시각·조회시각이 표시되나요? 저장 파일이면 실시간이 아님을 알렸나요?
  • 공개 코드·AI 대화·활동지·오류 캡처에 실제 키가 남지 않았나요?
