3. School Image Lab

MINI PROJECT 1 · TEAM LAB · 5~7차시
오늘의 질문학교 안에서 사진으로 상태를 구분하면 도움이 될 문제는 무엇일까?

SCHOOL IMAGE LAB은 학교 안에서 반복해서 확인해야 하거나 놓치기 쉬운 작은 문제를 찾아, 이미지 분류 AI가 실제로 도움이 될지 직접 실험하는 프로젝트입니다.

이 프로젝트에서는 문제 발견 → 데이터 설계·수집 → 모델 테스트·개선 → 구현·공유·판단의 과정을 스스로 설명합니다.

🎯 이번 프로젝트에서 가장 중요한 질문

“학교의 어떤 문제에 이미지 분류 AI가 도움이 되며, 어디까지 믿고 사용할 수 있을까?”를 끝까지 탐구합니다.

교과서와 활동지는 이렇게 사용합니다

섹션 제목: “교과서와 활동지는 이렇게 사용합니다”
  • 교과서에서는 각 단계의 핵심 개념과 판단 기준을 이해합니다.
  • 활동지에는 팀이 실제로 결정한 내용과 중요한 테스트 결과만 기록합니다.
  • TALK → DECIDE → TRY → TEST → RECORD의 리듬으로 진행합니다.
  • 활동지는 차시마다 새로 작성하지 않고 프로젝트가 끝날 때까지 이어서 완성합니다.

프로젝트 전체 흐름

섹션 제목: “프로젝트 전체 흐름”
1문제 발견·정의

사용자와 문제, 클래스 정하기

2데이터 설계·수집

다양한 사진과 테스트 자료 준비하기

3학습·테스트·개선

조건을 바꾸어 시험하고 판단하기

4구현·공유·판단

웹으로 보여주고 AI의 가치 판단하기

한 번에 끝나는 순서가 아닙니다. 테스트에서 문제를 발견하면 클래스 기준·데이터·문제 정의로 돌아가 다시 고칩니다.

일반적인 기계학습 문제 해결 과정과 연결하기

섹션 제목: “일반적인 기계학습 문제 해결 과정과 연결하기”

기계학습 프로젝트는 보통 문제 정의 → 데이터 수집·준비 → 학습 방법 선택과 모델 학습 → 평가·개선 → 활용·배포의 순환 과정으로 진행됩니다. 실제 프로젝트에서는 평가 결과에 따라 문제나 데이터 단계로 되돌아가므로 한 번만 지나가는 직선 과정은 아닙니다.

일반적인 과정이 프로젝트에서 수행하는 단계
문제 정의와 기계학습의 필요성 판단STEP 1 · 사용자·문제·대안·클래스 정의
데이터 수집과 준비STEP 2 · 학습용·테스트용 데이터 설계·수집, 라벨 확인
학습 방법과 모델 선택지도학습의 분류 문제로 정하고 이미지·음성·포즈 모델 선택
모델 학습과 평가STEP 3 · 1차 학습, 새로운 조건 테스트, 결과 기록
오류 분석과 개선STEP 3 · 원인 가설, 데이터·기준 수정, 재학습과 비교
활용과 배포STEP 4 · AI 서비스 웹페이지 구현, GitHub Pages 배포
실제 사용 검토모델의 한계, 사람의 확인, AI 사용 가치 최종 판단

📚 도구를 누르는 순서보다 판단의 근거가 중요합니다

티처블 머신의 화면 순서는 짧지만, 기계학습 문제 해결 과정에는 왜 이 문제를 선택했는지, 어떤 데이터가 필요한지, 무엇으로 성능과 한계를 확인했는지, 실제로 사용해도 되는지에 관한 사람의 판단이 계속 포함됩니다.

STEP 1 · 문제를 발견하고 정의하기

섹션 제목: “STEP 1 · 문제를 발견하고 정의하기”

학교생활의 문제부터 찾기

섹션 제목: “학교생활의 문제부터 찾기”

학교생활에서 사람이 반복해서 확인하는 일, 놓치기 쉬운 상태, 사진·소리·자세를 통해 확인하면 도움이 될 상황을 먼저 찾습니다.

예를 들어 “하교 전 교실 창문을 일일이 확인하는 불편을 줄이기 위해 열림과 닫힘을 구분한다”와 같이 사용자, 상황, 문제와 목적이 드러나도록 표현합니다.

주제 후보를 비교하고 선택하기

섹션 제목: “주제 후보를 비교하고 선택하기”

처음 떠오른 주제를 바로 확정하기 전에 팀원들이 각자 아이디어를 내고 후보를 두세 개 만듭니다. 다음 기준으로 비교하여 팀이 함께 탐구할 문제를 선택합니다.

살펴볼 기준확인할 질문
실제성우리 학교에서 직접 경험하거나 관찰한 문제인가?
구체성누구에게 언제 필요한 문제인지 설명할 수 있는가?
결과의 쓰임모델이 분류한 뒤 사용자가 취할 행동이 있는가?
분류 가능성두 상태의 차이를 눈·귀·자세로 분명하게 확인할 수 있는가?
실행 가능성학교에서 안전하게 데이터를 모으고 여러 번 테스트할 수 있는가?
팀의 흥미팀원들이 역할을 나누어 끝까지 재미있게 탐구하고 싶은가?

특히 “모델이 A라고 판단하면 사용자는 무엇을 하게 되는가?”를 질문해 봅니다. 분류 결과가 알림, 확인, 정리, 안내와 같은 실제 행동으로 이어지는지 살펴보면 프로젝트의 필요성을 더 분명하게 판단할 수 있습니다.

문제를 한 문장으로 구체화하기

섹션 제목: “문제를 한 문장으로 구체화하기”

다음 문장에 맞추어 팀의 문제를 설명해 봅니다.

[누구]가 [어떤 상황]에서 겪는 [어떤 문제]를 줄이기 위해 [무엇]과 [무엇]을 구분한다.

예를 들어 “마지막으로 교실을 나가는 사람이 하교 전에 창문을 다시 확인하는 수고를 줄이기 위해 창문의 열림과 닫힘을 구분한다”라고 표현할 수 있습니다.

굳이 AI가 필요할까?

섹션 제목: “굳이 AI가 필요할까?”

표지판이나 체크리스트 같은 단순한 방법도 함께 살펴보고, 분류 AI를 사용해볼 가치가 있는지 판단합니다.

먼저 질문판단 규칙을 사람이 명확하게 적을 수 있는가?
그렇다단순한 방법부터 검토

규칙·계산식·점검표로 해결할 수 있는지 살펴본다.

어렵다기계학습 실험 검토

대표성 있는 데이터를 모아 패턴을 학습할 수 있는지 살펴본다.

기계학습은 규칙을 직접 적기 어려운 문제에 유용하지만, 학습할 데이터를 안전하고 충분하게 마련할 수 있어야 합니다. 두 조건을 함께 확인한 뒤에 모델 제작 여부를 결정합니다.

확인할 질문판단 기준
분류 AI가 도움이 되는가?사람이 계속 직접 확인하기 어려운 상황인가?
더 단순한 방법은 없는가?표지판·위치 변경·점검표·간단한 규칙으로 해결하기 어려운가?
입력에서 차이가 확인되는가?사람이 사진·소리·자세만 보고도 두 상태의 차이를 설명할 수 있는가?
틀렸을 때 안전한가?큰 피해가 없고 사람이 다시 확인할 수 있는가?

⚠️ AI를 안전하게 사용할 수 있는 주제를 선택합니다

주제는 입력에서 직접 확인할 수 있고, 사람이 최종 확인할 수 있으며, 수업 시간에 안전하게 실험할 수 있는 문제로 정합니다. 사람의 감정·성격·능력·의도를 추측하거나 결과가 사람에게 불이익을 줄 수 있는 주제는 제외합니다.

문제에 맞는 입력 방식 선택하기

섹션 제목: “문제에 맞는 입력 방식 선택하기”

이 프로젝트는 이미지 분류를 기본으로 진행합니다. 문제를 판단하는 데 소리나 자세가 더 중요한 팀은 수업에서 사용할 수 있는지 확인한 뒤 티처블 머신의 음성 또는 포즈 분류를 선택할 수 있습니다.

입력 방식적합한 문제확인할 점
이미지 분류물건·공간·상태처럼 화면에 보이는 차이거리·각도·밝기·배경이 달라져도 구분되는가?
음성 분류특정 소리의 발생 여부나 소리 종류대화와 개인정보가 녹음되지 않는가? 배경 소음에서도 구분되는가?
포즈 분류몸의 위치와 형태로 확인할 수 있는 자세참여자의 동의를 받았는가? 사람마다 자세가 달라도 구분되는가?

음성·포즈 분류의 대상은 소리나 자세에서 직접 확인할 수 있는 상태로 정합니다. 특정 학생 식별과 태도·감정·능력 평가는 주제에서 제외합니다. 음성과 포즈 데이터에 사람이 포함될 때에는 참여자의 동의를 받고 안전하게 재현할 수 있는 상황에서 수집합니다.

📚 활동지는 선택한 입력 방식에 맞게 읽습니다

음성 분류를 선택한 팀은 활동지의 ‘사진·촬영·이미지 수’를 ‘소리·녹음·음성 샘플 수’로, 포즈 분류를 선택한 팀은 ‘사진·촬영·이미지 수’를 ‘자세·촬영·포즈 샘플 수’로 바꾸어 생각하며 작성합니다.

클래스는 ‘확인할 수 있는 기준’으로 정의하기

섹션 제목: “클래스는 ‘확인할 수 있는 기준’으로 정의하기”

팀원 모두가 같은 기준으로 데이터를 모을 수 있도록 클래스별로 사진·소리·자세에서 직접 확인할 수 있는 기준을 정합니다.

불분명한 기준더 구체적인 기준
정리됨 / 정리 안 됨물건이 지정 위치에 있음 / 지정 위치를 벗어난 물건이 있음
창문 열림 / 닫힘창틀 사이에 틈이 보임 / 창문이 끝까지 닫혀 틈이 보이지 않음
조용함 / 시끄러움정한 기준 소리가 들리지 않음 / 정한 기준 소리가 반복해서 들림
준비 자세 / 동작 자세팀이 정한 관절 위치와 몸의 방향이 보임 / 다음 동작의 관절 위치와 방향이 보임

사람마다 판단이 크게 다르거나 입력만으로 기준을 설명하기 어렵다면 클래스 기준이나 주제를 다시 검토합니다.

활동지에는 무엇을 남길까?

섹션 제목: “활동지에는 무엇을 남길까?”

다음의 결정을 기록합니다.

  1. 누구의 어떤 문제인지
  2. 현재 해결 방법과 한계
  3. AI를 사용해볼 가치가 있는지
  4. 선택한 입력 방식과 두 클래스의 차이
  5. 이 문제를 선택한 이유

STEP 2 · 모델이 배울 데이터를 설계하고 직접 수집하기

섹션 제목: “STEP 2 · 모델이 배울 데이터를 설계하고 직접 수집하기”

AI는 우리가 보여준 사진에서 배웁니다

섹션 제목: “AI는 우리가 보여준 사진에서 배웁니다”

이미지 분류 모델은 학습 사진에서 반복해서 나타나는 시각적 특징을 찾아 분류에 사용합니다.

팔찌는 항상 손목에서, 시계는 항상 책상 위에서 촬영했다면 모델은 손목과 책상 배경을 주요 특징으로 배울 수 있습니다. 학습 화면에서는 잘 맞아도 배경이 달라지면 쉽게 틀릴 수 있습니다.

📚 데이터에서 함께 살펴볼 네 가지

양은 충분한가, 균형은 두 클래스가 지나치게 차이 나지 않는가, 다양성은 여러 촬영 조건을 담았는가, 정확성은 사진과 라벨이 클래스 기준에 맞는가를 함께 확인합니다.

균형은 클래스별 수만 같게 만드는 일이 아닙니다. 각 클래스가 실제 사용 환경에서 만날 사람·장소·밝기·배경·기기 조건을 고르게 담고 있는지도 함께 확인합니다.

다양하게 찍는다는 것은 무엇일까?

섹션 제목: “다양하게 찍는다는 것은 무엇일까?”

실제 사용 환경을 고려해 거리·각도·밝기·배경·위치·촬영자를 바꾸어 촬영합니다.

바꿀 수 있는 조건생각해볼 질문
거리가까운 사진과 먼 사진이 모두 있는가?
각도정면·옆·위 등 여러 방향에서 촬영했는가?
밝기밝은 곳, 어두운 곳, 그림자가 있는 상황을 담았는가?
배경·장소한 장소나 배경에만 치우치지 않았는가?
물체 위치·상태위치, 방향, 크기, 가려짐이 달라지는가?
촬영자여러 팀원이 서로 다른 방식으로 촬영했는가?

모델이 실제로 사용될 때 달라질 가능성이 있는 조건을 팀이 골라 데이터에 반영합니다.

섹션 제목: “학습용과 테스트용을 왜 나눌까?”

바이브 코딩은 자연어로 원하는 프로그램을 설명하고 생성형 AI와 함께 코드를 만드는 방식입니다. 그러나 요청 한 번 → 코드 복사 → 제출을 뜻하지 않습니다. 우리 수업에서는 다음 과정을 반복합니다.

단계학생이 할 일
요청문제·사용자·입력·출력·필수 기능·성공 기준을 설명한다
실행파일을 저장하고 실제 브라우저와 기기에서 작동시킨다
관찰보이는 화면, 버튼 동작, 오류 메시지, 모델 결과를 기록한다
이해핵심 코드가 입력·모델 실행·출력을 어떻게 연결하는지 찾는다
개선발견한 문제 하나를 프롬프트에 구체적으로 반영해 다시 요청한다
비교처음 결과와 수정 결과를 같은 기준으로 시험한다

📚 코드보다 먼저 결과를 읽고, 필요한 코드는 끝까지 추적합니다

처음부터 모든 문법을 해석하려고 멈추지 않습니다. 먼저 프로그램을 실행해 무엇이 작동하고 무엇이 실패하는지 관찰합니다. 그다음 문제와 직접 관련된 HTML·CSS·JavaScript 부분을 찾아 AI에게 설명을 요청하고 직접 수정합니다. AI가 코드를 작성해도 무엇을 만들지 정하고, 실행 결과를 검증하고, 공개한 결과를 책임지는 사람은 학생입니다.

# 만들어야 할 결과

티처블 머신 모델이 실제로 작동하는 반응형 체험 웹페이지를 만들어주세요. 사용자가 다음 과정을 경험할 수 있어야 합니다.

1. 어떤 문제를 위해 만든 모델인지 이해한다.
2. 모델이 무엇을 구분하는지 확인한다.
3. 버튼을 눌러 카메라 또는 마이크 사용을 시작한다.
4. 실시간 입력으로 모델을 시험한다.
5. 클래스별 확률과 가장 높은 예측 결과를 확인한다.
6. 모델의 결과를 사람이 다시 확인해야 하는 이유를 이해한다.

# 반드시 구현할 기능

1. 제공한 모델 주소에서 필요한 모델 파일과 메타데이터를 올바르게 불러오세요.
2. 모델 종류에 맞는 TensorFlow.js와 티처블 머신 공식 라이브러리를 사용하세요.
3. 페이지가 열리자마자 카메라나 마이크를 실행하지 말고 사용자가 시작 버튼을 눌렀을 때 권한을 요청하세요.
4. 모델을 불러오는 동안 진행 상태를 한국어로 보여주세요.
5. 입력 장치를 시작하고 중지할 수 있게 하고, 버튼을 반복해서 눌러 장치가 중복 실행되지 않게 해주세요.
6. 모든 클래스의 확률을 0%~100%의 백분율과 가로 막대로 표시하세요.
7. 가장 높은 확률의 클래스를 크게 강조하되, 가장 높은 확률이 반드시 정답은 아니라는 안내를 넣으세요.
8. 예측값이 계속 바뀌어도 화면 요소의 위치가 심하게 움직이지 않게 해주세요.
9. 모델 로딩 실패, 잘못된 모델 주소, 입력 장치 권한 거부, 장치를 사용할 수 없는 경우에 사용자가 다음 행동을 알 수 있는 한국어 오류 안내를 보여주세요.
10. 시작 버튼을 여러 번 눌러도 모델·카메라·마이크와 예측 반복이 중복 실행되지 않게 하고, 중지 버튼을 누르면 입력 장치와 반복 작업을 정상적으로 종료하세요.
11. 클래스 이름은 코드에 예시로 다시 입력하지 말고 모델의 메타데이터에서 실제 값을 불러오세요.

# 디자인 조건

- 스마트폰 세로 화면에서 가장 편하게 사용할 수 있는 반응형 디자인으로 만들어주세요.

- 버튼은 손가락으로 누르기 충분한 크기로 만들고 글자와 배경의 명암 차이를 확보해주세요.
- 밝고 깔끔하게 구성하되 지나친 애니메이션, 장식, 이모지는 사용하지 마세요.
- 외부 이미지가 없어도 완성된 화면이 보이게 해주세요.

# 기술 조건

- HTML은 내용과 구조, CSS는 표현과 디자인, JavaScript는 모델 실행과 상호작용을 담당하게 작성하세요.
- CSS는 HTML의 style 영역에, JavaScript는 script 영역에 포함하여 하나의 index.html 파일로 완성하세요.
- 별도의 서버나 데이터베이스 없이 GitHub Pages에서 작동해야 합니다.
- 티처블 머신 실행에 필요한 공식 CDN 라이브러리 외에는 외부 파일에 의존하지 마세요.
- 이미지 분류에는 Teachable Machine Image, 음성 분류에는 Speech Commands 기반 Teachable Machine Audio, 포즈 분류에는 Teachable Machine Pose처럼 선택한 모델 종류에 맞는 라이브러리와 입력 처리 방식을 사용하세요.
- 카메라나 마이크가 GitHub Pages의 HTTPS 환경에서 작동하도록 작성하세요.
- 주요 코드에 초보자가 이해할 수 있는 짧은 한국어 주석을 넣으세요.
- 예시용 가짜 데이터나 사용하지 않는 코드를 넣지 마세요.

# 결과 형식과 검증

1. 완성된 index.html 전체 코드를 하나의 코드 블록으로 작성하세요.
2. 코드 일부를 생략하거나 '나머지는 동일합니다'라고 쓰지 마세요.
3. 코드 뒤에는 파일을 index.html로 저장하는 방법과 실행 후 확인할 항목만 짧게 설명하세요.
4. 답변하기 전에 다음을 스스로 점검하세요.
   - 실제 모델 주소가 코드에 들어갔는가?
   - 모델 종류에 맞는 라이브러리를 사용했는가?
   - 모델의 실제 클래스 이름을 불러오는가?
   - 시작과 중지가 중복 실행 없이 작동하는가?
   - 권한 거부와 모델 로딩 실패 안내가 있는가?
   - 스마트폰에서 사용할 수 있는가?
   - GitHub Pages에 올릴 수 있는 하나의 HTML 파일인가?

실행하고 검증하기

파일을 메모장으로 저장한다면 파일 형식은 모든 파일, 인코딩은 UTF-8, 파일 이름은 정확히 index.html로 지정합니다. 컴퓨터에서 파일을 직접 열면 브라우저 보안 정책으로 카메라·마이크가 제한될 수 있으므로 최종 기능은 HTTPS가 적용되는 GitHub Pages에서 확인합니다.

  • 우리 팀 모델이 정상적으로 불러와지는가?
  • 모델의 실제 클래스 이름이 모두 표시되는가?
  • 시작 버튼을 눌렀을 때 장치 권한 요청이 나타나는가?
  • 시작과 중지가 정상적으로 작동하며 중복 실행되지 않는가?
  • 새로운 테스트 데이터로 시험할 수 있는가?
  • 클래스별 확률과 가장 높은 예측 결과가 표시되는가?
  • 스마트폰에서도 글자·버튼·입력 화면이 잘 보이는가?
  • 모델의 한계와 사람이 확인해야 할 부분이 표시되는가?
  • 오류가 발생했을 때 사용자가 다음 행동을 알 수 있는가?

GitHub로 웹페이지 배포하기

GitHub는 코드와 파일을 저장하고 변경 내용을 관리하며 공유할 수 있는 온라인 서비스입니다. 이번 활동에서는 GitHub Pages를 이용해 index.html을 인터넷에서 접속할 수 있는 웹사이트로 배포합니다.

용어이번 활동에서의 의미
GitHub웹페이지 파일을 저장하고 관리하는 서비스
Repository우리 팀 파일을 모아 두는 온라인 프로젝트 공간
Commit파일을 추가하거나 수정한 내용을 변경 기록으로 저장하는 것
GitHub Pages저장소의 정적 웹 파일을 웹사이트로 공개하는 기능
Deploy다른 사람이 인터넷 주소로 접속할 수 있게 공개하는 것

⚠️ 공개하기 전에 개인정보를 확인합니다

학번·전화번호·집 주소·개인 이메일·비밀번호·API 키와 동의받지 않은 얼굴·음성을 공개하지 않습니다. 티처블 머신 학습 데이터와 화면에도 개인정보가 없는지 확인하고, 팀원 이름 공개는 수업의 제출 기준을 따릅니다.

  1. 1. 로그인하고 새 저장소 만들기

    GitHub에 로그인하고 오른쪽 위 + → New repository를 선택합니다. 이름은 영문·숫자·하이픈으로 정하고 Public, Add a README file을 선택한 뒤 Create repository를 누릅니다.

  2. 2. index.html 올리기

    저장소에서 Add file → Upload files를 선택해 index.html을 올리고 Commit changes를 누릅니다. 파일은 폴더 안이 아니라 저장소 맨 위에 둡니다.

  3. 3. Pages 켜기

    저장소의 Settings → Pages에서 Build and deployment → Source를 Deploy from a branch로 정합니다.

  4. 4. 공개 위치 정하기

    Branch는 main, 폴더는 /(root)를 선택하고 Save를 누릅니다.

  5. 5. 주소 확인하기

    배포가 끝나면 Pages 화면의 Visit site를 누릅니다. 주소는 보통 https://깃허브아이디.github.io/저장소이름/ 형식입니다.

  6. 6. 실제 기기에서 재검증하기

    스마트폰과 PC에서 접속해 카메라·마이크 권한을 허용하고 기능과 화면을 다시 확인합니다. 가능하면 다른 팀원의 기기에서도 시험합니다.

배포에는 몇 분이 걸릴 수 있습니다. 수정한 파일을 같은 주소에 반영하려면 기존 index.html을 교체하고 다시 Commit합니다.

문제확인할 내용
화면이 나오지 않음파일 이름이 소문자 index.html인지 확인
404 오류파일이 main 브랜치의 저장소 맨 위에 있는지 확인
배포 주소가 없음Pages가 Deploy from a branch, main / (root)인지 확인
수정 내용이 보이지 않음Commit과 Actions의 배포 상태를 확인하고 잠시 후 새로고침
모델 로딩 실패티처블 머신 공유 주소와 주소 끝의 / 확인
카메라·마이크 실행 실패HTTPS 주소인지, 브라우저 사이트 권한이 허용인지 확인
권한 요청이 다시 안 나옴주소창의 사이트 설정에서 카메라·마이크 권한 변경
스마트폰 화면이 깨짐화면 너비, 버튼 크기, 카메라 비율 확인

최종 기록과 제출

어느 경로를 선택하더라도 다음 과정을 완료합니다.
