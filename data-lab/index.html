6. 공공데이터로 첫 웹앱 만들기

식단표에서 좋아하는 메뉴가 나온 날을 찾으려면 날짜마다 내용을 읽어야 합니다. 조건을 선택하면 필요한 기록을 모아 보여 주는 앱을 만들어 봅시다. 실제 자료를 읽고 질문을 다듬은 뒤, 화면과 기능을 설계하고 생성형 AI와 함께 제작합니다.

📚 학습지 한 부로 시작하기

프로젝트 통합 학습지의 ‘시작 · 공통 실습 기록’을 사용합니다. 이후 팀 프로젝트도 같은 학습지에 이어 씁니다. 먼저 해 보고, 중요한 발견과 수정 이유를 짧게 남깁니다.

1. 만들 앱과 사용 장면 살펴보기

섹션 제목: “1. 만들 앱과 사용 장면 살펴보기”

만들 앱: 급식 메뉴 탐색기

학생이 학교·월·검색어를 선택하면, 해당 메뉴가 포함된 중식 날짜와 일수를 보여 줍니다. 첫 사용 흐름을 만든 뒤 비교와 화면 기능을 발전시켜 봅니다.

CSV 선택 → 조건 선택 → 검색 → 날짜·식단 확인 → 다른 조건으로 비교

기본 앱 열기에서 화면을 살펴봅니다. 처음에는 ‘가상 점검 데이터 불러오기’로 조작해 볼 수 있습니다. 이 6개 기록은 기능 확인용으로 만든 자료입니다. 실제 학교의 식단 분석에는 다음 단계에서 확보한 공공데이터를 사용합니다.

앱을 만져 보며 ‘어떤 정보가 먼저 보여야 할까?’, ‘검색한 결과를 어떻게 확인하면 좋을까?’를 생각해 봅시다.

2. 급식 데이터 준비하기

섹션 제목: “2. 급식 데이터 준비하기”

원자료에서 CSV 받기

섹션 제목: “원자료에서 CSV 받기”

나이스의 급식식단정보 Sheet 화면을 엽니다. 이 화면에는 조회 결과를 파일로 저장하는 기능이 있습니다.

  1. 학교와 기간 정하기

    조회 조건에서 사용할 학교와 급식일자 범위를 정합니다. 수업에서 정한 공통 학교·기간을 기준으로 조회하고, 결과의 학교명·날짜·식사명을 확인합니다.

  2. 자료의 범위 확인하기

    검색된 건수와 실제 날짜를 살펴봅니다. 화면 일부와 전체 조회 결과 중 어느 범위를 저장하는지 확인합니다.

  3. CSV 저장하기

    ‘파일변환저장’의 CSV를 선택해 저장합니다. 화면이나 다운로드 방식이 달라졌다면 같은 출처에서 준비한 공통 파일을 사용하고 조회 조건을 확인합니다.

  4. 원본과 사본 나누기

    원본 파일은 보관하고 사본을 만들어 분석합니다. 사본을 스프레드시트로 열어 아래 네 항목을 확인합니다.
분석용 열원자료에서 찾을 항목앱에서 하는 일
날짜급식일자 또는 MLSV_YMD날짜·월 선택과 일수 계산
학교명학교명 또는 SCHUL_NM학교 구분
식사명식사명 또는 MMEAL_SC_NM중식 기록 선택
메뉴요리명 또는 DDISH_NM검색과 식단 원문 표시

사본의 열 이름을 날짜, 학교명, 식사명, 메뉴로 맞춥니다. 날짜는 YYYY-MM-DD 또는 YYYYMMDD 형태로 준비하고, 메뉴 원문과 알레르기 표시는 함께 보존합니다. 이 기본 앱은 표에 적힌 NEIS 열 이름도 읽을 수 있습니다.

Google 스프레드시트에서는 파일 → 다운로드 → 쉼표로 구분된 값(.csv), Excel에서는 다른 이름으로 저장 → CSV UTF-8 형식으로 저장할 수 있습니다. 원본이 XLSX일 때도 이 과정을 거쳐 CSV를 만듭니다. 화면 명칭은 사용 중인 버전에 따라 조금 다를 수 있습니다.

작업 폴더 만들기

섹션 제목: “작업 폴더 만들기”

파일명과 저장 위치를 알아두면 AI에게 오류를 설명하거나 다른 기기에서 다시 실행할 때 도움이 됩니다. 우선은 파일 선택 방식으로 시작하고, API를 이용한 자동 갱신은 이후 확장 단계에서 살펴볼 수 있습니다.

3. 데이터를 읽고 질문 다듬기

섹션 제목: “3. 데이터를 읽고 질문 다듬기”

자료의 일부를 직접 읽고, 한 행이 무엇을 뜻하는지 확인합니다. 같은 학교·날짜에 조식과 중식이 함께 있거나 같은 날짜의 기록이 여러 줄인지도 살펴봅니다.

[학교·기간]의 중식에서 ‘카레’라는 문자열이 포함된 메뉴가 나온 날짜는 며칠일까?

예상한 결과를 적은 뒤 짧은 기간을 골라 직접 셉니다. 전체 중식일 수, 검색어가 포함된 날짜, 중복을 처리한 기준을 기록합니다. 이 결과를 나중에 앱의 계산과 대조합니다.

급식 자료를 읽고 계산 기준을 정하는 프롬프트 {{빨간 부분}}을 우리 팀의 내용으로 바꾸세요.
프롬프트 구조와 각 부분이 필요한 이유 보기

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

과업·필수 기능은 만들어야 할 결과와 빠뜨리면 안 되는 동작을 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

첨부한 급식 파일을 읽고 아래 질문을 살펴보려고 해.
질문: [학교·기간]의 중식에서 [검색어]가 포함된 메뉴가 나온 날짜는 며칠일까?

실제 열 이름, 한 행의 의미, 학교·기간·식사 종류를 먼저 확인해줘.
중복·빈 값·날짜 표기와 메뉴의 줄바꿈을 어떻게 처리하면 좋을지 설명해줘.
같은 학교·날짜의 중식 기록은 하루로 묶는 기준으로 계산해줘.
내가 직접 대조할 날짜와 원문을 보여줘.
확인한 사실과 추가로 알아볼 내용을 나누고, 자료를 읽기 어려우면 알려줘.
지금은 데이터와 계산 기준을 이해하는 단계야.

발견에서 기능으로 연결하기

섹션 제목: “발견에서 기능으로 연결하기”

같은 날짜가 여러 행에 있다면 행 수와 급식일 수가 달라질 수 있습니다. 월별 전체 급식일 수가 다르면 횟수와 비율을 함께 보아야 비교가 쉬울 수 있습니다. 우리 자료에서 실제로 확인한 점을 골라 기능으로 연결합니다.

확인한 사실 → 사용자에게 필요한 정보 → 앱의 처리·표시 방법

자료에 들어 있는 것은 편성된 식단 기록입니다. 학생의 선호도나 만족도까지 알아보려면 그에 맞는 추가 자료가 필요합니다. 찾은 자료가 처음 질문과 다르면 기간·대상·검색 기준을 바꾸어 봅시다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

검토한 설계대로 한국어 급식 메뉴 탐색기를 만들어줘.
HTML·CSS·JavaScript를 index.html 한 파일에 작성하고 외부 라이브러리 없이 실행되게 해줘.
자료는 사용자가 선택한 CSV를 브라우저에서만 읽어 처리해줘.

[데이터 계약]
필수 열: 날짜, 학교명, 식사명, 메뉴.
날짜: YYYY-MM-DD 또는 YYYYMMDD. CSV는 UTF-8이며 BOM과 따옴표 안의 쉼표·줄바꿈도 처리해줘.
실제 파일에 있는 자료로 결과를 만들고, 부족한 값은 확인이 필요한 기록으로 알려줘.

[첫 기능]
1. CSV 파일 선택 → 학교 선택 → 월 선택 → 메뉴 검색.
2. 중식만 사용하고 같은 학교·날짜의 기록은 메뉴를 모아 하루로 계산.
3. 검색어를 포함한 메뉴가 나온 일수와 해당 날짜·메뉴 원문 표시.
4. 검색어가 비면 선택 범위의 전체 중식일 표시. 결과가 비면 0일과 안내 표시.
5. 필수 열 누락·잘못된 날짜·잘못된 파일은 오류와 처리 기준 안내. 새 파일 오류 때 이전 결과는 초기화.
6. 출처·조회 조건·확인일을 적는 칸과 파일의 날짜 범위, 파일 기준 조회 안내.
7. 메뉴 원문과 알레르기 표시 보존. 파일 내용은 화면에 텍스트로 표시.

[화면]
제목, 설명, 조건 선택, 결과 카드, 날짜별 식단, 출처 순서로 배치해줘.
여백과 글자 크기를 충분히 두고 휴대기기에서는 한 열로 배치해줘.
버튼에 동작을 적고 처음 화면·빈 결과·오류 상태의 안내를 포함해줘.

[결과]
전체 코드를 제공하고 저장·실행 방법을 설명해줘.
데이터 읽기·조건 처리·계산·결과 표시 부분에 주석을 달아줘.
정상 검색과 예외 상황을 원자료와 대조할 테스트도 알려줘.

저장하고 실행하기

섹션 제목: “저장하고 실행하기”

  1. 전체 코드 저장

    일반 텍스트 편집기를 열어 받은 HTML 코드를 붙여 넣습니다. 코드 블록 앞뒤의 백틱을 제외한 HTML 내용만 저장합니다.

  2. 파일 이름과 인코딩 확인

    Windows 메모장에서는 ‘다른 이름으로 저장’을 선택하고 파일 이름 index.html, 파일 형식 모든 파일, 인코딩 UTF-8로 저장합니다. 실제 확장자가 .html인지 확인합니다.

  3. 브라우저로 열기

    index.html을 Chrome이나 Edge로 엽니다. 앱의 파일 선택에서 meals.csv를 불러옵니다. 이 단계는 PC의 웹브라우저에서 진행합니다.

  4. 같은 조건으로 검색

    직접 센 것과 같은 학교·월·검색어를 선택합니다. 출처와 확인일을 적고, 날짜·일수가 예상한 결과와 맞는지 확인합니다.

  5. 첫 실행본 보관

    정상 실행된 index.html을 versions 폴더에 별도 이름으로 복사합니다. 이후에는 무엇을 바꾸었는지 비교하며 수정합니다.

코드를 읽기 어려울 때는 AI에게 자료를 읽는 부분, 조건을 적용하는 부분, 날짜를 세는 부분, 결과를 표시하는 부분을 짚어 설명해 달라고 요청합니다. 각각이 화면의 어느 동작과 연결되는지 살펴봅니다.

기본 흐름을 다시 확인할 때는 기본 index.html과 가상 점검 CSV를 사용할 수 있습니다. 기본 코드를 출발점으로 선택했다면 우리 팀이 바꾼 부분을 기록합니다.

6. 원자료와 실행 결과 대조하기

섹션 제목: “6. 원자료와 실행 결과 대조하기”

정상 검색부터 빈 결과와 파일 오류까지 조건을 바꾸어 실행합니다.

실제 메뉴 검색직접 확인한 날짜·일수와 일치

가상학교의 6개 기록을 날짜별로 묶으면 전체 중식일은 5일입니다. ‘카레’를 검색하면 3일이 나옵니다. 2025년 9월은 전체 3일 중 2일, 10월은 전체 2일 중 1일입니다. 이 숫자는 기능 확인용이며 실제 학교의 식단 결과와 구분합니다.

예상과 다를 때 수정하기

섹션 제목: “예상과 다를 때 수정하기”

‘작동이 안 돼’보다 입력·기대 결과·실제 결과를 함께 보여 주면 무엇을 고칠지 분명해집니다. 수정 뒤에는 같은 입력으로 다시 확인합니다.

7. 화면을 다듬고 기능 확장하기

섹션 제목: “7. 화면을 다듬고 기능 확장하기”

첫 흐름이 작동하면 데이터에서 발견한 점이나 직접 사용하며 느낀 불편을 바탕으로 다음 기능을 정합니다.

비교 기능 발전시키기

섹션 제목: “비교 기능 발전시키기”

월별 비교 표, 검색된 중식일의 비율, 날짜별 보기 등 필요한 기능을 선택합니다. 비율을 표시할 때는 검색된 중식일 ÷ 선택한 범위의 전체 중식일 × 100이라는 기준과 분모를 함께 확인합니다.

기능을 추가하고 다시 확인하는 프롬프트 {{빨간 부분}}을 우리 팀의 내용으로 바꾸세요.
프롬프트 구조와 각 부분이 필요한 이유 보기

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

과업·필수 기능은 만들어야 할 결과와 빠뜨리면 안 되는 동작을 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

현재 정상 작동하는 앱을 다음과 같이 개선하려고 해.
바꿀 부분: [월별 비교 표 / 검색된 중식일의 비율 / 화면의 불편한 점]
발견과 수정 이유: [데이터 분석 또는 사용 경험]

기존 파일 읽기·중식 선택·중복 처리·출처 표시를 유지하며 수정해줘.
비율을 추가한다면 분모는 검색 전 선택한 학교·월의 전체 유효 중식일, 분자는 검색어가 포함된 중식일로 해줘.
분모가 0이면 자료 없음으로 표시해줘. 월별 비교에서는 각 월의 전체 일수도 함께 보여줘.
수정 계획, 바꾼 전체 파일, 변경한 부분, 다시 실행할 테스트를 설명해줘.

사용하기 편한 화면 만들기

섹션 제목: “사용하기 편한 화면 만들기”

화면의 글자 크기와 여백을 조정하고, 자주 사용하는 조건을 찾기 쉽게 배치합니다. 표의 날짜와 메뉴는 읽기 편하게 정렬하고, 휴대기기에서는 입력 영역이 한 열로 내려오도록 구성할 수 있습니다. 색상과 함께 문구로도 상태를 설명합니다.

AI에게 화면을 요청할 때는 ‘예쁘게’라는 말에 더해 누가 어떤 기기에서 쓰는지, 먼저 보여 줄 정보가 무엇인지, 현재 불편한 배치가 어디인지를 설명합니다. 기능과 계산 기준은 유지하면서 화면만 바꾸는 요청도 연습해 봅시다.

짝에게 검색 과제를 주고 앱을 사용하게 합니다. 혼자 할 수 있었던 일과 머뭇거린 장면을 살펴본 뒤 한 부분을 개선합니다. 개선 후에는 검색과 계산도 다시 실행합니다.

8. 공유하고 다음 프로젝트로 이어가기

섹션 제목: “8. 공유하고 다음 프로젝트로 이어가기”

웹 주소로 공유하기

섹션 제목: “웹 주소로 공유하기”

GitHub Pages에 게시하면 다른 기기에서도 주소로 앱을 열 수 있습니다. 기존 작업을 보존하며 새 저장소를 준비합니다.

  1. 새 저장소 만들기

    GitHub에서 New repository를 열어 meal-data-lab 같은 이름을 정하고 저장소를 만듭니다. 계정과 공개 범위는 수업 안내를 따릅니다.

  2. 파일 올리기

    Add file → Upload files로 index.html을 저장소 최상위에 올리고 Commit changes를 누릅니다. 파일 선택 방식에서는 사용자가 CSV를 별도로 준비합니다.

  3. Pages 설정

    Settings → Pages의 Source에서 Deploy from a branch를 선택합니다. Branch는 main, 폴더는 /(root)를 선택하고 Save를 누릅니다.

  4. 주소로 테스트

    Actions에서 게시 작업을 확인하고 Pages에 표시된 주소를 엽니다. iPad에서는 Safari로 주소에 접속하고 파일 앱에 저장한 CSV를 선택합니다.

공개할 파일은 데이터의 이용 조건을 확인해 정합니다. 개인정보와 인증 정보는 공개 파일과 분리합니다. 게시가 진행되는 동안에는 PC에서 파일 실행과 원자료 확인을 계속할 수 있습니다.
