## 1. 프로젝트 산출물 확인하기

완성된 프로젝트는 멋진 화면 하나만으로 판단하지 않습니다. 문제를 이해하고, 데이터를 확인하고, AI를 활용해 분석·설계·구현을 반복한 과정이 함께 보여야 합니다.

| 산출물 | 반드시 드러날 내용 |
| --- | --- |
| 문제 정의 | 누가 어떤 상황에서 무엇을 어려워하는지, 왜 볼 만한 문제인지 |
| 도메인 지식 기록 | 주제와 관련된 용어, 이해관계자, 공식 자료, 조심할 오해 |
| 데이터 수집 기록 | 출처, 기간, 지역, 단위, 행의 의미, 수집 또는 조회 방법 |
| 분석 결과 | 표·그래프·계산 기준, 원자료 대조, 사실과 해석의 구분 |
| 인사이트 | 분석 결과가 사용자 문제와 서비스 기능으로 이어지는 이유 |
| AI 서비스 설계 | AI가 필요한 부분, 사람이 확인할 부분, 입력·처리·출력 흐름 |
| 구현 결과 | 실제로 실행되는 최소 웹앱 또는 핵심 기능 프로토타입 |
| 발표와 성찰 | 팀의 판단, 검증, 한계, AI 활용 후 성장한 점 |

<Callout kind="checklist" title="최소 완성 기준">최소 기능 하나는 실제로 작동해야 합니다. 예를 들어 파일을 읽고 조건에 맞는 결과를 보여 주거나, 사용자의 선택에 따라 데이터 근거를 보여 주는 기능이 있어야 합니다. 더 복잡한 AI 모델이나 API 연결은 선택 확장입니다.</Callout>

## 2. 재미있는 문제에서 출발하기

재미는 가벼움이 아니라 계속 알아보고 싶게 만드는 힘입니다. 좋은 주제는 학생이 궁금해하고, 팀이 이야기하고 싶고, 데이터를 열어 보면 예상과 다른 점이 나올 가능성이 있습니다.

### 주제 선택의 세 기준

| 기준 | 질문 |
| --- | --- |
| 흥미 | 우리 팀이 진짜 궁금해하거나 사용해 보고 싶은가? |
| 현실성 | 실제 사용자나 상황을 설명할 수 있는가? |
| 데이터 가능성 | 확인할 수 있는 공식 자료, 기록, 관찰, 설문이 있는가? |

처음부터 거창한 사회 문제를 고를 필요는 없습니다. 다만 질문이 너무 얕게 끝나지 않도록 한 번 더 깊게 바꿉니다.

| 너무 가벼운 질문 | 더 깊은 탐구 질문 | 서비스로 이어지는 방향 |
| --- | --- | --- |
| 급식에 카레가 몇 번 나왔을까? | 메뉴 반복성, 영양 기준, 선호도 자료를 함께 보면 급식 선택에 어떤 정보가 필요할까? | 급식 메뉴 탐색·피드백 도구 |
| 우리 지역 청소년이 줄었을까? | 청소년 인구 변화와 문화·체육 시설 수는 지역별로 균형이 맞을까? | 청소년 시설 탐색·정책 제안 앱 |
| 날씨가 더워졌을까? | 폭염일 변화가 등하교·야외활동 안전과 어떻게 연결될까? | 학교생활 안전 알림 앱 |
| 영화는 어떤 장르가 인기일까? | 장르·개봉 시기·관람 등급에 따라 흥행 패턴은 어떻게 달라질까? | 영화 추천·상영 전략 탐색 앱 |
| 버스가 불편할까? | 특정 시간대와 정류장의 이용량·대기 경험은 어떻게 다를까? | 통학 교통 정보 도우미 |

## 3. 도메인 지식 만들기

어떤 분야를 잘 모르면 좋은 질문을 만들기 어렵습니다. 그래서 프로젝트 초반에는 주제를 바로 확정하지 않고, 그 분야의 기본 배경지식을 빠르게 만듭니다.

도메인 지식은 전문가가 되는 것이 아닙니다. **그 분야의 말, 사람, 자료, 기준, 오해**를 알아가며 질문을 더 정확하게 만드는 과정입니다.

<CopyPrompt title="도메인 지식 빠르게 만들기 프롬프트" content={domainPrompt} />

### 도메인 지식 탐색 카드

| 항목 | 작성할 내용 |
| --- | --- |
| 핵심 용어 | 이 주제를 이해하려면 알아야 할 말 |
| 관련 사람 | 영향을 받는 사람, 사용하는 사람, 관리하는 사람 |
| 공식 자료 | 기관, 공공데이터, 통계표, 보고서, 안내문 |
| 조심할 오해 | 데이터만 보고 쉽게 단정하면 안 되는 것 |
| 확인 가능한 질문 | 데이터로 비교하거나 계산할 수 있는 질문 |
| 확인하기 어려운 질문 | 인터뷰·관찰·추가 자료가 필요한 질문 |

도메인 지식을 만들면 문제 정의가 바뀔 수 있습니다. 그것은 실패가 아니라 문제를 더 정확히 이해했다는 뜻입니다.

## 4. 문제를 발견하고 구체화하기

프로젝트의 출발점은 사용자의 상황을 이해하는 일입니다. 어떤 앱을 만들지보다 **누가 무엇을 하려고 하며, 어느 순간에 어려움을 겪는지**부터 살펴봅시다.

### 실제 장면에서 시작하기

| 생각할 질문 | 살펴볼 내용 |
| --- | --- |
| 누구의 상황인가? | 사용할 사람과 이용하는 장소·시간 |
| 무엇을 하려는가? | 사용자가 이루려는 목적과 필요한 정보 |
| 지금은 어떻게 하는가? | 현재 방법과 순서, 이미 도움을 주는 도구 |

| 무엇이 재미있는가? | 팀이 끝까지 궁금해할 만한 지점 |

대화에서 들은 말과 직접 관찰한 내용은 확인한 사실로 적습니다. 팀이 추측한 이유는 더 살펴볼 가정으로 남깁니다.

## 6. AI와 데이터 분석하기

데이터 분석은 질문에 답하기 위해 자료를 정리하고 비교하는 과정입니다. 개수를 세거나 비율을 비교할 수도 있고, 시간 변화·지역 차이·집단 차이·관계·분포를 볼 수도 있습니다.

### 분석 기준 세우기

먼저 사용할 범위를 정하고, 날짜·단위·표기 차이와 중복을 살펴봅니다. 빈 값은 확인이 필요한 항목으로 표시하고, 분석에 포함하거나 제외한 기준을 남깁니다.

같은 조건에서 비교하고 있는지 확인한 뒤 질문에 맞는 표나 그래프를 만듭니다. 비율은 분자와 분모를, 평균은 포함한 기록을, 범주 비교는 분류 기준과 근거 문장을 설명할 수 있어야 합니다.

<CopyPrompt title="분석 기준과 결과를 확인하는 프롬프트" content={analysisPrompt} />

AI가 만든 결과에서 대표적인 값이나 문장을 골라 원자료와 직접 대조합니다. 어떤 기록과 계산을 사용했는지 설명하면서 결과를 읽어 봅시다.

수정한 뒤 같은 과제로 다시 사용해 봅니다. 설명이나 배치를 바꾼 경우에도 결과의 정확성을 함께 확인합니다. 직접 확인한 변화와 앞으로 더 검증할 효과를 나누어 정리합니다.

**학습지 6**에 테스트와 개선 결과를 기록합니다. 더 필요한 자료가 보이면 데이터 탐색으로, 사용자와 문제가 달라졌다면 문제 정의로 돌아가 보완합니다.

## 11. AI 활용과 협업 기록하기

이 프로젝트에서는 AI 활용 역량, 데이터 리터러시, 문제 해결 역량, 협업 역량이 함께 드러나야 합니다. 결과물만 보지 않고 팀이 어떻게 판단했는지를 남깁니다.

| 역량 | 기록으로 보여 줄 것 |
| --- | --- |
| AI 활용 역량 | AI에게 준 맥락, 결과 검증, 수정 요청, 채택하지 않은 제안 |
| 데이터 리터러시 | 출처·단위·행의 의미·전처리·그래프 선택·한계 설명 |
| 문제 해결 역량 | 큰 문제를 작은 질문으로 나누고, 결과에 따라 방향을 수정한 과정 |
| 공동체 역량 | 실제 사용자와 영향을 받는 사람을 고려한 설계 |
| 협업 역량 | 팀원별 기여, 서로의 의견을 반영해 바뀐 결정 |

팀원 역할은 고정 직업처럼 나누기보다 함께 판단해야 합니다. 다만 각자 더 책임지는 부분은 분명히 남깁니다.

## 12. 공유하고 발표하기
