## 1. MCP와 Open API는 어떻게 다를까?

KOSIS MCP와 Open API는 모두 외부 데이터를 활용하는 방법입니다. 수업에서 사람이 만나는 방식과 프로젝트에 연결되는 방식이 다릅니다.

| 구분 | KOSIS MCP | Open API |
| --- | --- | --- |
| 쉽게 말하면 | AI가 통계 도구를 불러와 자료를 찾는 방식 | 주소에 조건을 넣어 데이터를 직접 요청하는 방식 |
| 사용자가 주로 하는 일 | 자연어로 질문하고 통계표 후보 확인 | 요청 주소, 조건값, 응답 항목 확인 |
| 자주 만나는 자료 | 통계표, 수치, 설명 | JSON, XML, CSV |
| 확인할 것 | 통계표 이름, 기간, 지역, 단위 | API 명세서, 요청 변수, 응답 항목, 인증키 |
| 프로젝트 연결 | 문제의식을 뒷받침하는 통계 근거 찾기 | 사용자가 조건을 바꾸며 조회하는 앱 기능 만들기 |

Open API는 앱이나 웹사이트가 데이터를 가져올 때 자주 사용하는 방식입니다. 날짜를 바꾸면 다른 날의 급식이 나오고, 학교 코드를 바꾸면 다른 학교의 자료가 나옵니다.

<Callout kind="concept" title="요청과 응답">앱은 API 주소로 데이터를 요청합니다. 요청 주소에 <code>Type=json</code>을 넣으면 서버는 JSON 형식의 응답을 보냅니다. 요청은 주소와 조건값이고, 응답은 서버가 보내 주는 데이터입니다.</Callout>

JSON은 **반정형 데이터**입니다. 표처럼 행과 열만 있는 구조가 아니라, 이름표와 값이 계층적으로 묶여 있습니다. 구조가 정해져 있어 프로그램이 읽기 쉽고, 필요한 항목만 골라 앱 화면에 보여 줄 수 있습니다.

| 구분 | 오늘 예시 | 읽는 방법 |
| --- | --- | --- |
| 요청 | 급식 API 주소와 조건값 | 어느 학교, 어느 날짜의 급식을 달라고 보내는 말 |
| 응답 | JSON 데이터 | API가 찾아서 보내 준 급식 정보 |
| 앱에서 하는 일 | JSON에서 필요한 항목 추출 | 메뉴, 날짜, 칼로리 같은 값을 화면에 표시 |

## 3. API 명세서 읽기

Open API를 사용할 때는 먼저 공식 문서나 명세서를 확인합니다. 영화 데이터, 날씨 데이터, 버스 데이터도 제공 기관이 정한 요청 규칙이 있습니다. 문서 이름은 **오픈 API 명세서**, **개발 가이드**, **API Reference**, **활용 안내**처럼 다르게 쓰일 수 있습니다.

NEIS 급식식단정보 명세서에서 확인할 핵심 부분은 다음과 같습니다.

| 명세서 항목 | 확인할 내용 | 급식 API 예시 |
| --- | --- | --- |
| 요청주소 | 데이터를 요청할 기본 주소 | <code>https://open.neis.go.kr/hub/mealServiceDietInfo</code> |
| 기본인자 | API마다 공통으로 쓰는 값 | <code>KEY</code>, <code>Type</code>, <code>pIndex</code>, <code>pSize</code> |
| 요청인자 | 원하는 데이터를 고르는 조건 | 교육청 코드, 학교 코드, 급식일자 |
| 출력값 | 응답 데이터에 들어 있는 항목 | 학교명, 식사명, 요리명, 칼로리정보 |
| 메시지 설명 | 요청 성공, 오류, 데이터 없음 확인 | <code>INFO-000</code>, <code>INFO-200</code>, <code>ERROR-290</code> 등 |

<Callout kind="teacher" title="수업 운영 Tip">첫 실습은 교사가 준비한 예시 주소와 샘플 JSON으로 진행할 수 있습니다. 실제 프로젝트에서 실시간 API 조회가 필요한 팀은 공식 포털에서 인증키를 신청하고, 공개 저장소에 키를 올리지 않는 방법을 함께 정합니다.</Callout>

## 4. API 요청 주소 구성하기

API 요청 주소는 **기본 주소**와 **조건값**으로 구성됩니다. <code>?</code> 뒤에는 조건값이 이어지고, 여러 조건은 <code>&</code>로 연결됩니다. 각 조건은 <code>이름=값</code> 형태로 씁니다.

~~~text
https://open.neis.go.kr/hub/mealServiceDietInfo
?KEY=발급받은_인증키
&Type=json
&pIndex=1
&pSize=100
&ATPT_OFCDC_SC_CODE=시도교육청코드
&SD_SCHUL_CODE=학교코드
&MLSV_YMD=급식일자
~~~

| 부분 | 의미 | 예시 또는 형식 | 앱에서 달라지는 것 |
| --- | --- | --- | --- |
| <code>mealServiceDietInfo</code> | 급식식단정보 서비스 이름 | 고정 | 요청하는 데이터 종류 |
| <code>KEY</code> | API 인증키 | 발급받은 인증키 | 요청자를 확인하는 값 |
| <code>Type</code> | 응답 형식 | <code>json</code> | JSON 또는 XML 형식 |
| <code>pIndex</code> | 페이지 번호 | <code>1</code> | 몇 번째 묶음을 받을지 |
| <code>pSize</code> | 한 번에 받을 개수 | <code>100</code> | 응답에 담길 최대 기록 수 |
| <code>ATPT_OFCDC_SC_CODE</code> | 시도교육청 코드 | <code>B10</code>: 서울특별시교육청 | 어느 교육청 자료인지 |
| <code>SD_SCHUL_CODE</code> | 학교 코드 | 학교별 행정표준코드 | 어느 학교 자료인지 |
| <code>MLSV_YMD</code> | 급식일자 | <code>20210222</code> | 어느 날짜의 급식인지 |

API 인증키는 제공 기관이 발급하는 개인 또는 팀의 인증값입니다. 인증키가 있으면 명세서에 적힌 요청 주소의 <code>KEY=</code> 뒤에 그 값을 넣어 요청합니다. 수업 자료나 공개 코드에는 실제 인증키를 적지 않습니다.

학교 코드와 시도교육청 코드는 NEIS 포털의 학교기본정보 서비스, 제공 기관의 코드 안내, 교사가 준비한 예시 자료에서 확인할 수 있습니다. 날짜는 명세서의 형식에 맞춰 입력합니다. 급식 API에서는 보통 <code>YYYYMMDD</code> 형식을 사용합니다.

<Callout kind="caution" title="API 키 관리">API 키는 공개 게시물, GitHub 저장소, GitHub Pages용 HTML 파일에 직접 넣지 않습니다. 실습용 주소를 공유할 때는 샘플 응답 파일을 사용하거나, 키 부분을 <code>발급받은_인증키</code>처럼 가려서 표시합니다.</Callout>

## 5. 브라우저로 API 응답 확인하기

처음에는 코드를 쓰기보다 브라우저 주소창에서 요청 주소를 열어 봅니다. 아래 예시는 실제 키 대신 자리표시자를 넣은 구조입니다.

~~~text
https://open.neis.go.kr/hub/mealServiceDietInfo?KEY=발급받은_인증키&Type=json&pIndex=1&pSize=100&ATPT_OFCDC_SC_CODE=B10&SD_SCHUL_CODE=7010259&MLSV_YMD=20210222
~~~

<Steps>
<Step title="1. 명세서에서 필요한 값 찾기">요청주소, 기본인자, 요청인자, 출력값을 확인합니다.</Step>
<Step title="2. 요청 주소 완성하기">인증키, 교육청 코드, 학교 코드, 날짜를 넣어 주소를 완성합니다.</Step>
<Step title="3. 브라우저에서 실행하기">주소창에 요청 주소를 붙여 넣고 Enter를 누릅니다.</Step>
<Step title="4. 정상 처리 여부 확인하기"><code>RESULT</code>의 <code>CODE</code>와 <code>MESSAGE</code>를 확인합니다.</Step>
<Step title="5. 조건값 하나 바꿔 보기">날짜, 학교 코드, 페이지 크기 중 하나를 바꿔 응답이 어떻게 달라지는지 봅니다.</Step>
</Steps>

학생 실습에서는 처음부터 모든 값을 직접 찾기보다, 교사가 제공한 예시 주소에서 날짜나 식사 종류처럼 하나의 조건만 바꿔 확인할 수 있습니다. 이 경험을 통해 “앱의 입력값이 API 요청 조건으로 바뀐다”는 구조를 이해합니다.

| 바꿔 볼 값 | 예시 | 확인할 변화 |
| --- | --- | --- |
| 날짜 | <code>MLSV_YMD=20210222</code> | 해당 날짜의 메뉴가 나오는지 |
| 페이지 크기 | <code>pSize=5</code>, <code>pSize=100</code> | 한 번에 받는 기록 수가 달라지는지 |
| 학교 코드 | <code>SD_SCHUL_CODE=...</code> | 다른 학교의 급식 자료가 나오는지 |
| 식사 코드 | <code>MMEAL_SC_CODE=2</code> | 조식, 중식, 석식 중 특정 식사만 나오는지 |

## 6. JSON 응답에서 앱에 필요한 데이터 찾기

API 응답은 사람이 보기 좋은 표보다 프로그램이 읽기 좋은 구조로 제공됩니다. JSON에서는 중괄호, 대괄호, 이름표와 값을 차례로 읽습니다.

~~~json
{
  "mealServiceDietInfo": [
    {
      "head": [
        { "list_total_count": 1 },
        { "RESULT": { "CODE": "INFO-000", "MESSAGE": "정상 처리되었습니다." } }
      ]
    },
    {
      "row": [
        {
          "SCHUL_NM": "한영외국어고등학교",
          "MMEAL_SC_NM": "중식",
          "MLSV_YMD": "20210222",
          "DDISH_NM": "$차조밥<br/>$설렁탕5.6.13.16.<br/>$오리훈제...",
          "CAL_INFO": "1196.2 Kcal"
        }
      ]
    }
  ]
}
~~~

| JSON 표시 | 뜻 | 급식 응답에서 보는 방법 |
| --- | --- | --- |
| <code>{ }</code> | 하나의 묶음 | 결과 코드, 한 건의 급식 기록 |
| <code>[ ]</code> | 여러 개의 묶음 | 여러 날짜 또는 여러 식사 기록 |
| <code>"이름": "값"</code> | 항목 이름과 실제 값 | <code>"SCHUL_NM": "한영외국어고등학교"</code> |
| <code>head</code> | 응답 상태 정보 | 전체 개수, 정상 처리 여부 |
| <code>row</code> | 실제 데이터 목록 | 학교명, 날짜, 메뉴, 칼로리 |

급식 앱에서 먼저 확인할 항목은 다음과 같습니다.

| 응답 항목 | 학생용 이름 | 앱에서 쓰는 방식 |
| --- | --- | --- |
| <code>SCHUL_NM</code> | 학교명 | 요청한 학교가 맞는지 표시 |
| <code>MLSV_YMD</code> | 급식일자 | 날짜 선택 결과 표시 |
| <code>MMEAL_SC_NM</code> | 식사명 | 조식, 중식, 석식 구분 |
| <code>DDISH_NM</code> | 요리명 | 메뉴 카드나 표로 표시 |
| <code>CAL_INFO</code> | 칼로리정보 | 칼로리 안내 또는 비교 |
| <code>NTR_INFO</code> | 영양정보 | 영양 항목 표시 |
| <code>RESULT.CODE</code> | 처리 코드 | 정상, 오류, 데이터 없음 확인 |

<code>DDISH_NM</code> 안의 <code>&lt;br/&gt;</code>는 줄바꿈 표시입니다. 앱에서는 이 표시를 기준으로 메뉴를 줄마다 나누어 보여 줄 수 있습니다. 메뉴 이름 뒤의 숫자는 알레르기 번호를 뜻하며, 번호의 의미는 공식 문서에서 확인합니다.

## 7. 데이터 항목을 앱 기능으로 바꾸기

Open API 실습의 핵심은 데이터를 받는 데서 끝나지 않고, 받은 데이터를 사용자의 문제 해결 기능으로 바꾸는 것입니다. 분석은 문제의식과 기능 설계를 뒷받침하는 근거로 사용합니다.

~~~text
사용자 입력
→ API 요청 조건 만들기
→ JSON 응답 받기
→ 필요한 항목 추출하기
→ 화면에 표나 카드로 표시하기
→ 출처와 기준 표시하기
~~~

| 문제의식 또는 아이디어 | 필요한 API 항목 | 앱 기능 예시 | 확인할 점 |
| --- | --- | --- | --- |
| 오늘 급식이 궁금하다 | <code>MLSV_YMD</code>, <code>DDISH_NM</code> | 날짜를 고르면 메뉴 카드 표시 | 날짜와 학교가 맞는지 |
| 특정 메뉴가 언제 나오는지 알고 싶다 | 기간, <code>DDISH_NM</code> | 메뉴 검색 후 나온 날짜 표시 | 메뉴 이름 표기 차이 |
| 알레르기 번호를 쉽게 보고 싶다 | <code>DDISH_NM</code> | 메뉴 옆에 알레르기 번호 강조 | 번호 의미 공식 문서 확인 |
| 급식 칼로리를 비교하고 싶다 | <code>CAL_INFO</code> | 날짜별 칼로리 표 또는 그래프 | 단위와 누락값 확인 |
| 월별 메뉴 경향을 보고 싶다 | 기간, <code>DDISH_NM</code> | 자주 나온 메뉴 순위 표시 | 중복 메뉴 정리 기준 |

앱형 프로젝트에서는 데이터 분석 결과가 바로 최종 산출물이 되기보다, 앱의 기능과 화면을 설계하는 근거가 됩니다. 예를 들어 “화요일 급식이 아쉽다”는 생각은 기간별 메뉴와 칼로리를 확인하는 과정으로 이어지고, 그 결과는 메뉴 검색 앱이나 급식 알림 앱의 기능으로 연결됩니다.

## 8. 팀 프로젝트로 이어가기

팀 프로젝트의 최종 산출물은 사용자의 문제를 해결하는 웹앱입니다. 데이터는 문제를 확인하고, 기능을 설계하고, 결과를 검증하는 데 사용합니다.

~~~text
문제 발견
→ 데이터 출처 선택
→ 데이터 확인과 정리
→ 앱 기능 설계
→ 생성형 AI와 웹앱 제작
→ 결과 검증과 개선
→ 발표와 성찰
~~~

| 출발점 | 데이터 활용 방식 | 앱형 프로젝트 예시 |
| --- | --- | --- |
| 평소 불편함이 있다 | KOSIS나 공공데이터로 실제 현황 확인 | 청소년 여가, 진로, 사교육, 지역 격차 데이터를 바탕으로 정보 안내 앱 만들기 |
| KOSIS 탐색 중 문제를 발견했다 | 국가통계로 문제의 규모와 변화 확인 | 지역별 문화시설 차이를 보고 우리 지역 활동 추천 앱 만들기 |
| 조건별로 조회되는 생활 데이터가 필요하다 | Open API로 날짜, 지역, 학교 같은 조건별 데이터 요청 | 급식 조회, 메뉴 검색, 알레르기 확인, 날씨 기반 추천, 영화 정보 조회 앱 만들기 |
| 공식 데이터에 없는 학교 안 문제가 있다 | 직접 설문조사로 우리 학교 데이터를 수집 | 학습 습관, 급식 만족도, 진로 관심, 학교생활 불편을 반영한 맞춤 안내 앱 만들기 |

| 데이터 길 | 어울리는 역할 | 주의할 점 |
| --- | --- | --- |
| KOSIS MCP | 문제의식과 사회 현상을 통계로 확인 | 통계표 이름, 기간, 지역, 단위 확인 |
| 파일 다운로드 | 표 데이터를 정리하고 앱에 넣기 | 갱신 시점과 가공 기준 기록 |
| Open API | 사용자가 조건을 바꾸며 조회하는 기능 구현 | 명세서 확인, API 키 관리, 오류 처리 |
| 직접 설문 | 우리 학교나 우리 반의 실제 의견 반영 | 질문 문항, 익명성, 표본 수 설명 |

생성형 AI의 역할은 명세서 요약, JSON 구조 정리, 앱 요구사항 정리, 코드 초안 작성, 오류 점검입니다. 사람의 역할은 문제 정의, 데이터 선택, 출처 확인, 개인정보와 API 키 관리, 최종 판단입니다.
