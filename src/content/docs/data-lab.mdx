## 2. 데이터에서 인사이트까지

### 2-1. 출처와 조회 조건 확인

[NEIS 교육정보개방포털](https://open.neis.go.kr/)에서 **급식식단정보**를 검색합니다. 원하는 학교·기간의 자료인지, 필요한 항목이 있는지 확인합니다. 화면에 표시된 일부 결과나 API 샘플 응답을 전체 자료로 착각하지 않습니다.

직접 확보하거나 수업에서 배부한 파일을 사용하되 출처 페이지와 조회 조건을 직접 확인합니다. 인증키 발급과 API 자동 연결은 첫 실습에 요구하지 않습니다.

<Step title="원자료와 사본 분리">원본은 그대로 보존하고 분석용 사본을 만듭니다.</Step>
<Step title="필요한 열 확인">급식일자·학교명·식사명·요리명에 해당하는 열을 찾습니다. 없는 항목은 만들지 않습니다.</Step>
<Step title="CSV로 정리">필요한 경우 사본의 열 이름을 아래 기준에 맞춥니다. XLSX라면 CSV UTF-8로 내보내거나 다운로드합니다. 확장자만 바꾸지 않습니다.</Step>
<Step title="정리 전후 대조">일부 기록의 날짜·메뉴를 원본과 비교합니다. 필터·변환·삭제 기준과 변경한 기록 수를 남깁니다.</Step>
</Steps>

| 분석용 열 | NEIS에서 대응할 수 있는 항목 | 확인할 것 |
| --- | --- | --- |
| 날짜 | 급식일자 / MLSV_YMD | YYYYMMDD 또는 YYYY-MM-DD. 없는 날짜를 채우지 않는다. |
| 학교명 | 학교명 / SCHUL_NM | 원하는 학교가 맞는가? |
| 식사명 | 식사명 / MMEAL_SC_NM | 조식·중식·석식을 구분한다. |
| 메뉴 | 요리명 / DDISH_NM | 한 행에 여러 메뉴가 포함될 수 있다. 원문과 알레르기 표시는 보존한다. |

원하는 기간을 확보하지 못하면 분석 범위를 조정합니다. 실제 자료를 열지 못한 상태를 ‘수집 완료’로 표시하지 않습니다.

### 2-2. 질문을 정하고 직접 분석하기

<Step title="첫 파일 저장">생성된 전체 HTML 코드를 일반 텍스트 파일로 저장합니다. 코드 블록 표시인 세 개의 백틱은 넣지 않습니다. 이름은 index.html, 인코딩은 UTF-8로 정합니다.</Step>
<Step title="확장자 확인">index.html.txt로 저장되지 않았는지 확인합니다. PC에서는 웹브라우저로 파일을 엽니다.</Step>
<Step title="실제 CSV 선택">준비한 CSV를 불러오고 출처·조회 조건·확인일을 입력합니다. 출처 칸을 채웠다고 자동으로 검증되는 것은 아닙니다.</Step>
<Step title="같은 질문으로 실행">직접 센 것과 같은 학교·월·검색어를 선택합니다. 일수뿐 아니라 날짜와 메뉴 원문을 대조합니다.</Step>
<Step title="코드의 네 부분 찾기">데이터 읽기·조건 처리·계산·결과 표시 부분을 AI에게 설명하게 한 뒤, 각각의 역할을 내 말로 정리합니다.</Step>
</Steps>

실행이 막히면 기본 index.html로 같은 CSV를 사용해 봅니다. AI가 작성한 첫 버전은 보존하고, 기본 예시로 돌아온 이유를 적습니다. 모든 코드를 외우기보다 데이터가 어떤 처리를 거쳐 결과가 되는지 설명합니다.

### 3-3. GitHub Pages로 공유하기

기존 작업을 덮어쓰지 않도록 이번 실습용 저장소를 새로 만듭니다. 배포가 지연되어도 파일 실행과 데이터 검증은 이어 갑니다.

<Steps>
<Step title="새 저장소 만들기">GitHub의 New repository에서 meal-data-lab 같은 이름으로 저장소를 만듭니다. 학교가 허용한 계정과 공개 범위를 확인합니다.</Step>
<Step title="index.html 올리기">Add file → Upload files 또는 Create new file로 최상위에 index.html을 저장하고 Commit changes를 누릅니다. 파일 선택 방식이면 실제 CSV를 저장소에 올리지 않아도 됩니다.</Step>
<Step title="게시 위치 설정">Settings → Pages → Build and deployment에서 Source를 Deploy from a branch로 정합니다. Branch는 main, 폴더는 /(root)를 선택하고 Save를 누릅니다.</Step>
<Step title="배포 확인">Actions에서 배포 상태를 확인한 뒤 Pages에 표시된 주소를 엽니다. iPad에서는 배포된 주소를 Safari에서 열어 확인합니다.</Step>
</Steps>

공개되는 사이트와 저장소에는 개인정보·인증키·재배포할 수 없는 파일을 올리지 않습니다. 학교 네트워크에서 로그인이 막히면 임의로 우회하지 않고 수업에서 정한 실행 방식으로 테스트합니다.

## 4. 결과 검증하기

실제 CSV에서 직접 센 결과를 기준으로 삼습니다. 정상 사례와 예외 상황을 모두 확인합니다.

| 테스트 | 입력·상황 | 확인할 것 |
| --- | --- | --- |
| 정상 검색 | 실제 자료에 있는 메뉴 | 날짜·일수가 원자료와 일치하는가? |
| 빈 검색어 | 검색어를 지운다. | 선택 범위의 전체 중식일을 보여 주는가? |
| 없는 메뉴 | 자료에 없는 문자열 | 0일과 검색 결과 없음 안내가 나오는가? |
| 월 변경 | 다른 월을 선택한다. | 해당 월의 기록만 남는가? |
| 중복·잘못된 기록 | 중복 날짜, 누락, 잘못된 날짜 | 하루로 묶고 제외 이유를 알리는가? |
| 잘못된 파일 | 필수 열이 없는 CSV | 오류를 안내하고 이전 결과를 지우는가? |

<details>
<summary>가상 점검 데이터의 정답 · 먼저 직접 세고 확인하기</summary>

이 정답은 가상학교 6개 기록에만 해당하며 실제 학교의 급식 결과가 아닙니다.

| 조건 | 전체 중식일 | ‘카레’ 포함 중식일 |
| --- | --- | --- |
| 전체 월 | 5일 | 3일 |
| 2025-09 | 3일 | 2일 |
| 2025-10 | 2일 | 1일 |

2025-09-01의 두 기록은 하루로 묶습니다. 없는 문자열을 검색하면 0일이어야 합니다. 기능을 점검한 뒤 실제 공공데이터로 다시 확인합니다.

</details>

```text
[오류 수정 요청]
현재 코드와 재현 조건: [파일·학교·월·검색어]
기대 결과: [직접 확인한 날짜·일수]
실제 결과: [화면 결과 또는 오류 메시지]
근거: [원자료 기록·계산 기준]
가능한 원인부터 설명하고 해당 부분을 수정해줘.
다른 정상 기능은 유지하고 재검증할 테스트를 알려줘.
```

## 5. 개인·짝 미션 · 기능 하나 바꾸기

정상 실행본을 별도 파일로 보관합니다. 분석이나 사용 과정에서 발견한 점을 근거로 기능 하나를 수정합니다.

| 수정 후보 | 결정할 기준 |
| --- | --- |
| 검색된 중식일의 비율 | 분모는 검색 전 선택 범위의 전체 중식일. 분모가 0이면 자료 없음으로 표시한다. |
| 월별 비교 표·막대그래프 | 월별 전체 중식일 수를 함께 보여 준다. |
| 사용 중 발견한 불편 개선 | 불편한 장면과 입력·처리·출력의 변화를 설명한다. |

<CopyPrompt title="기능 하나 수정하는 프롬프트" content={improvePrompt} />

새 기능과 기존의 검색·중복·오류 테스트를 다시 실행합니다. 짝에게 검색 조건 하나를 정해 주고 앱으로 결과를 찾게 합니다. 짝이 설명 없이 할 수 있었던 일과 막혔던 장면을 기록합니다.

## 6. 실습 기록과 팀 프로젝트 준비

실행본·계산 근거·테스트 결과를 한곳에 모으고 다음 세 가지를 기록합니다.

| 역량 | 내가 남길 설명 |
| --- | --- |
| 문제 해결력 | 어떤 발견이나 불편 때문에 기능을 바꾸었고, 바꾼 뒤 무엇을 확인했는가? |
| 데이터 리터러시 | 어떤 출처·기간·항목을 사용했고, 어떤 기준으로 계산하여 원자료와 대조했는가? |
| AI 활용 역량 | AI에게 어떤 조건을 주었고, 제안 중 무엇을 채택·수정·거절했으며 이유는 무엇인가? |

<Callout kind="checklist" title="공통 실습 완료 기준">
- 실제 자료의 출처·기간과 한 행·열의 의미를 설명했다.
- 일부 기록을 직접 분석하고 발견을 기능으로 연결했다.
- 실제 CSV로 앱을 실행하고 원자료와 결과를 대조했다.
- 예외 상황을 테스트하고 기능 하나를 수정·재검증했다.
- AI의 제안을 그대로 사용하지 않고 내가 확인한 근거를 남겼다.
- 데이터 읽기·처리·계산·출력 과정을 내 말로 설명했다.
</Callout>

다음 3~12차시에는 설문에 적었던 문제나 만들고 싶은 것을 다시 살펴보고 팀 프로젝트를 진행합니다. 데이터 읽기·처리·출력 구조는 재사용할 수 있습니다. 팀은 문제에 맞는 자료를 선택하고 분석에서 얻은 인사이트를 근거로 필요한 기능을 연결·확장합니다.

공공데이터를 우선 검토하되, 출처와 사용 범위를 확인한 학습 자료·직접 만든 자료·연습 기록도 선택할 수 있습니다. 자료의 종류는 달라도 분석·인사이트·기능·검증의 연결은 유지합니다. 자세한 주제 후보와 선택 기준은 7번에서 확인합니다.
