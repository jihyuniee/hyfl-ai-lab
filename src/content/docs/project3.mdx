## Project Mission

<Callout kind="mission">
**데이터를 통해 우리 주변의 문제를 발견하고, 분석을 통해 인사이트를 도출한 뒤, 이를 해결하는 AI 서비스를 기획하라.**
</Callout>

**핵심 질문**: 데이터를 통해 문제를 더 정확하게 이해하고, 어떤 AI 서비스가 정말 필요한지 어떻게 결정할 수 있는가?

이 프로젝트에서 배우는 태도는 네 가지입니다. 서비스를 먼저 정하고 데이터를 끼워 맞추지 않는다는 것, 데이터에서 확인한 사실과 나의 해석을 구분한다는 것, 인사이트가 서비스 기능의 근거가 되어야 한다는 것, 그리고 AI는 분석을 도울 수 있지만 의미와 책임을 대신 결정하지 않는다는 것입니다.

> **서비스를 먼저 정하지 않습니다.**
> 데이터가 보여주는 문제를 살펴본 뒤, 그 문제에 필요한 서비스를 결정합니다.

<Callout kind="think" title="문제 해결 도구로서의 AI">
누구에게 중요한 문제인가요? 이 문제는 AI가 없어도 해결할 수 있나요? 필요한 데이터가 있나요? 이 해결책은 편리함 외에 어떤 가치를 만드나요? 일부 사람에게만 유리하거나 다른 사람을 배제하지는 않나요?
</Callout>

이번 프로젝트가 끝날 때, 여러분은 이렇게 설명할 수 있어야 합니다.

> "저는 이러한 문제에 관심을 가졌습니다. 이 문제가 실제로 어떻게 나타나는지 확인하기 위해 관련 데이터를 수집했습니다. 데이터를 분석한 결과 이러한 패턴을 발견했고, 이를 통해 이러한 인사이트를 도출했습니다. 그래서 그 인사이트를 바탕으로 이러한 AI 서비스를 기획했습니다."

### 잘못된 접근 vs 우리가 경험할 접근

<Callout kind="caution" title="잘못된 접근 — 서비스가 먼저">
"공부 계획 AI를 만들고 싶다." → AI에게 기능을 물어본다 → 그럴듯한 웹앱을 만든다 → 나중에 관련 데이터를 붙인다.
</Callout>

<Callout kind="lab" title="우리가 경험할 접근 — 데이터가 먼저">
"학생들이 공부 계획을 실천하지 못하는 이유는 무엇일까?" → 관련 데이터를 수집한다 → 실천을 방해하는 패턴을 분석한다 → 실제로 필요한 도움을 찾는다 → 분석 결과에 근거하여 AI 서비스 기능을 결정한다.
</Callout>

## Finding Evidence — 문제를 탐구 질문으로, 데이터를 증거로

### 관심 문제를 탐구 질문으로 바꾸기

바로 서비스를 정하지 마세요. 먼저 아래 질문으로 생각을 넓힙니다.

- 누가 이 문제를 경험하는가?
- 어떤 상황에서 문제가 나타나는가?
- 문제라고 판단한 근거가 있는가?
- 얼마나 자주 발생하는가? 누구에게 더 크게 나타나는가?
- 원인이 무엇이라고 예상하는가? 그 예상은 데이터로 확인할 수 있는가?
- 데이터를 통해 알고 싶은 것은 무엇인가?

<Callout kind="concept" title="넓은 관심 → 확인 가능한 질문 (예시)">
**학습** — 관심: "AI로 공부 계획을 세워주고 싶다." → 탐구 질문: "학생들은 공부 계획의 어느 단계에서 가장 많이 실패하는가? 계획의 구체성과 실제 실천율 사이에는 어떤 관계가 있는가?"

**외국어** — 관심: "외국어 학습 AI를 만들고 싶다." → 탐구 질문: "학습자가 가장 어려워하는 것은 단어의 의미, 발음, 문법, 자연스러운 표현 중 무엇인가?"

**진로** — 관심: "개인 맞춤형 진로 추천 AI를 만들고 싶다." → 탐구 질문: "학생들은 진로를 결정할 때 어떤 정보가 가장 부족하다고 느끼는가? 추천 결과를 신뢰하는 데 가장 중요한 조건은 무엇인가?"

**허위정보** — 관심: "AI 허위정보 판별 서비스를 만들고 싶다." → 탐구 질문: "학생들은 어떤 특징 때문에 AI가 만든 허위정보를 사실이라고 판단하는가? 출처, 이미지, 문체, 반복 노출 중 무엇이 신뢰도에 가장 큰 영향을 주는가?"
</Callout>

좋은 탐구 질문은 **데이터로 확인할 수 있어야 합니다**. 핵심 질문 1개, 보조 질문 2~3개로 좁히세요.

### 데이터를 문제의 증거로 바라보기

개인 경험이나 예상만으로 문제를 확정하지 않습니다. 데이터로 확인하세요.

**사용할 수 있는 데이터**: 공공데이터·국가통계·학교/학급 설문·인터뷰·직접 관찰 기록·학습 또는 생활 로그·공개 보고서·신뢰할 수 있는 연구 자료·뉴스와 정책 자료·간단한 비교 실험 데이터

공공데이터만 써야 하는 것은 아닙니다. 탐구 질문에 따라 설문, 관찰, 인터뷰, 실험, 공개 데이터 중 적절한 방법을 고르세요. 데이터를 찾기 전에 먼저 결정하세요.

- 무엇을 확인하려는가? 어떤 데이터가 있어야 답할 수 있는가?
- 어떤 변수가, 누구의 데이터가 필요한가?
- 어떤 기간을 살펴봐야 하는가? 비교할 집단이나 조건이 있는가?

<Callout kind="checklist" title="체크포인트 — 다음 단계로 넘어가기 전에">
- 내 탐구 질문은 데이터로 답할 수 있는 질문인가?
- 핵심 질문 1개와 보조 질문 2~3개로 정리했는가?
- 어떤 데이터가 필요한지 구체적으로 말할 수 있는가?
</Callout>

## Reading Data — 데이터를 읽는 눈

### 데이터의 구조와 품질 확인

개념을 먼저 외우지 않습니다. 자신의 데이터를 직접 열어보며 아래 개념을 하나씩 찾아보세요.

<Callout kind="concept" title="데이터를 열면 보이는 것들">
행 · 열 · 속성 · 변수 · 값 · 범주형 데이터 · 수치형 데이터 · 결측치 · 이상치 · 중복 · 표본 · 단위 · 수집 기간 · 데이터 출처
</Callout>

- 한 행은 무엇을 의미하는가? 각 열은 무엇을 측정하는가? 값의 단위는 무엇인가?
- 비어 있는 값은 왜 생겼는가? 너무 크거나 작은 값은 실제 현상인가, 입력 오류인가?
- 같은 데이터가 중복되어 있지는 않은가?
- 어떤 사람이 포함되어 있고 누가 빠져 있는가?
- 이 데이터는 언제, 누구에 의해, 어떤 목적으로 수집되었는가?

### 데이터 분석과 시각화

모든 분석 방법을 배울 필요는 없습니다. 탐구 질문에 필요한 것만 고르세요.

**분석**: 빈도·비율·평균·중앙값·최댓값과 최솟값·집단 간 비교·시간에 따른 변화·순위·두 변수의 관계·간단한 상관관계·범주별 차이·응답 내용의 주제 분류

**시각화**: 막대그래프·꺾은선그래프·산점도·히스토그램·표·간단한 지도 시각화·키워드 빈도(원그래프는 필요한 경우에만 제한적으로)

그래프를 많이 만드는 것이 목표가 아닙니다. **핵심 질문에 답하는 시각화 2~3개**만 고르세요.

<Callout kind="caution" title="같은 데이터도 다르게 보일 수 있다">
축의 시작점 · 그래프 범위 · 비교 집단 · 집계 방식 · 기간 · 평균과 중앙값 · 비율과 실제 인원 · 제외한 데이터 — 이 중 하나만 바뀌어도 같은 데이터가 다른 인상을 줄 수 있습니다.
</Callout>

## From Pattern to Insight — 사실에서 인사이트로

### 패턴과 원인 구분하기

이 프로젝트에서 가장 중요한 개념입니다. 두 현상이 함께 나타나더라도 곧바로 원인이라고 결론 내리지 않습니다.

<Callout kind="caution" title="예시 — '공부 시간이 짧은 학생들의 성적이 낮게 나타났다'">
데이터로 말할 수 있는 것: **두 변수 사이에 관련성이 나타났다.**

바로 말할 수 없는 것: 공부 시간이 짧기 때문에 성적이 낮아졌다.

함께 고려할 다른 변수: 학습 방법, 수업 이해도, 과목 난이도, 수면 시간, 사교육, 시험 불안, 기존 학업 수준
</Callout>

"원인이다"라고 단정하기 전에 이런 표현을 쓰세요: *관련성이 나타났다 · 이러한 경향이 관찰되었다 · 원인일 가능성이 있다 · 추가 확인이 필요하다 · 이 데이터만으로 인과관계를 확정할 수 없다.*

### 관찰에서 인사이트로 이동하기

<Callout kind="concept" title="관찰 → 해석 → 인사이트">
**관찰** (데이터에서 직접 확인한 사실): "응답자 50명 중 32명이 계획을 끝까지 실천하지 못했다고 답했다."

**비교와 해석** (집단·조건의 차이): "계획을 실천하지 못한 학생 중 가장 많은 학생이 과제 소요 시간을 예상하기 어렵다고 답했다."

**인사이트** (문제 해결에 주는 의미): "학생들에게 필요한 것은 계획을 대신 작성하는 기능보다, 과제별 소요 시간을 현실적으로 예상하고 상황에 따라 계획을 조정해주는 기능일 수 있다."
</Callout>

인사이트는 **데이터에서 발견한 사실 + 그 사실이 의미하는 것 + 해결에 주는 시사점**을 모두 포함해야 합니다.

<Callout kind="caution" title="좋지 않은 인사이트 vs 좋은 인사이트">
❌ "학생들은 계획을 잘 세워야 한다." — 사실도 시사점도 없는 당위적 주장입니다.

✅ "학생들은 계획의 필요성을 모르기보다 과제별 소요 시간을 부정확하게 예상하여 계획을 지키지 못하는 경우가 많았다. 따라서 새로운 서비스는 계획표 작성보다 시간 예측과 자동 조정 기능을 우선해야 한다."
</Callout>

<Callout kind="checklist" title="체크포인트 — 다음 단계로 넘어가기 전에">
- 사실(관찰)과 나의 해석을 구분해서 말할 수 있는가?
- "원인이다"라고 단정한 부분은 없는가?
- 내 인사이트에 '사실 + 의미 + 시사점'이 모두 들어있는가?
</Callout>

## From Insight to AI Solution — 인사이트를 서비스로

### 인사이트를 AI 서비스 기능으로 연결하기

멋있어 보이는 기능을 무작정 추가하지 않습니다. 서비스의 모든 핵심 기능은 데이터와 인사이트에 근거해야 합니다.

<FlowDiagram items={[{ ko: '발견한 사실' }, { ko: '인사이트' }, { ko: '해결 원칙' }, { ko: '서비스 기능' }]} />

| 데이터에서 발견한 사실 | 인사이트 | AI 서비스 기능 |
| --- | --- | --- |
| 과제 시간을 자주 잘못 예상함 | 현실적인 시간 예측이 필요함 | 과제별 예상 소요 시간 추천 |
| 짧은 자투리 시간을 활용하지 못함 | 작은 학습 단위 제안이 필요함 | 남은 시간에 맞는 학습 추천 |
| 외국어 표현을 문법적으로는 알지만 실제 사용을 어려워함 | 상황과 맥락이 필요함 | 상황별 자연스러운 표현 비교 |
| 진로 추천의 이유를 알 수 없어 믿기 어려움 | 추천 근거를 보여줘야 함 | 추천 이유와 관련 데이터 표시 |
| 허위정보를 출처 확인 없이 믿음 | 검증 과정을 눈에 보이게 해야 함 | 출처·근거 확인 단계 제공 |
| 폭염 문제의 체감이 지역에 따라 다름 | 지역별 위험 정보를 제공해야 함 | 지역별 위험도와 행동 안내 |

서비스 기획에는 다음이 포함되어야 합니다: 해결하려는 문제 · 대상 사용자 · 사용한 데이터 · 핵심 분석 결과 · 도출한 인사이트 · AI가 필요한 이유 · 서비스 입력 · AI가 처리하는 내용 · 사용자에게 제공할 출력 · 핵심 기능 · 인간이 최종 판단해야 하는 부분 · 예상되는 오류 · 데이터 편향 가능성 · 개인정보 문제 · 서비스의 한계

### AI를 협업자로 사용하기

이 프로젝트는 AI 사용을 제한하지 않습니다. 적극적으로 활용하되, **사고의 출발점과 최종 판단은 넘기지 않습니다.** [6차시](/hyfl-ai-lab/part3/ch6/)에서 배운 AI 협업 기본 구조는 이 프로젝트에서도 그대로 이어집니다.

<CollabProcess />

| 학생이 직접 해야 하는 일 | AI의 도움을 받을 수 있는 일 |
| --- | --- |
| 관심 문제 선택 | 관련 주제와 키워드 확장 |
| 탐구 질문 결정 | 질문이 모호한 부분 피드백 |
| 필요한 데이터 판단 | 데이터 출처 후보 탐색 지원 |
| 설문·인터뷰의 목적 결정 | 문항 표현과 순서 점검 |
| 데이터 출처의 신뢰성 판단 | 데이터 정리 방법 제안 |
| 중요한 변수 선택 | 분석 방법 후보 추천 |
| 분석 결과 확인 | 반복 계산과 그래프 제작 지원 |
| 인사이트 최종 결정 | 여러 해석 가능성 제시 |
| 서비스 핵심 기능 선택 | 기능 아이디어 확장 |
| 윤리적 판단과 최종 책임 | 위험 요소 후보 제안 |

<Callout kind="teacher">
핵심 메시지: AI는 빠르게 정리하고 여러 가능성을 제안할 수 있지만, 무엇이 중요한 문제인지 결정하고 결과가 타당한지 판단하는 책임은 사람에게 있습니다.
</Callout>

**AI가 데이터 수집을 도울 때** — 검색 키워드 만들기, 관련 기관 추천, 공공데이터 포털 탐색 방법 설명, 필요한 변수 목록 제안, 설문·인터뷰 문항 다듬기를 도울 수 있습니다. 다만 AI가 알려준 출처는 반드시 실제로 존재하는지 확인하세요: *이 기관과 자료가 실제로 존재하는가? 원문 링크에 직접 접속했는가? 수집 시점은 언제인가? AI가 자료명이나 수치를 지어낸 것은 아닌가?*

**AI가 데이터 분석을 도울 때** — 열 이름·구조 설명, 결측치 확인, 정리·그래프 코드 작성, 기초 통계 계산, 해석과 반대 해석 제시를 도울 수 있습니다.

<Callout kind="caution" title="AI 분석, 그대로 받아들이지 않기">
- AI가 열 이름과 단위를 정확히 이해했는가?
- 실제 데이터에 없는 내용을 만들어내지 않았는가?
- 행의 개수와 계산 결과가 맞는가? 직접 계산하거나 다른 도구로 재현할 수 있는가?
- 상관관계를 인과관계처럼 표현하지 않았는가?
- 원하는 결론에 맞는 데이터만 선택하지 않았는가? 반대 결과나 예외를 무시하지 않았는가?
- 데이터가 대표하지 못하는 집단까지 일반화하지 않았는가?
</Callout>

AI에게 이렇게 검증을 요청해보세요: *"이 분석에서 내가 놓친 다른 해석을 제시해줘." · "이 결과를 원인이라고 단정할 수 없는 이유를 설명해줘." · "이 데이터가 대표하지 못하는 집단을 찾아줘." · "내 결론에 반대되는 관점에서 검토해줘." · "계산 과정과 사용한 열을 단계별로 보여줘."*

### 최종 발표

모든 팀은 이 순서로 발표합니다: 문제 → 탐구 질문 → 수집한 데이터 → 분석 방법 → 데이터에서 발견한 사실 → 도출한 인사이트 → 서비스 기획 → AI와 인간의 역할 → 검증 과정 → 한계와 다음 탐구

<Callout kind="lab" title="발표 문장 템플릿">
"저희는 \_\_\_\_ 문제에 관심을 가졌습니다."
"이 문제가 실제로 어떻게 나타나는지 확인하기 위해 \_\_\_\_ 데이터를 수집했습니다."
"데이터를 분석한 결과 \_\_\_\_라는 패턴을 발견했습니다."
"이 결과는 \_\_\_\_을 의미할 가능성이 있다고 해석했습니다."
"이를 통해 \_\_\_\_라는 인사이트를 도출했습니다."
"그래서 단순히 \_\_\_\_하는 서비스가 아니라, \_\_\_\_ 기능을 가진 AI 서비스를 기획했습니다."
"이 과정에서 AI는 \_\_\_\_을 도왔고, 저희는 \_\_\_\_을 직접 판단했습니다."
"다만 이 데이터에는 \_\_\_\_라는 한계가 있어, 실제 서비스로 사용하기 전에 \_\_\_\_을 추가로 확인해야 합니다."
</Callout>

## 평가와 산출물

<Callout kind="rubric" title="평가에서 중요하게 보는 것">
웹앱의 화려함이나 기능의 개수가 아니라 다음을 봅니다.

- 문제를 구체적으로 정의했는가? 탐구 질문이 데이터로 확인 가능한가?
- 질문에 적합한 데이터를 수집했는가? 데이터의 출처와 한계를 확인했는가?
- 분석 방법이 질문에 적합한가?
- 데이터에서 확인한 사실과 자신의 해석을 구분했는가? 상관관계를 원인으로 단정하지 않았는가?
- 인사이트가 실제 분석 결과에서 나왔는가? 서비스 기능이 인사이트와 연결되는가?
- AI의 분석 결과를 검증했는가? AI가 한 일과 학생이 판단한 일을 구분했는가?
- 서비스의 오류·편향·윤리 문제를 고려했는가?
- 자신의 결론으로 말할 수 없는 부분을 정직하게 설명했는가?
</Callout>

<Callout kind="checklist" title="최종 산출물">
문제 정의 · 탐구 질문 · 데이터 출처와 수집 방법 · 핵심 데이터 설명 · 핵심 시각화 2~3개 · 데이터에서 발견한 사실 · 인사이트 2~3개 · 인사이트와 서비스 기능의 연결 · AI 서비스 기획 · AI와 인간의 역할 구분 · AI 협업과 검증 과정 · 한계 · 최종 발표
</Callout>

실제 웹앱 구현은 필수가 아니라 **선택·확장 활동**입니다. 완성된 서비스를 억지로 만드는 것보다, 데이터와 문제의 연결·인사이트의 타당성·서비스 기능의 근거를 충분히 설명하는 것이 우선입니다.

## 마무리

> 이 프로젝트의 목표는 멋있는 AI 서비스를 먼저 만드는 것이 아닙니다.
> 데이터를 통해 문제를 더 정확하게 이해하고, 근거 있는 인사이트를 바탕으로 정말 필요한 AI 서비스를 기획하는 것입니다.

<Callout kind="reflect">
- 데이터를 보기 전과 후에 문제에 대한 생각이 어떻게 달라졌는가?
- 처음 만들고 싶었던 기능 중 데이터가 필요 없다고 알려준 것은 무엇인가?
- 데이터가 새롭게 필요하다고 알려준 기능은 무엇인가?
- AI의 해석 중 받아들이지 않은 것은 무엇이며, 그 이유는 무엇인가?
- 지금의 데이터로 말할 수 없는 것은 무엇인가?
- 추가로 어떤 데이터를 수집하면 더 나은 판단을 할 수 있는가?
</Callout>
