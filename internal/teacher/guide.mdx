## 현재 수업 시작점

이 프로젝트는 처음부터 AI와 데이터를 설명하는 단원이 아닙니다. 학생들은 이미 다음 경험을 마친 상태에서 들어옵니다.

| 이미 경험한 내용 | 다음 단계에서 연결할 지점 |
| --- | --- |
| 인공지능의 큰 개념 | AI가 결과를 만들어도 사람이 질문·검증·판단해야 함 |
| 머신러닝의 기본 원리 | 데이터의 품질과 기준이 결과를 바꾼다는 경험 |
| Teachable Machine 실습 | 훈련 데이터, 테스트, 실패, 개선의 감각 |
| 공공데이터 첫 탐색 | 출처, 형식, 기준 시점, 주요 항목 확인 |

따라서 최종 프로젝트의 첫 과제는 “주제를 정하라”가 아니라, 학생이 이미 가진 관심 분야를 **검증 가능한 문제 정의와 구현 가능한 서비스 흐름**으로 바꾸는 것입니다.

## 교과서와 활동지의 역할

활동지는 수업 상황에 맞게 별도로 제작합니다. 교과서 본문은 학생이 반드시 알아야 할 기준, 실습 순서, 토론 질문, 생성형 AI 활용법, 검증 원칙을 담습니다.

| 구분 | 역할 |
| --- | --- |
| 교과서 | 공통 기준, 개념, 실습 흐름, AI 활용 원칙, 검증 기준 제시 |
| 활동지 | 팀별 기록, 아이디어 정리, 자료 목록, 발표 준비, 교사 피드백 수합 |
| 생성형 AI | 도메인 탐색, 질문 확장, 분석 보조, 설계 초안, 코드 초안 생성 |
| 학생 | 문제 선택, 출처 확인, 사실과 해석 구분, 최종 판단, 구현 검증 |

교과서에는 확인되지 않은 통계 수치, 출처가 불분명한 사례, AI가 만든 정책명이나 기관명을 사실처럼 싣지 않습니다. 생성형 AI의 답변은 출처가 아니라 탐색을 돕는 초안입니다.

## 수업 철학

```text
관심 분야를 말한다 → 도메인 지식을 만든다 → 문제를 정의한다
→ 공식 자료와 데이터를 확인한다 → 분석하고 해석한다
→ 인사이트를 기능으로 연결한다 → 구현하고 검증한다
→ 발표하며 한계와 개선점을 설명한다
```

학생들은 수준 높은 관심과 자기 생각을 가지고 있습니다. 그래서 지나치게 쉬운 예시만 제공하면 오히려 탐구가 얕아질 수 있습니다. 교사는 주제를 대신 정해 주기보다 다음 질문을 반복해 사고의 깊이를 만듭니다.

- 이 주장은 어떤 공식 자료로 확인할 수 있는가?
- 데이터에서 확인한 사실과 팀의 해석이 구분되어 있는가?
- 이 문제의 영향을 받는 사람은 누구인가?
- 데이터만으로 단정할 수 없는 것은 무엇인가?
- 분석 결과가 서비스 기능으로 어떻게 연결되는가?
- AI가 한 일과 사람이 판단한 일은 무엇인가?

<Callout kind="mission" title="운영 핵심">재미와 흥미는 필수입니다. 다만 재미있는 관심사가 가벼운 결론으로 끝나지 않도록 도메인 지식, 공공데이터, 검증, 구현을 연결합니다.</Callout>

## 최종 프로젝트의 필수 흐름

| 단계 | 학생에게 남아야 하는 것 | 교사의 확인 질문 |
| --- | --- | --- |
| 문제 정의 | 사용자, 상황, 어려움, 확인할 질문 | 누가 어떤 상황에서 왜 어려운가? |
| 데이터 수집 | 출처·기간·범위·단위·행의 의미가 확인된 자료 | 이 데이터로 그 질문에 답할 수 있는가? |
| 데이터 분석 | 표·그래프·계산 기준과 원자료 대조 | 어떤 값이 원자료에서 확인되는가? |
| 인사이트 | 사실·해석·가설·반례·한계의 구분 | 이 결과가 사용자에게 어떤 의미인가? |
| AI 서비스 설계 | 입력·처리·출력, AI 필요성, 사람의 확인 | AI가 꼭 필요한 기능인가? |
| 구현 | 최소 기능이 실제로 작동하는 웹앱 또는 프로토타입 | 같은 입력에서 기대한 결과가 나오는가? |

순서를 엄격하게 지키는 것보다 분석 결과 때문에 문제 정의와 기능이 바뀌는 경험이 중요합니다. 방향이 바뀐 팀은 실패한 것이 아니라 근거를 바탕으로 더 정확해진 것입니다.

## 권장 운영 흐름

| 차시 | 핵심 활동 | 생성형 AI 활용 | 산출 기준 |
| --- | --- | --- | --- |
| 1 | 관심 분야를 도메인 지식으로 확장 | 핵심 용어, 이해관계자, 공식 자료 후보 탐색 | 확인할 문제 후보 |
| 2 | 문제 정의와 탐구 질문 구체화 | 가벼운 질문을 검증 가능한 질문으로 변환 | 문제 정의문과 분석 질문 |
| 3 | 공공데이터 수집 계획 | 검색어, 자료 후보, 확인 기준 제안 | 데이터 후보표 |
| 4 | 데이터 읽기와 분석 | 열·단위·기준 확인, 그래프와 계산 보조 | 표·그래프·계산 근거 |
| 5 | 인사이트와 서비스 설계 | 사실·해석 구분, 기능 초안 생성 | 핵심 기능 설계 |
| 6 | 바이브코딩 구현 | HTML/CSS/JS 코드 초안, 오류 수정 | 작동하는 최소 기능 |
| 7 | 검증과 개선 | 테스트 조건, 빈 결과, 오류 처리 점검 | 수정 기록과 검증 결과 |
| 8 | 발표 | 발표 흐름, 대본, 한계 정리 | 시연 포함 발표 |

차시는 수업 여건에 따라 합치거나 늘릴 수 있습니다. 중요한 것은 데이터 분석과 구현을 분리하지 않고, 분석 결과가 기능으로 이어지게 하는 것입니다.

## 생성형 AI 활용 원칙

| 상황 | AI에게 맡길 수 있는 일 | 학생이 반드시 해야 할 일 |
| --- | --- | --- |
| 도메인 탐색 | 용어, 이해관계자, 자료 후보 정리 | 공식 출처 확인, 오해 표시 |
| 문제 정의 | 질문 후보와 비교 기준 제안 | 최종 문제 선택, 사용자 맥락 설명 |
| 데이터 수집 | 검색어와 자료 후보 추천 | 원문 페이지 확인, 출처·단위 기록 |
| 데이터 분석 | 표·그래프·계산 방법 제안 | 원자료 대조, 사실과 해석 구분 |
| 인사이트 | 가능한 의미와 반례 제안 | 과장 제거, 서비스 기능과 연결 |
| 구현 | 코드 초안, 오류 원인 설명 | 실행, 테스트, 수정 이유 설명 |
| 발표 | 발표 구조와 표현 다듬기 | 근거와 한계 직접 설명 |

AI가 만든 수치, 그래프, 코드, 설명은 검증 대상입니다. 특히 출처가 없는 통계, 실제로 존재하는지 모르는 기관명, 근거 없는 원인 설명은 사용하지 않습니다.

## 검증 원칙

프로젝트 전 과정에서 다음 다섯 가지를 반복 확인합니다.

| 원칙 | 설명 |
| --- | --- |
| 원자료 우선 | 중요한 수치와 항목은 공식 자료 또는 원문에서 확인한다. |
| 기준 명시 | 기간, 지역, 단위, 분모, 필터 기준을 말할 수 있어야 한다. |
| 사실과 해석 구분 | 데이터에서 확인한 사실과 팀의 해석을 섞지 않는다. |
| 한계 기록 | 데이터가 말해 주지 않는 것과 추가로 필요한 자료를 적는다. |
| 공개 안전 | 개인정보, API 키, 비공개 자료, 저작권 문제를 점검한다. |

학생이 발표에서 “AI가 그렇게 말했습니다”라고 답하면 충분하지 않습니다. “어떤 자료의 어떤 항목을 확인했고, 우리는 이렇게 해석했습니다”라고 말하도록 지도합니다.

## 고급 학생을 위한 도전 질문

수준 높은 학생에게는 더 어려운 코드를 먼저 요구하기보다, 질문과 검증의 깊이를 높이는 편이 효과적입니다.

| 도전 방향 | 발문 |
| --- | --- |
| 도메인 깊이 | 이 분야에서 겉으로 보이는 문제와 실제 구조적 문제는 어떻게 다른가? |
| 반례 | 우리 해석과 반대되는 설명은 무엇인가? |
| 비교 기준 | 단순 건수보다 비율이나 기준화가 필요한가? |
| 데이터 한계 | 이 자료가 만들어진 목적 때문에 빠지는 관점은 없는가? |
| 서비스 윤리 | 이 기능이 누군가에게 불이익이나 오해를 만들 수 있는가? |
| 구현 검증 | 이 기능이 실제 데이터에서 계산된 결과인지 확인할 수 있는가? |

## 바이브코딩 운영 원칙

바이브코딩은 수업의 결과물을 빠르게 만드는 좋은 방법이지만, 코드의 책임을 AI에게 넘기는 방식이 아닙니다.

```text
요구사항을 사람의 말로 쓴다 → AI가 코드 초안을 만든다
→ 실행한다 → 원자료와 기대 결과로 검증한다
→ 오류와 개선점을 구체적으로 설명한다 → 다시 수정한다
```

학생은 모든 문법을 완벽히 설명할 필요는 없지만, 다음은 말할 수 있어야 합니다.

- 어떤 데이터를 불러오는가?
- 사용자가 어떤 값을 입력하거나 선택하는가?
- 어떤 기준으로 필터링·계산·분류하는가?
- 결과가 화면의 어느 부분에 표시되는가?
- 어떤 테스트에서 정상 작동을 확인했는가?
- 어떤 오류가 있었고 어떻게 수정했는가?

## 구현 도구 선택

| 도구 | 기본 운영 판단 |
| --- | --- |
| HTML/CSS/JavaScript | 전체 학생의 기본 구현 방식. 브라우저에서 실행하기 쉽고 GitHub Pages 배포가 가능함. |
| Streamlit | 파이썬 경험을 살리거나 데이터 처리·시각화가 필요한 심화팀에 적합함. |
| API | 최신 조회나 조건별 검색이 필요할 때 선택. 인증키 관리 교육이 함께 필요함. |
| MCP | 공공통계 후보 탐색과 조회 조건 확인에 유용함. 최종 수치는 원자료 확인이 필요함. |
| 노코드·로우코드 도구 | 화면 초안이나 발표용 프로토타입에 활용 가능. 데이터 출처와 처리 과정을 설명해야 함. |

API 키는 공개 코드, GitHub 저장소, 발표 화면에 직접 넣지 않습니다. 전체 필수 과제는 환경 의존성이 낮은 파일 기반 웹앱으로 두고, API와 Streamlit은 선택 확장으로 운영하면 안정적입니다.

## 평가 관점

| 평가 요소 | 무엇을 보는가 |
| --- | --- |
| 문제 정의 | 사용자와 상황이 구체적이며 데이터로 확인할 질문이 있는가 |
| 도메인 지식 | 핵심 용어, 이해관계자, 공식 자료, 조심할 오해를 확인했는가 |
| 데이터 리터러시 | 출처, 기준 시점, 범위, 단위, 행의 의미, 한계를 설명하는가 |
| 분석과 검증 | 질문에 맞는 표·그래프·계산을 사용하고 원자료로 확인했는가 |
| 인사이트 | 사실, 해석, 가설, 반례, 한계를 구분하고 기능으로 연결했는가 |
| AI 활용 | AI에게 맥락을 주고 결과를 검증·수정한 과정이 드러나는가 |
| 구현 | 최소 기능이 실제 데이터로 작동하며 테스트 결과가 있는가 |
| 협업 | 팀원이 핵심 판단을 함께 설명하고 각자의 기여가 분명한가 |
| 발표 | 근거, 한계, 개선 방향을 과장 없이 설명하는가 |
| 성장 | AI 사용 후 새롭게 이해하거나 스스로 할 수 있게 된 것이 있는가 |

## 교사의 핵심 발문 모음

- 이 문제는 왜 여러분에게 흥미로운가요?
- 이 관심 분야를 데이터로 확인 가능한 질문으로 바꾸면 무엇인가요?
- 지금 말한 내용 중 공식 자료로 확인한 것은 무엇인가요?
- 이 데이터의 한 행은 무엇을 뜻하나요?
- 단위, 기간, 지역, 분모가 맞나요?
- 이 그래프가 보여 주는 사실은 무엇이고, 해석은 무엇인가요?
- 다른 설명이나 반례는 없나요?
- 인사이트가 어떤 기능으로 연결되나요?
- AI가 꼭 필요한 기능인가요, 아니면 필터·검색·계산으로 충분한가요?
- 같은 조건으로 원자료와 앱 결과를 비교했나요?
- 팀원 모두 이 앱의 입력·처리·출력을 설명할 수 있나요?
- 발표에서 데이터로 확인한 사실과 앞으로 확인해야 할 내용을 구분했나요?
