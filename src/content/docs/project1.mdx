개인 실험에서 작은 이미지 분류 모델을 직접 학습시키며 **학습 데이터 → 모델 → 테스트 → 오류 → 개선**의 과정을 경험했습니다.

이번에는 팀으로 범위를 넓힙니다.

<Callout kind="mission" title="Mini Project Mission">
**우리 교실 또는 학교에서 사진으로 상태를 구분하면 도움이 될 수 있는 작은 문제를 발견하고, 그 문제를 이미지 분류 머신러닝 모델로 표현해보세요.**

완성된 서비스나 웹앱을 만드는 것이 목표가 아닙니다. 좋은 문제를 정하고, 필요한 데이터를 생각하고, 모델의 실패를 분석하고 개선하는 과정이 핵심입니다.
</Callout>

## 1. AI보다 문제를 먼저 찾기

처음부터 "무엇을 AI로 만들까?"라고 생각하지 않습니다. 먼저 교실과 학교를 관찰합니다.

- 반복해서 확인해야 하는 상태가 있는가?
- 사람이 눈으로 보고 구분하는 일이 있는가?
- 사진 한 장으로 어느 정도 상태를 판단할 수 있는가?
- 상태를 빠르게 구분하면 누군가에게 실제로 도움이 되는가?

예를 들어 다음과 같은 방향을 생각할 수 있습니다.

| 관찰한 상황 | 이미지로 구분할 수 있는 상태 예시 |
| --- | --- |
| 쓰레기통 관리 | 비어 있음 / 적당함 / 가득 참 |
| 분리배출 | 올바른 분리 / 확인 필요 |
| 칠판 관리 | 깨끗함 / 지워야 함 |
| 교실 조명 | 켜짐 / 꺼짐 |
| 창문 상태 | 열림 / 닫힘 |
| 교실 정리 | 정돈됨 / 정돈 필요 |

이 예시는 정답이 아닙니다. 팀이 직접 학교 안에서 관찰 가능한 문제를 찾아보세요.

<Callout kind="caution" title="사람을 분류 대상으로 삼을 때">
학생의 얼굴, 감정, 행동, 집중도처럼 사람을 촬영하고 평가하는 주제는 개인정보, 동의, 편향, 감시와 같은 문제가 생길 수 있습니다. 이번 미니 프로젝트에서는 가능하면 **사람이 아닌 사물이나 환경의 상태**를 중심으로 문제를 찾습니다.
</Callout>

## 2. 문제를 이미지 분류 문제로 바꾸기

좋은 아이디어는 다음 두 문장으로 설명할 수 있어야 합니다.

> **우리가 발견한 문제는 __________이다.**
>
> 이 문제를 돕기 위해 사진을 보고 **__________ / __________ / __________** 상태를 구분하는 모델을 실험한다.

그리고 반드시 확인합니다.

- 사진만으로 실제로 구분 가능한가?
- 클래스의 기준이 서로 겹치지 않는가?
- 필요한 사진을 안전하고 현실적으로 수집할 수 있는가?
- AI 분류 결과가 이 문제에 실제로 도움이 되는가?

## 3. 학습 데이터를 설계하기

<Callout kind="concept" title="사진을 많이 찍는 것보다 중요한 질문">
**실제 사용 상황에서는 어떤 모습이 나타날까?**
</Callout>

거리, 각도, 조명, 배경, 물체의 종류와 위치 등이 달라질 수 있습니다. 한 조건에서만 비슷한 사진을 많이 모으면 새로운 상황에서 잘 작동하지 않을 수 있습니다.

팀은 데이터를 촬영하기 전에 다음을 결정합니다.

- 클래스마다 어떤 장면이 필요한가?
- 각 클래스의 데이터 양은 적절한가?
- 어떤 거리와 각도를 포함할 것인가?
- 배경이나 조명은 얼마나 다양해야 하는가?
- 모델이 엉뚱한 특징을 배우지 않도록 무엇을 조심해야 하는가?

## 4. 첫 모델을 만들고 새로운 데이터로 테스트하기

<Steps>
	<Step title="문제와 클래스 확정">누구의 어떤 문제인지, 모델이 구분할 상태가 무엇인지 정합니다.</Step>
	<Step title="학습 데이터 수집">팀이 정한 기준에 따라 클래스별 이미지를 모읍니다.</Step>
	<Step title="첫 모델 학습">Teachable Machine으로 첫 번째 모델을 학습시킵니다.</Step>
	<Step title="테스트 데이터 준비">가능하면 학습에 사용하지 않은 새로운 사진과 새로운 조건을 준비합니다.</Step>
	<Step title="실패 사례 찾기">잘 맞힌 사례뿐 아니라 틀린 사례를 적극적으로 찾습니다.</Step>
	<Step title="실패 원인 가설">어떤 데이터나 조건 때문에 틀렸을지 팀의 가설을 세웁니다.</Step>
	<Step title="한 가지 개선">데이터의 양, 다양성, 클래스 기준 등 한 가지를 의도적으로 바꿉니다.</Step>
	<Step title="재학습·재테스트">가능하면 같은 테스트 조건으로 다시 확인하여 무엇이 달라졌는지 비교합니다.</Step>
</Steps>

## 5. 성능보다 중요한 것

이번 프로젝트에서는 높은 정확도 숫자 자체가 목표가 아닙니다.

<Callout kind="concept" title="프로젝트에서 더 중요하게 보는 것">
- 문제를 구체적으로 정의했는가?
- 왜 이미지 분류가 도움이 되는지 설명할 수 있는가?
- 학습 데이터와 테스트 데이터를 구분했는가?
- 새로운 상황에서 모델을 시험했는가?
- 모델이 틀린 이유를 데이터와 연결해 생각했는가?
- 개선 전후의 차이를 설명할 수 있는가?
- 실제 사용한다면 생길 한계와 위험을 생각했는가?
</Callout>

## 6. 프로젝트 속 핵심 개념 다시 보기

**학습 데이터(Training Data)**  
모델이 패턴을 배우는 데 사용하는 데이터입니다.

**테스트 데이터(Test Data)**  
학습된 모델이 새로운 데이터에서도 잘 작동하는지 확인하는 데 사용하는 데이터입니다.

**일반화(Generalization)**  
학습할 때 보지 못한 새로운 상황에서도 적절하게 판단하는 능력입니다.

**과대적합(Overfitting)**  
학습 데이터에는 지나치게 잘 맞지만 새로운 데이터에서는 성능이 떨어지는 현상입니다.

<Callout kind="caution">
모델이 실패했다고 프로젝트가 실패한 것은 아닙니다. **왜 실패했는지를 찾아 데이터와 모델을 다시 생각했다면 그것이 이번 프로젝트의 중요한 학습입니다.**
</Callout>
