## 1. 이미 가진 관심을 탐구 질문으로 바꾸기

여러분은 이미 관심 분야가 있습니다. 진로, 사회 문제, 문화, 환경, 학교생활, 기술, 언어, 미디어, 경제, 복지, 교통처럼 출발점은 다양할 수 있습니다. 중요한 것은 관심 자체가 아니라 그 관심을 **확인 가능한 질문**으로 바꾸는 일입니다.

| 출발점 | 탐구 질문으로 바꾸는 기준 |
| --- | --- |
| 내가 관심 있는 분야 | 어떤 현상이나 문제가 실제로 있는가? |
| 내가 중요하다고 생각하는 주장 | 어떤 자료로 확인하거나 반박할 수 있는가? |
| 내가 만들고 싶은 서비스 | 어떤 사용자에게 어떤 정보가 필요한가? |
| 내가 예상한 원인 | 데이터만으로 확인 가능한가, 추가 조사가 필요한가? |
| 내가 바꾸고 싶은 상황 | 현재 상태와 목표 상태를 어떻게 비교할 수 있는가? |

처음부터 완벽한 문제를 찾으려 하지 않습니다. 관심 분야를 말로 설명한 뒤, 공공데이터와 공식 자료로 확인할 수 있는 부분을 찾습니다.

<Callout kind="caution" title="AI는 출처가 아닙니다">생성형 AI의 답변은 탐색과 정리를 돕는 초안입니다. 통계 수치, 정책명, 기관명, 사례, 데이터 항목은 반드시 원자료나 공식 출처에서 다시 확인해야 합니다.</Callout>

## 2. 필요한 배경지식 확인하기

도메인 지식은 어떤 분야를 이해하는 데 필요한 배경지식입니다. 모든 팀이 처음부터 긴 조사 보고서를 만들 필요는 없습니다. 관심 주제를 말하고 문제를 정하는 과정에서 모르는 용어, 관련 기관, 제도, 이해관계자, 조심할 오해가 나오면 필요한 만큼 찾아봅니다.

중요한 순서는 **내 생각 → 팀 의논 → 필요한 배경지식 확인 → AI 도움 → 원자료 검증**입니다. AI가 정리한 배경지식은 초안일 뿐이며, 통계 수치·정책명·기관명·사례는 반드시 공식 자료에서 다시 확인합니다.

### 배경지식이 필요해지는 순간

| 필요한 순간 | 확인할 내용 |
| --- | --- |
| 용어가 낯설 때 | 이 분야에서 자주 쓰는 말과 정확한 의미 |
| 사용자가 흐릿할 때 | 문제의 영향을 받는 사람, 관리하는 기관, 서비스를 사용할 사람 |
| 문제가 감상처럼 느껴질 때 | 생활 속 사례, 정책, 제도, 현장의 불편 |
| 자료를 찾기 어려울 때 | 공공기관 자료, 통계표, 보고서, 안내문, 원문 링크 |
| 결론이 너무 빨리 나올 때 | 데이터 하나만 보고 쉽게 단정하면 안 되는 것 |
| 질문이 너무 넓을 때 | 자료로 비교하거나 계산할 수 있는 질문 |

팀 토론에서는 AI가 정리한 내용을 그대로 받아들이지 않습니다. 먼저 팀의 생각을 말하고, 이해가 되지 않는 용어, 출처가 없는 설명, 너무 넓은 주장, 검증이 필요한 수치를 표시한 뒤 다시 확인합니다.

## 4. 데이터 수집 계획 세우기

공공데이터는 공공기관이 생성하거나 관리하고 공개하는 자료입니다. 프로젝트에서는 공식 자료를 우선 사용하고, 필요한 경우 설문·인터뷰·관찰 기록을 보조 자료로 활용할 수 있습니다.

대표적인 공공데이터 탐색 출발점은 공공데이터포털, KOSIS 국가통계포털, 지방자치단체 열린데이터, 기상자료개방포털, 교육·문화·교통 관련 공공기관의 공개 자료입니다. 단, 실제 프로젝트에서는 항상 원문 페이지의 제공 기관, 갱신일, 이용 조건을 확인해야 합니다.

### 자료를 고를 때 확인할 기준

| 기준 | 확인 질문 |

파일, API, MCP, 설문, 인터뷰는 서로 경쟁하는 방법이 아닙니다. 탐구 질문에 맞게 선택합니다. API 키가 필요한 자료는 공개 저장소나 화면에 키를 노출하지 않습니다. 개인정보가 포함될 수 있는 자료는 수집하지 않거나 익명화하고, 공개 범위를 제한합니다.

## 5. 데이터 읽기와 분석하기

분석은 그래프를 많이 만드는 일이 아닙니다. 탐구 질문에 답하기 위해 자료를 정리하고 비교하는 과정입니다.

분석 전에 먼저 데이터의 구조를 읽습니다. 한 행이 무엇을 뜻하는지, 어떤 열을 사용할지, 단위가 무엇인지, 비교 기준이 공정한지 확인합니다.

<CopyPrompt title="데이터 분석 프롬프트" content={analysisPrompt} />

### 분석 관점 고르기

| 보고 싶은 것 | 적절한 방법 | 확인할 점 |
| --- | --- | --- |
| 시간 변화 | 연도별·월별 변화 표와 선그래프 | 기간이 충분한가? 기준이 바뀌지 않았는가? |
| 지역 차이 | 지역별 비교 표와 막대그래프 | 인구나 규모 차이를 고려해야 하는가? |
| 집단 차이 | 유형·연령·성별·분류별 비교 | 분류 기준이 명확한가? |
| 비율 | 전체 대비 비율 계산 | 분모가 무엇인지 설명할 수 있는가? |
| 순위 | 상위·하위 항목 비교 | 값이 큰 이유를 단정하지 않는가? |
| 관계 | 두 변수의 산점도 또는 교차표 | 상관을 원인으로 해석하지 않는가? |
| 이상값 | 평균에서 크게 벗어난 값 확인 | 오류인지 의미 있는 사례인지 확인했는가? |

AI에게 분석을 맡길 때도 원자료와 비교합니다. AI가 만든 표나 그래프가 실제 파일의 어떤 열과 어떤 계산에서 나온 것인지 확인해야 합니다.

<Callout kind="caution" title="상관관계와 인과관계">두 값이 함께 움직인다고 해서 하나가 다른 하나의 원인이라고 말할 수는 없습니다. 원인을 주장하려면 추가 자료, 비교 조건, 다른 설명 가능성을 함께 검토해야 합니다.</Callout>

## 6. 인사이트 도출하기

인사이트는 “그래프가 이렇게 나왔다”가 아닙니다. 데이터에서 확인한 사실을 사용자 상황과 연결하여, 어떤 서비스 기능이나 판단으로 이어질 수 있는지 설명하는 것입니다.

> 자료에서 **[확인한 사실]**을 발견했다. 이 사실은 **[사용자 상황]**에서 **[의미]**가 있다. 그래서 우리 서비스는 **[필요한 정보 또는 기능]**을 제공해야 한다.

<CopyPrompt title="인사이트 도출 프롬프트" content={insightPrompt} />

### 인사이트 점검 질문

| 질문 | 이유 |
| --- | --- |
| 이것은 데이터에서 확인한 사실인가, 우리의 해석인가? | 사실과 해석 구분 |
| 다른 설명이나 반례가 가능한가? | 성급한 결론 방지 |
| 사용자에게 어떤 의미가 있는가? | 서비스 연결 |
| 이 인사이트 때문에 문제 정의가 바뀌는가? | 탐구 순환 |
| 어떤 기능으로 구현할 수 있는가? | 산출물 연결 |

인사이트가 약하면 앱은 단순 정보 게시판이 되기 쉽습니다. 반대로 인사이트가 분명하면 작은 기능 하나도 설득력이 생깁니다.

## 7. AI 서비스 설계하기

AI 서비스라고 해서 모든 기능에 AI가 들어가야 하는 것은 아닙니다. 어떤 기능은 검색, 필터, 계산, 시각화만으로 더 정확하고 안전합니다. AI는 요약, 질문 응답, 설명, 추천, 분류, 코드 작성 보조처럼 필요한 순간에 사용합니다.

<CopyPrompt title="AI 서비스 설계 프롬프트" content={designPrompt} />

### 기능을 설계할 때 구분할 것

| 구분 | 설명 | 예 |
| --- | --- | --- |
| 데이터 기반 기능 | 실제 데이터에서 계산하거나 필터링한 결과 | 지역별 변화, 조건별 검색, 순위 표시 |
| AI 보조 기능 | 사용자의 질문을 정리하거나 결과를 설명 | 그래프 해석 문장 생성, 탐색 질문 추천 |

### 화면 흐름 설계

사용자가 앱을 열었을 때 무엇을 먼저 보고, 어떤 값을 입력하거나 선택하며, 어떤 결과를 확인하는지 순서대로 설계합니다.

```text
첫 화면 → 조건 선택 또는 입력 → 데이터 처리 → 결과 표시 → 근거 확인 → 다음 행동
```

화면에는 데이터 출처, 기준 시점, 결과가 비어 있을 때의 안내, 오류가 났을 때의 안내가 들어가야 합니다.

## 8. 바이브코딩으로 구현하기

바이브코딩은 “AI에게 알아서 만들어 달라”가 아닙니다. 사람이 문제, 데이터, 기능, 테스트 조건을 명확히 주고, AI가 만든 코드를 실행·검증·수정하며 결과물을 완성하는 방식입니다.

<CopyPrompt title="바이브코딩 구현 프롬프트" content={developmentPrompt} />

### 구현 순서

| 단계 | 할 일 |
| --- | --- |
| 1. 최소 기능 정하기 | 이번 시간에 반드시 작동해야 하는 기능 하나를 정한다. |
| 2. 데이터 연결하기 | 파일, JSON, CSV, 예시 데이터 중 사용할 방법을 정한다. |
| 3. 화면 만들기 | 사용자가 입력하고 결과를 볼 수 있는 구조를 만든다. |
| 4. 처리 로직 만들기 | 필터, 계산, 검색, 분류 기준을 코드로 표현한다. |
| 5. 원자료와 비교하기 | 같은 조건에서 원자료의 값과 앱 결과를 대조한다. |
| 6. 오류와 빈 결과 처리 | 잘못된 입력, 데이터 없음, 파일 오류를 안내한다. |
| 7. UI 다듬기 | 사용자가 이해하기 쉬운 문장과 배치를 적용한다. |

기본 구현은 HTML, CSS, JavaScript로 시작합니다. 팀의 질문에 필요하고 실행 환경이 준비되어 있다면 Streamlit, API, 지도, 차트 라이브러리 등을 선택 확장할 수 있습니다.

### 오류를 AI에게 설명하는 방법

```text
현재 파일과 실행 환경: [내용]
입력한 값과 실행 순서: [내용]
원자료에서 기대한 결과: [내용]
화면에 나온 결과 또는 오류 메시지: [내용]
정상 작동해야 하는 기능: [내용]

기존 정상 기능을 유지하면서 원인을 설명하고 수정할 부분을 제안해줘.
수정한 전체 코드와 다시 확인할 테스트를 함께 알려줘.
```

코드를 공개 저장소에 올릴 때는 API 키, 개인 식별 정보, 비공개 자료가 포함되지 않았는지 확인합니다.

## 9. 협업과 토론

이 프로젝트는 역할을 나누되 중요한 판단은 함께 해야 합니다. 도메인 탐색 담당, 데이터 담당, 분석 담당, 구현 담당, 발표 담당이 따로 있어도 문제 정의와 인사이트, 서비스 방향은 팀 전체가 설명할 수 있어야 합니다.

| 협업 장면 | 함께 결정할 것 |
| --- | --- |
| 도메인 탐색 후 | 어떤 문제를 볼 만한가? 어떤 오해를 피해야 하는가? |
| 데이터 선택 후 | 이 자료로 우리의 질문에 답할 수 있는가? |
| 분석 후 | 결과가 예상과 같았는가? 문제를 수정해야 하는가? |
| 설계 후 | 사용자가 실제로 쓸 이유가 있는가? |
| 구현 후 | 원자료와 결과가 맞는가? 화면이 이해하기 쉬운가? |
| 발표 전 | 사실, 해석, 제안이 구분되어 있는가? |

팀 회의에서는 AI에게 바로 결론을 묻기 전에 각자 먼저 판단을 말합니다. 그다음 AI를 사용해 빠진 관점, 반례, 검증 방법을 찾습니다.

## 10. 검증하고 개선하기

완성도는 화면의 화려함보다 검증에서 드러납니다. 앱이 실제 데이터와 맞는지, 사용자가 원하는 일을 할 수 있는지 확인합니다.

### 데이터 검증

| 확인 항목 | 방법 |
| --- | --- |
| 원자료 대조 | 원자료에서 직접 계산한 값과 앱 결과를 비교한다. |
| 기준 확인 | 기간, 지역, 단위, 필터 기준이 화면과 코드에서 일치하는지 본다. |
| 예외 입력 | 결과 없음, 잘못된 입력, 빠진 데이터 상황을 확인한다. |
| 반복 실행 | 같은 조건에서 같은 결과가 나오는지 본다. |

### 사용자 검증

다른 팀에게 앱을 사용하게 하고, 어디에서 막히는지 관찰합니다. 설명이 부족한 부분, 결과를 오해할 수 있는 부분, 더 필요한 기능을 기록한 뒤 수정합니다.

검증 결과 때문에 문제 정의, 데이터 범위, 기능이 바뀔 수 있습니다. 그것은 프로젝트가 흔들린 것이 아니라 더 정확해진 것입니다.

| 개선 | 사용자 테스트 후 이 부분을 더 쉽게 바꾸었습니다. |

최종 발표에는 실제 화면 시연이 포함되어야 합니다. 실행이 어려운 경우에도 코드, 화면, 데이터, 테스트 결과를 통해 최소 기능이 어떻게 작동하는지 설명할 수 있어야 합니다.

## 12. 최종 확인 기준

| 기준 | 확인할 내용 |
| --- | --- |

| 도메인 지식 | 핵심 용어, 이해관계자, 공식 자료, 조심할 오해를 확인했는가? |
