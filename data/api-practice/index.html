공공데이터 API: 요청부터 앱 연결까지

API로 자료를 받는 팀이 필요한 부분을 찾아보는 도움말입니다. 파일 자료를 사용하는 팀은 기존 파일 분석·구현을 이어갑니다. NEIS에서 해 본 요청·응답을 다른 기관에 적용할 때는 그 기관의 명세를 확인합니다. 키를 발급받았다고 데이터가 자동으로 들어오지는 않습니다. 사용할 조회 기능과 조건으로 요청을 보내고, 받은 응답에서 필요한 값을 골라 앱에 표시합니다.

1. 활용신청 다음에 펼칠 화면

섹션 제목: “1. 활용신청 다음에 펼칠 화면”

공공데이터포털에서 내가 활용신청한 API의 상세 페이지를 엽니다. 승인 상태와 이용 범위를 확인하고, 사용할 상세기능을 선택합니다. 화면 이름이 달라져도 다음 내용을 찾으면 됩니다.

포털·명세서의 표현뜻과 가져올 내용
참고문서·활용가이드API 사용 명세서입니다. 내려받아 필요한 기능의 설명·요청 예시·응답 예시를 읽습니다. 첨부 ZIP이면 압축을 풀어 문서와 코드표도 확인합니다.
상세기능·오퍼레이션(operation)같은 API 안에서 할 수 있는 조회 작업입니다. 원하는 자료를 주는 기능 하나를 선택합니다.
서비스 URL·End Point기관의 API가 있는 기본 주소입니다. 상세기능 경로를 더해야 하는지 예시와 비교합니다.
요청주소선택한 기능까지 포함한 주소일 수 있습니다. 포털이 완성된 요청주소를 주면 기능 이름을 또 붙이지 않습니다.
요청변수·요청인자기관으로 보낼 값입니다. 변수 이름·필수 여부·길이·형식·예시를 확인합니다.
출력결과·응답메시지기관에서 받을 값입니다. 항목 이름·목록 위치·단위·정상/오류 코드를 확인합니다.

예를 들어 보낼 값은 ‘격자와 시각’이고 받을 값은 ‘기온·습도 등’일 수 있습니다. 입력과 출력은 같은 이름으로 일대일 대응하지 않습니다. 문서에 없는 검색 조건을 마음대로 추가하지 않습니다.

2. 기상청 예제로 요청 기능 정하기

섹션 제목: “2. 기상청 예제로 요청 기능 정하기”

이 예제는 공공데이터포털에서 발급받은 키로 기상청 단기예보 조회서비스의 초단기실황조회(getUltraSrtNcst)를 요청합니다. 서비스 이름에 ‘예보’가 있지만 이 기능은 관측된 실황을 조회합니다. 미래 기온 예보를 받는 기능과 구분하세요.

같은 기상청이라도 공공데이터포털 apis.data.go.kr의 serviceKey와 기상청 API허브의 authKey는 다른 인증 체계입니다. 활용가이드에 API허브 예제가 함께 있더라도 주소와 키를 섞지 않습니다. 아래는 공공데이터포털 방식으로 통일합니다.

목적선택할 기능보내는 조건받을 항목앱에서 보여 줄 값
한 지역·기준시각의 기온 확인getUltraSrtNcst격자 nx,ny, 날짜 base_date, 시각 base_timecategory가 T1H인 항목의 obsrValue기온(℃), 관측 기준시각, 격자

지역 이름 대신 격자 좌표를 보냅니다. 포털 참고문서의 격자 자료에서 지역에 맞는 nx,ny를 찾습니다. 서울특별시 대표 격자 예시는 60, 127입니다. 모든 서울 동네가 같은 격자라는 뜻은 아니며, 위도·경도 값을 그대로 넣지 않습니다.

요청변수구분값의 예·형식필요한 이유
serviceKey필수YOUR_API_KEY요청자의 이용 권한 확인
pageNo필수1받을 페이지
numOfRows필수1000한 페이지에서 받을 개수. 실제 전체 건수와 받은 범위도 확인

초단기실황은 공식 안내상 매시각 10분 이후 호출합니다. 정각 직후에는 해당 시각 자료가 준비되지 않을 수 있습니다. 현재 제공 범위 안의 준비된 정시를 선택하고, 자정 전후에는 날짜도 함께 바꿉니다. 가이드·서비스 상태에 따라 실제 제공 여부를 확인하세요. 아래 날짜 자리표시자를 과거 예시 날짜로 그대로 두지 않습니다.

3. 요청 URL을 한 부분씩 만들기

섹션 제목: “3. 요청 URL을 한 부분씩 만들기”

① 기본 주소

② 상세기능을 한 번 붙인 요청주소

③ ? 뒤에 첫 조건, & 뒤에 다음 조건을 붙입니다. 이름=값에서 왼쪽은 문서에 나온 정확한 변수 이름, 오른쪽은 넣을 값입니다. 대소문자·버전·철자를 유지합니다.

위 ...는 구조 설명용이며 실행 주소가 아닙니다. 아래 완성형에서 키·날짜·시각·격자를 바꿉니다.

  • YOUR_API_KEY: 교사가 안내한 개인 실습 환경에서 직접 적용합니다. AI 대화·공개 문서·저장소에는 넣지 않습니다.
  • YYYYMMDD: 현재 제공되는 범위에서 선택한 실제 날짜로 바꿉니다.
  • HH00: 자료가 준비된 정시 네 자리로 바꿉니다. 예를 들어 오전 9시는 0900입니다.
  • 60,127: 격자 자료에서 확인한 우리 지역 값으로 바꿉니다.

인코딩은 사용하는 도구와 맞춰 한 번 처리합니다. 포털은 일반 인증키를 Encoding/Decoding 형태로 안내할 수 있습니다. 주소 문자열을 직접 붙이는 방식과 Swagger·URLSearchParams처럼 값을 인코딩하는 도구는 입력 방식이 다릅니다. 이미 인코딩한 값을 다시 인코딩하면 % 등이 중복 변환될 수 있습니다. 포털 테스트 도구의 안내와 공식 예시를 따르고, 오류가 나면 키를 재발급하기 전에 이중 인코딩 여부를 확인합니다.

이번처럼 GET이고 인증·조건이 URL 쿼리에 들어가는 요청은 완성형을 줄바꿈 없는 한 줄로 브라우저 주소창에 붙여 넣어 실행할 수 있습니다. 헤더 인증이나 POST가 필요한 다른 API는 주소창만으로 같은 요청을 만들 수 없습니다. 기관 테스트 도구와 해당 명세의 방법을 사용하세요. 키가 들어간 주소는 공유·캡처·공개 북마크로 남기지 않습니다.

명세서로 요청 URL 만들기 표시된 부분을 우리 팀의 내용으로 바꾸세요.
프롬프트 구조와 각 부분이 필요한 이유 보기

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

과업·필수 기능은 만들어야 할 결과와 빠뜨리면 안 되는 동작을 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

공식 명세를 바탕으로 GET 요청 URL 하나를 만들려고 해.
API 이름·제공 기관: {{정확한 이름}}
공식 활용 명세서: {{파일 첨부 또는 링크와 해당 요청·응답 설명 발췌}}

1. 기본 주소·상세기능 경로·요청 방식·인증 위치를 문서에서 확인해줘. GET 주소창 요청이 가능한 방식인지 먼저 판단해줘.
2. 필수/선택 요청변수의 정확한 이름·대소문자·형식·예시·의미를 표로 설명해줘. 문서에 없는 항목이나 값은 지어내지 마.
3. 기본 주소에 기능 경로, ? 뒤 첫 조건, & 뒤 다음 조건을 더하는 순서를 보여주고, 마지막에는 한 줄 URL을 제공해줘. 문서가 완성된 요청주소를 주면 기능 경로를 중복해서 붙이지 마.
4. 실제 키는 넣지 말고, 사용하는 도구에 맞는 인코딩 방법과 직접 바꿀 위치만 알려줘. 문서를 읽을 수 없으면 필요한 페이지나 발췌를 요청해줘.
5. 정상/자료없음/오류를 응답에서 구분할 위치와 앱에서 꺼낼 항목·단위를 알려줘. 실행하지 않은 요청은 성공했다고 하지 마. 나는 URL과 값을 확인한 뒤 직접 실행할게.

4. 받은 응답에서 기온 찾기

섹션 제목: “4. 받은 응답에서 기온 찾기”

먼저 HTTP 상태와 응답 본문의 기관 처리 결과를 구분합니다. HTTP 200은 응답을 받았다는 뜻이지 원하는 자료를 받았다는 보장은 아닙니다. 이 API는 본문의 response.header.resultCode와 resultMsg도 확인합니다. 정상 코드 00을 확인한 다음 실제 목록을 읽습니다. 03은 자료없음, 10은 요청변수 오류, 11은 필수값 누락, 22는 요청 제한, 30은 미등록 키를 뜻하는 이 서비스의 코드 예입니다. 다른 기관에도 같은 번호를 적용하지 않습니다.

아래는 구조 설명용으로 만든 모의 JSON입니다. 실제 조회 결과도, 현재 날씨도 아닙니다. 실제 응답 구조와 값은 직접 요청한 결과와 비교합니다.

  1. response → header에서 처리 결과를 읽습니다.
  2. response → body → items → item에서 기록 목록을 찾습니다.
  3. category=T1H를 요청 URL에 임의로 추가하는 것이 아니라 받은 목록에서 고릅니다. 목록의 첫 항목이라고 기온은 아닙니다. category === "T1H"인 항목을 찾습니다.
  4. 그 항목의 obsrValue가 기온 값이며 단위는 ℃입니다. REH는 습도(%), RN1은 1시간 강수량(mm)처럼 항목별 단위가 다릅니다.
  5. baseDate, baseTime, nx, ny가 내가 요청한 조건과 맞는지 비교합니다. 요청의 base_date와 응답의 baseDate는 이름부터 다릅니다.

obsrValue가 -999 등 공식 결측 범위(−900 이하 또는 +900 이상)에 해당하면 실제 기온으로 표시하지 않고 관측값 없음으로 안내합니다.

초단기예보처럼 다른 기능의 fcstValue·예보 날짜를 이 실황 예제에 섞지 않습니다. 이 예제는 obsrValue와 관측 기준시각을 사용합니다.

5. 응답이 예상과 다를 때

섹션 제목: “5. 응답이 예상과 다를 때”
관찰한 결과먼저 확인할 것
HTTP 404·찾을 수 없는 경로기관·버전·상세기능의 철자, 기능 경로 중복 여부
HTTP 401/403 또는 본문에 인증·권한 오류활용신청 승인 상태, 해당 API에 발급된 키인지, 인증 위치·이름·인코딩 방식. HTTP와 기관 코드를 같은 뜻으로 단정하지 않기
본문에 요청변수 오류필수값 누락, 변수 대소문자, 날짜8자리·시각4자리·격자 형식
정상 응답이지만 목록 없음 또는 자료없음 메시지오래된 날짜, 아직 생성되지 않은 시각, 제공 범위·격자. ‘기온 0도’로 바꾸지 않기
JSON 대신 XML·문자 오류 응답dataType=JSON 여부와 원문 내용. 인증 단계의 오류는 다른 형식일 수도 있음
일부 항목만 보임numOfRows, pageNo, totalCount, 실제 받은 목록 길이
주소창에서는 보이지만 앱에서 실패Console·Network의 실제 오류, CORS 허용, HTTPS 페이지에서 HTTP 호출, 요청 생성·JSON 처리 코드, 서버 설정을 구분

직접 실행해 보는 화면 예제

섹션 제목: “직접 실행해 보는 화면 예제”
  1. 정상 응답을 확인했다면 응답 본문 JSON만 weather.json으로 저장합니다. 요청주소나 인증키는 파일에 넣지 않습니다.
  2. 저장한 응답을 표시하는 HTML 내려받기로 파일을 저장한 뒤 브라우저에서 엽니다.
  3. 조회한 시각을 적고 weather.json을 선택합니다. 기온·관측 기준시각·격자를 원문과 대조합니다.
  4. 다른 격자나 준비된 다른 기준시각으로 요청해 저장한 JSON을 선택하고, 조건에 맞는 표시인지 확인합니다. 실제 값이 우연히 같을 수도 있으므로 값이 바뀌었는지만 보지 않습니다.

이 HTML은 실제 응답을 파일로 읽는 예제이며 API를 자동 호출하지 않습니다. ‘저장된 자료, 실시간 아님’과 출처를 표시합니다. 자료가 없거나 오류인 JSON을 넣었을 때 안내도 확인하세요. 자료의 이용 조건을 지키고, 임의의 예시값을 실제 기온처럼 표시하지 않습니다.

현재 앱 파일·공식 명세·키를 가린 정상 응답을 함께 준비합니다. 앱이 이미 허용된 방식으로 데이터를 요청한다면 그 구조를 유지하며 응답을 화면에 연결합니다. 공개 앱에서 비밀키를 사용하려면 서버에서 키를 보관하고 호출하는 구성이 필요할 수 있습니다. GitHub Pages는 정적 파일을 제공하며 비밀키를 숨겨 주거나 서버 코드를 실행해 주지 않습니다. 서버 연결이 준비되지 않았다면 파일 기반 화면으로 확인한 범위를 남기고 선생님과 다음 설정을 확인합니다.

8. 짧게 바꿔 보고 확인하기

섹션 제목: “8. 짧게 바꿔 보고 확인하기”

원래 활동지의 자료 확보·구현·검증 기록에 필요한 내용을 이어 적습니다. 추가 제출물은 없습니다.

  • 조건 하나만 바꿔 다시 요청하고, 응답의 지역·기준시각과 필요한 항목을 비교했나요?
  • 실패했다면 실제 오류로 원인을 좁혔나요? 아직 확인하지 못한 내용도 구분했나요?
