<Stage label="FINAL PROJECT · TEAM · 8~10차시" question="데이터에서 발견한 현상을 어떤 AI 서비스로 연결할 수 있을까?" />

<Callout kind="mission" title="DATA TO AI SERVICE">나의 진로·관심 분야 또는 해결하고 싶은 사회문제에서 출발합니다. 공공데이터를 분석해 문제 가설을 확인하거나 수정하고, 분석에서 발견한 인사이트를 근거로 AI 서비스 기획안을 제안합니다. **서비스 기획은 필수이며 실제 모델 학습과 웹 구현은 선택입니다.**</Callout>

```text
관심·문제 가설 → 현재 상태·목표 상태 → 문제 분해 → 팀 구성
→ 공공데이터 탐색 → 구조·품질·전처리
→ 시각화·관계 분석 → 사실·해석·한계 → 인사이트
→ 문제 재정의 → AI 필요성 → 데이터·역할·시나리오 설계
→ 위험 점검 → 피드백 → 최종 제안
```

## 먼저 팀을 구성합니다

비슷한 관심 분야를 가장 먼저 맞추고, 팀 안에서는 서로 다른 강점이 최대한 섞이도록 3인 내외로 구성합니다.

| 주도 역할 | 주로 맡는 일 |
| --- | --- |
| 데이터 탐색·근거 | 공공데이터와 원자료 검색, 출처·기간·변수 확인 |
| 분석·검증 | 전처리, 그래프, 관계 분석, 결과 재현과 오류 확인 |
| 서비스 기획·표현 | 사용자, 기능, 이용 장면, 발표 자료 구성 |

역할은 일을 나누기 위한 출발점일 뿐입니다. 중요한 질문·전처리 기준·인사이트·서비스 방향은 팀원이 함께 결정합니다.

## STEP 1 · 관심에서 문제 가설로

완성된 서비스 아이디어부터 정하지 않습니다. 먼저 교육·외국어·문화·경제·국제사회·심리·환경·안전·진로·학교생활처럼 팀이 끝까지 궁금해할 분야를 고릅니다.

<Steps>
<Step title="관심 현상 말하기">우리 팀이 실제로 궁금하거나 불편하다고 느낀 현상을 각자 제안합니다.</Step>
<Step title="대상과 상황 좁히기">누가, 언제, 어디에서 어떤 어려움을 겪는지 구체화합니다.</Step>
<Step title="현재 상태와 목표 상태 쓰기">지금 실제로 일어나는 모습과 우리가 바라는 모습을 각각 관찰 가능한 문장으로 씁니다.</Step>
<Step title="차이를 작은 문제로 나누기">현재와 목표 사이의 차이를 원인·정보·행동·환경처럼 확인 가능한 작은 문제로 나눕니다.</Step>
<Step title="문제 가설 쓰기">나눈 문제 중 데이터로 확인할 수 있는 부분을, 결과에 따라 수정 가능한 임시 문장으로 씁니다.</Step>
<Step title="확인할 질문 만들기">대상·기간·지역·지표·비교 기준이 드러나는 분석 질문을 만듭니다.</Step>
</Steps>

> 현재는 **[관찰 가능한 현재 상태]**이고, 목표는 **[관찰 가능한 목표 상태]**이다. 그 차이에는 **[작게 나눈 문제들]**이 있으며, 우리는 그중 **[데이터로 확인할 문제]**를 먼저 살펴본다.

<Callout kind="concept" title="문제를 분해하는 힘">
AI에게 큰 문제 전체를 바로 해결해 달라고 하지 않습니다. 큰 문제를 작게 나누어야 어떤 부분은 데이터로 확인하고, 어떤 부분은 규칙이나 사람의 안내로 해결하며, 어떤 부분에만 AI가 필요한지 판단할 수 있습니다.
</Callout>

<Callout kind="caution" title="아직 서비스 이름을 정하지 않습니다">처음 생각한 해결책을 증명하기 위해 데이터를 찾지 않습니다. 분석 결과가 예상과 다르면 질문·문제 정의·서비스 방향을 바꾸는 것이 좋은 탐구입니다.</Callout>

### 이 순간의 AI 활용

AI에게 해결책을 바로 요청하지 말고 검색어와 확인 질문을 넓히게 합니다.

```text
우리 팀의 관심 분야는 [분야]이고, 현재 [현상]을 문제라고 생각하고 있어.
이 생각을 확인하거나 반박할 수 있는 공공데이터 검색어를 한국어와 영어로 제안해줘.
대상·기간·지역·지표가 드러나는 분석 질문 후보도 만들어줘.
아직 해결책은 제안하지 말고, 우리가 당연하다고 가정한 부분과 먼저 확인할 점을 알려줘.
```

## STEP 2 · 공공데이터를 찾고 읽기

데이터의 규모보다 질문과의 적합성이 중요합니다.

<Steps>
<Step title="데이터 후보 세 개 찾기">공공데이터포털, 기관 통계, 국제기구 등에서 원파일을 내려받을 수 있는 자료를 찾습니다.</Step>
<Step title="후보 비교하기">제공 기관·대상·기간·지역·단위·갱신일·이용 조건·필요한 변수를 비교합니다.</Step>
<Step title="핵심 데이터 선택">질문에 가장 적합한 자료를 고르고 필요하면 두 자료를 공통 기준으로 연결합니다.</Step>
<Step title="수집 맥락 기록">누가 왜 어떤 기준으로 모았고 누구나 무엇이 빠질 수 있는지 기록합니다.</Step>
<Step title="원본 보존">원파일·출처 URL·다운로드 날짜를 남기고 분석은 사본에서 진행합니다.</Step>
</Steps>

공공데이터만으로 모든 원인을 알 수는 없습니다. 필요하면 직접 실시한 설문·인터뷰·관찰이나 신뢰할 수 있는 보고서를 보충 근거로 활용할 수 있습니다. 개인정보와 동의 문제를 먼저 확인합니다.

## STEP 3 · 전처리하고 분석하기

분석 방법은 멋있어 보이는 기술이 아니라 질문에 맞게 선택합니다.

| 알고 싶은 것 | 방법 | 주로 사용할 표현 |
| --- | --- | --- |
| 시간이 지나며 달라졌는가 | 연도·월별 집계와 추이 분석 | 선그래프 |
| 지역·집단에 차이가 있는가 | 합계·평균·비율 비교 | 막대그래프 |
| 값이 어떻게 퍼져 있는가 | 분포와 이상치 확인 | 히스토그램·상자그림 |
| 두 수치 변수가 함께 움직이는가 | 산점도와 상관계수 | 산점도 |
| 여러 변수 중 관계 후보는 무엇인가 | 상관행렬 | 히트맵 |

<Steps>
<Step title="구조 확인">행·열 수, 열 이름, 자료형, 기간과 단위를 확인합니다.</Step>
<Step title="전처리 기록">결측·중복·이상치·자료형·단위 문제를 확인하고 변경 이유와 전후 행 수를 남깁니다.</Step>
<Step title="핵심 그래프 만들기">분석 질문에 직접 답하는 그래프 두 개 이상을 선택합니다.</Step>
<Step title="관계 분석하기">적절한 수치 변수가 있다면 산점도·상관계수·히트맵을 사용하되 인과로 해석하지 않습니다.</Step>
<Step title="결과 재현하기">사용한 파일·열·필터·집계 기준으로 같은 결과를 다시 만들 수 있는지 확인합니다.</Step>
</Steps>

### 이 순간의 AI 활용

```text
첨부한 공공데이터로 [분석 질문]을 확인하려고 해.
1. 사용할 열·단위·기간을 먼저 제시해줘.
2. 결측치·중복값·이상치 처리안을 설명하고 내가 확인하기 전에는 임의로 삭제하지 마.
3. 처리 전후 행 수와 변경 내역을 표로 남겨줘.
5. 질문에 맞는 그래프를 추천하고 선택 이유를 설명해줘.
6. 코드가 필요하면 단계별로 작성하고 각 코드가 어떤 열에 무엇을 하는지 설명해줘.
7. 파일에 없는 값이나 사건은 만들지 마.
```

AI가 만든 코드를 처음부터 외워 쓸 필요는 없습니다. 그러나 어떤 파일을 불러왔고, 어떤 열을 사용했으며, 무엇을 삭제·집계하고, 그래프의 축이 무엇인지는 팀이 설명할 수 있어야 합니다.

<Callout kind="checklist" title="결과물과 함께 나도 성장했는가?">
- AI가 한 핵심 처리 과정을 팀의 말로 설명할 수 있는가?
- 결과가 이상할 때 파일·열·필터·계산 중 어디부터 확인할지 아는가?
- AI의 첫 제안에서 무엇을 수정하거나 거부했는가?
- 이번 과정에서 다음 문제에 다시 사용할 수 있는 개념을 무엇을 배웠는가?

설명할 수 없는 결과는 그대로 제출하지 않습니다. AI에게 코드와 처리 과정을 학생 수준으로 다시 설명하게 하고, 원파일과 실행 결과를 대조한 뒤 팀의 설명으로 바꿉니다.
</Callout>

## STEP 4 · 인사이트를 도출하고 문제를 다시 정의하기

그래프가 올라가거나 내려갔다는 설명만으로는 인사이트가 아닙니다. 다음 네 층을 구분합니다.

| 층 | 질문 |
| --- | --- |
| 관찰한 사실 | 데이터에서 직접 확인한 수치·차이·변화는 무엇인가? |
| 가능한 해석 | 이 현상은 누구에게 어떤 의미가 있을 수 있는가? |
| 원인 가설 | 왜 나타났다고 생각하며 무엇을 더 확인해야 하는가? |
| 서비스 기회 | 어떤 사용자의 어떤 결정·행동·불편을 도울 수 있는가? |

> 데이터에서 **[현상]**을 발견했다. 이는 **[대상 사용자]**에게 **[의미·어려움]**과 관련될 수 있다. 가능한 원인은 **[가설]**이지만 현재 자료만으로 단정할 수 없다. 따라서 우리는 **[도울 필요가 있는 구체적인 상황]**을 최종 문제로 정의한다.

### 이 순간의 AI 활용

```text
다음은 우리 팀이 원파일과 그래프에서 직접 확인한 사실이야: [사실]
1. 이 사실에서 가능한 해석과 원인 가설을 구분해줘.
2. 우리가 빠뜨린 변수와 반대 설명을 제시해줘.
3. 현재 데이터만으로 말할 수 없는 내용을 표시해줘.
5. 서비스 아이디어보다 먼저, 영향을 받는 사용자와 구체적인 상황을 질문해줘.
```

<Callout kind="concept" title="데이터는 문제를 대신 결정하지 않습니다">데이터는 반복되는 현상과 차이를 보여주지만 그 현상이 왜 중요한지, 누구를 도와야 하는지, 어떤 가치를 우선할지는 사람이 맥락 속에서 판단합니다.</Callout>

## STEP 5 · 데이터의 역할을 나누고 AI 필요성을 판단하기

공공데이터를 분석했다고 해서 반드시 그 자료로 AI를 학습시키는 것은 아닙니다.

| 데이터의 역할 | 확인할 질문 |
| --- | --- |
| 문제 확인 데이터 | 이 서비스가 필요한 현상을 보여주는가? |
| AI 학습 데이터 | AI가 패턴을 배우려면 어떤 정답·라벨·사례가 필요한가? |
| 서비스 입력 데이터 | 사용자가 이용할 때 무엇을 입력하거나 제공하는가? |
| 서비스 운영 데이터 | 추천·검색·안내에 어떤 최신 정보가 필요한가? |
| 평가 데이터 | 결과가 정확하고 공정한지 무엇으로 시험하는가? |

서비스에는 공공데이터, 팀이 직접 수집한 자료, 사용자가 입력한 정보, 이미지·글·음성 같은 비정형 데이터가 함께 필요할 수 있습니다. 실제로 구할 수 있는지, 수집 동의가 필요한지, 누구의 정보가 빠질 수 있는지 확인합니다.

AI를 넣기 전에 묻습니다.

1. 규칙·검색·안내·체크리스트가 더 단순하고 안전하지 않은가?
2. 분류·예측·추천·생성·번역·요약·대화 중 어떤 역할이 문제 해결에 꼭 필요한가?
3. AI가 틀리면 누가 어떤 피해를 입는가?
5. 필요한 학습·운영·평가 데이터를 현실적으로 구할 수 있는가?
6. 사람이 확인하고 결과에 이의를 제기할 수 있는가?

AI가 필요하지 않다는 결론도 좋은 문제 해결입니다.

## STEP 6 · 서비스 시나리오 설계하기

```text
사용자 상황 → 입력 데이터 → AI가 하는 일 → 서비스 출력
→ 사람이 확인·선택하는 일 → 기대 변화
```

| 설계 요소 | 반드시 답할 질문 |
| --- | --- |
| 사용자 | 누가 언제 사용하는가? |
| 입력 | 무엇을 입력받고 어디에서 얻는가? |
| AI의 역할 | 어떤 패턴을 찾아 무엇을 분류·예측·추천·생성하는가? |
| 출력 | 사용자는 어떤 결과를 보거나 듣는가? |
| 사람의 역할 | 무엇을 확인·수정·선택하고 누가 최종 책임지는가? |
| 안전장치 | 오류·편향·개인정보·저작권·악용을 어떻게 줄이는가? |

김현철 교수님의 설명처럼 AI는 빠른 분석과 패턴 인식에 강한 엔진이 될 수 있습니다. 그러나 방향과 목적을 정하고, 데이터 밖의 맥락을 읽고, 직관적 통찰로 결과를 검증하며, 가치와 책임을 판단하는 운전자는 사람입니다.

### 이 순간의 AI 활용

```text
우리의 최종 문제 정의는 [문제]이고 근거는 [분석 결과]야.
현재 해결 방법과 한계는 [내용]이야.
AI가 맡을 수 있는 역할 후보를 제안하되, 규칙 기반 방법으로 충분한 기능은 구분해줘.
각 후보에 필요한 학습·입력·운영·평가 데이터와 확보 가능성을 표로 정리해줘.
마지막에 오류가 났을 때 피해, 사람이 확인할 지점, 개인정보·편향 위험을 비판적으로 검토해줘.
```

## STEP 7 · 피드백으로 수정하고 제안하기

최종 발표 전에 다른 팀은 다음 역할로 기획안을 검토합니다.

- 데이터 검증자: 분석 결과와 주장 사이에 비약이 없는가?
- 사용자 대변인: 실제 사용자의 상황과 필요가 반영되었는가?
- 안전 검토자: 오류·편향·개인정보·악용 가능성과 사람의 개입이 설계되었는가?

피드백을 받은 뒤 문제 정의·기능·데이터·AI 역할 중 한 가지 이상을 수정하고 전후 변화를 기록합니다.

## 최종 기획안 구성

수상작의 좋은 구조를 참고하되 우리 프로젝트의 판단 과정을 더 분명하게 보여줍니다.

1. 프로젝트명과 팀의 관심 분야
2. 현재 상태·목표 상태와 작게 분해한 문제
3. 처음의 문제 가설과 대상 사용자
5. 활용 공공데이터 정보와 선택 이유
5. 데이터 구조·단위·기간과 전처리 내역
6. 핵심 그래프와 분석 결과
7. 관찰한 사실·가능한 해석·원인 가설·한계
8. 분석 후 수정한 최종 문제 정의
9. 기존 해결 방법과 남은 빈틈
10. AI 필요성 판단과 다른 해결 방법 비교
11. 문제 확인·학습·입력·운영·평가 데이터 구분
12. AI와 사람의 역할
13. 서비스 이용 시나리오
14. 독창성·차별점과 기대 효과
15. 오류·편향·개인정보·저작권·악용 위험과 안전장치
16. 생성형 AI 활용 명세와 사람이 검증·수정한 내용
17. 피드백 전후 변화와 최종 판단

<Callout kind="rubric" title="프로젝트 완료 기준">
- 현재 상태와 목표 상태를 구분하고 큰 문제를 확인 가능한 작은 문제로 나누었다.
- 관심 분야의 문제 가설을 공공데이터로 확인하거나 수정했다.
- 원자료의 출처·기간·단위·수집 맥락을 기록했다.
- 전처리와 분석 과정을 다른 사람이 다시 확인할 수 있다.
- 그래프의 사실, 해석, 원인 가설을 구분했다.
- 상관관계를 인과관계로 단정하지 않았다.
- 분석 결과가 최종 문제 정의와 서비스 필요성에 연결된다.
- 문제 확인 데이터와 AI 학습·입력·운영·평가 데이터를 구분했다.
- AI가 필요한 이유와 더 단순한 해결 방법을 비교했다.
- AI의 역할과 사람의 판단·책임을 구분했다.
- 생성형 AI의 결과를 원파일·원자료와 비교해 검증했다.
- AI가 만든 코드·분석·제안의 핵심을 팀의 말로 설명할 수 있다.
- 피드백을 받아 기획안을 실제로 수정했다.
- AI를 사용해 결과물뿐 아니라 팀의 이해와 문제 해결 능력도 성장했다는 근거가 있다.
</Callout>

<Callout kind="concept" title="발표에서 가장 듣고 싶은 문장">“우리는 이 서비스를 생각해냈습니다”가 아니라 **“이 데이터를 분석해 이런 현상을 발견했고, 그래서 이 사용자의 문제를 이렇게 다시 정의했습니다. AI에는 이 역할만 맡기고 사람은 이 판단과 책임을 가집니다.”**라고 설명합니다.</Callout>
