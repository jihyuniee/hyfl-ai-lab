7. DATA TO WEB APP

데이터를 살펴보면 익숙한 상황에서도 새로운 질문이 생깁니다. 이 프로젝트에서는 우리 팀이 해결하고 싶은 문제를 찾고, 자료에서 얻은 발견을 사람들이 직접 활용할 수 있는 웹 서비스로 만들어 갑니다.

문제 정의 ↔ 데이터 탐색 → 분석·인사이트 → 설계 → 제작 → 검증·개선 → 공유

탐색과 제작은 여러 번 오갈 수 있습니다. 새로운 자료나 사용 경험을 만날 때마다 질문과 기능을 더 정확하게 다듬어 봅시다.

📚 한 학습지에 이어 쓰기

공통 실습에서 시작한 프로젝트 통합 학습지를 끝까지 사용합니다. 팀이 이야기하고 시도한 뒤, 중요한 발견과 결정만 해당 부분에 기록합니다. 생각이 달라진 곳에는 날짜와 이유를 덧붙입니다.

1. 문제를 발견하고 구체화하기

섹션 제목: “1. 문제를 발견하고 구체화하기”

프로젝트의 출발점은 사용자의 상황을 이해하는 일입니다. 어떤 앱을 만들지보다 누가 무엇을 하려고 하며, 어느 순간에 어려움을 겪는지부터 살펴봅시다.

실제 장면에서 시작하기

섹션 제목: “실제 장면에서 시작하기”

팀원 각자가 떠올린 상황을 이야기하고, 함께 더 알아보고 싶은 문제를 고릅니다. 사용자가 지금 하는 일을 직접 따라가 보거나, 그 일을 해 본 사람에게 경험을 물어봅니다.

생각할 질문살펴볼 내용
누구의 상황인가?사용할 사람과 이용하는 장소·시간
무엇을 하려는가?사용자가 이루려는 목적과 필요한 정보
지금은 어떻게 하는가?현재 방법과 순서, 이미 도움을 주는 도구
어디에서 불편한가?반복하는 일, 찾기 어려운 정보, 혼동하는 지점
무엇이 달라지면 좋을까?사용자가 더 쉽게 할 수 있기를 바라는 행동

대화에서 들은 말과 직접 관찰한 내용은 확인한 사실로 적습니다. 팀이 추측한 이유는 더 살펴볼 가정으로 남깁니다. 이 구분은 다음에 어떤 자료를 찾아야 할지 알려 줍니다.

문제를 한 문장으로 쓰기

섹션 제목: “문제를 한 문장으로 쓰기”

[사용자]는 [상황]에서 [하려는 일]을 하고 싶지만 [현재의 어려움]을 겪는다. 우리는 [도울 부분]을 살펴보려고 한다.

이 문장은 탐구의 첫 출발점입니다. 모든 내용을 처음부터 확정하려 하기보다 지금 이해한 상황을 표현해 봅시다. 이어서 데이터로 확인하고 싶은 질문을 적습니다. 대상·기간·항목·비교 기준이 구체적일수록 찾을 자료가 분명해집니다.

문제와 질문을 다듬는 프롬프트 {{빨간 부분}}을 우리 팀의 내용으로 바꾸세요.
프롬프트 구조와 각 부분이 필요한 이유 보기

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

과업·필수 기능은 만들어야 할 결과와 빠뜨리면 안 되는 동작을 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

우리 팀이 살펴보는 상황은 다음과 같아.
사용자와 상황: [내용]
현재 사용하는 방법과 불편: [내용]
직접 확인한 사실: [내용]
아직 확인할 가정: [내용]

지금은 문제와 탐구 질문을 다듬는 단계야.
우리 설명에서 더 알아볼 점을 질문해줘.
자료로 확인할 수 있는 질문을 제안하고, 각 질문에 필요한 항목과 비교 기준을 설명해줘.
처음 생각과 다른 설명도 함께 검토해줘. 최종 질문은 우리가 정할게.

탐색하면서 문제 다시 보기

섹션 제목: “탐색하면서 문제 다시 보기”

자료를 찾다 보면 처음 생각한 원인과 다른 점이 보이거나, 필요한 항목이 충분하지 않을 수 있습니다. 그때는 사용자, 문제의 범위, 탐구 질문 중 무엇을 바꾸면 좋을지 다시 이야기합니다.

처음의 문제 → 새롭게 확인한 내용 → 바꾼 질문과 이유를 같은 학습지에 이어 씁니다. 질문을 수정하는 과정도 문제를 더 잘 이해해 가는 탐구입니다.

학습지 1에 현재의 문제 정의와 확인할 질문을 기록하고, 자료를 살펴보며 계속 보완합니다.

2. 데이터를 탐색하고 선택하기

섹션 제목: “2. 데이터를 탐색하고 선택하기”

문제를 정의하면서 자료를 함께 찾아봅니다. 공공데이터 탐색에서 살펴본 포털을 출발점으로 삼고, 문제에 더 적합한 학습 자료나 직접 기록한 자료도 검토할 수 있습니다.

실제 내용을 열어 보기

섹션 제목: “실제 내용을 열어 보기”

자료 후보를 찾으면 일부 기록을 직접 읽어 봅니다. 제목뿐 아니라 한 행이나 문장이 무엇을 뜻하는지, 어떤 항목이 들어 있는지, 어떤 기간과 대상을 다루는지 확인합니다.

확인할 내용선택에 도움이 되는 질문
출처와 작성 방식누가 어떤 목적으로 만들었을까?
범위와 기준 시점우리 질문의 대상·기간과 맞을까?
항목과 단위무엇을 비교하거나 계산할 수 있을까?
자료의 상태빈 값·중복·표기 차이는 어떻게 살펴볼까?
이용 조건수업, AI 입력, 온라인 공유에 각각 어느 범위까지 사용할 수 있을까?

질문에 맞는 자료를 선택한 뒤 원본과 분석용 사본을 구분해 보관합니다. 파일명, 원문 주소, 확인일과 조회 조건을 함께 적어 두면 결과를 다시 확인하기 쉽습니다.

직접 자료를 기록할 때는 기록 방법·기간·분류 기준을 먼저 정합니다. 본인의 연습 기록처럼 앱 제작 전에도 얻을 수 있는 자료로 탐구를 시작할 수 있습니다.

자료에 맞게 질문 조정하기

섹션 제목: “자료에 맞게 질문 조정하기”

원하는 항목이 부족하면 다른 자료를 찾아보거나 질문의 범위를 바꿉니다. 분석에 사용하는 자료와 앱에서 정보를 보여 주는 자료가 서로 다를 수도 있습니다. 각 자료가 맡는 역할을 설명해 봅시다.

자료를 공유할 때는 필요한 항목과 공개할 수 있는 범위를 정합니다. 개인 기록은 수업에서 정한 범위 안에서 다루고, 공개 화면에는 확인된 집계 결과나 시연용 자료를 사용합니다. 시연용 가상 자료에는 그 성격을 표시합니다.

학습지 2에 자료의 선택 이유와 분석 범위를 적습니다. 탐구 질문이 달라졌다면 학습지 1의 문제 정의도 함께 고칩니다.

3. 분석에서 인사이트로

섹션 제목: “3. 분석에서 인사이트로”

데이터 분석은 질문에 답하기 위해 자료를 정리하고 비교하는 과정입니다. 개수를 세거나 비율을 비교할 수도 있고, 문장이나 사례를 일정한 기준으로 분류할 수도 있습니다.

분석 기준 세우기

섹션 제목: “분석 기준 세우기”

먼저 사용할 범위를 정하고, 날짜·단위·표기 차이와 중복을 살펴봅니다. 빈 값은 확인이 필요한 항목으로 표시하고, 분석에 포함하거나 제외한 기준을 남깁니다.

같은 조건에서 비교하고 있는지 확인한 뒤 질문에 맞는 표나 그래프를 만듭니다. 비율은 분자와 분모를, 평균은 포함한 기록을, 범주 비교는 분류 기준과 근거 문장을 설명할 수 있어야 합니다.

분석 기준과 결과를 확인하는 프롬프트 {{빨간 부분}}을 우리 팀의 내용으로 바꾸세요.
프롬프트 구조와 각 부분이 필요한 이유 보기

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

과업·필수 기능은 만들어야 할 결과와 빠뜨리면 안 되는 동작을 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

첨부한 실제 자료로 [탐구 질문]을 살펴보려고 해.
1. 읽은 파일, 한 기록의 의미, 사용할 항목과 단위를 먼저 확인해줘.
2. 범위·분류·비교 기준과 빈 값·중복을 처리할 방법을 설명해줘.
3. 질문에 맞는 표나 그래프를 만들고, 원자료와 계산·분류 결과를 구분해줘.
4. 내가 다시 확인할 수 있도록 계산식 또는 근거 문장을 보여줘.
5. 확인한 사실, 가능한 해석, 추가로 필요한 자료를 나눠 설명해줘.
자료를 읽기 어렵거나 정보가 부족한 부분은 확인 필요로 표시해줘.

AI가 만든 결과에서 대표적인 값이나 문장을 골라 원자료와 직접 대조합니다. 어떤 기록과 계산을 사용했는지 설명하면서 결과를 읽어 봅시다.

발견의 의미 생각하기

섹션 제목: “발견의 의미 생각하기”

인사이트는 분석한 내용이 사용자의 상황과 해결 방법에 어떤 의미가 있는지 판단한 결과입니다. 다음 세 문장을 연결해 봅니다.

자료에서 [확인한 사실]을 발견했다.
이 사실은 [사용자 상황]에서 [의미]가 있다고 생각한다.
그래서 [필요한 정보·기능·처리 기준]을 설계하려고 한다.

확인한 사실, 가능한 해석, 추가로 확인할 내용을 나누어 적습니다. 처음의 예상과 다른 결과나 예외에도 주목합니다. 차이가 생긴 이유와 서비스의 효과는 추가 자료나 사용 경험으로 더 살펴볼 수 있습니다.

학습지 3에 핵심 표·그래프와 인사이트를 남깁니다. 분석 때문에 달라진 문제나 기능이 있다면 앞의 기록에 연결합니다.

4. 서비스와 화면 설계하기

섹션 제목: “4. 서비스와 화면 설계하기”

인사이트를 바탕으로 사용자가 실제로 할 일을 설계합니다. 먼저 앱을 열어 원하는 결과를 얻기까지의 흐름을 말로 설명하고, 종이나 화면에 배치해 봅시다.

시작 → 입력·조건 선택 → 처리 → 결과 확인 → 다음 행동

기능을 데이터와 연결하기

섹션 제목: “기능을 데이터와 연결하기”
설계 요소정할 내용
기능의 목적어떤 불편을 줄이며, 어떤 발견과 연결되는가?
입력사용자가 입력·선택하는 값과 불러올 자료
처리필터·검색·분류·계산에 적용할 기준
출력보여 줄 결과, 단위, 근거, 다음 행동
확인 방법어떤 입력에서 어떤 결과가 나와야 하는가?

가장 먼저 완성할 사용 흐름을 정하고 필요한 기능을 순서대로 연결합니다. 프로젝트가 발전하면 범위도 넓힐 수 있습니다. 기능을 추가할 때는 사용자에게 필요한 이유와 사용할 자료를 함께 확인합니다.

화면의 기본 구성

섹션 제목: “화면의 기본 구성”

앱의 목적을 알 수 있는 제목과 설명, 입력·선택 영역, 결과 영역, 출처와 도움말을 배치합니다. 결과가 있는 화면뿐 아니라 처음 들어온 화면, 자료를 읽는 동안, 검색 결과가 비어 있을 때의 모습도 생각해 봅니다.
