7. DATA TO WEB APP

이 단원은 이미 배운 내용을 하나로 연결하는 팀 프로젝트입니다. 여러분은 인공지능의 기본 원리, 머신러닝의 학습 과정, Teachable Machine 실습, 공공데이터 탐색을 경험했습니다. 이제부터는 각자의 관심 분야를 공공데이터로 검토하고, 분석에서 얻은 인사이트를 실제 웹앱 또는 AI 서비스 프로토타입으로 구현합니다.

최종 산출물은 보고서가 아니라 데이터 근거가 있는 작동 결과물입니다.

이 순서는 고정된 직선이 아닙니다. 데이터를 찾다가 문제를 좁힐 수 있고, 분석 결과가 예상과 다르면 질문을 바꿀 수 있습니다. 좋은 탐구는 처음 생각을 끝까지 고집하는 것이 아니라, 확인한 사실 때문에 더 정확해지는 과정입니다.

🎯 이번 프로젝트의 미션

각자의 관심 분야에서 출발해 공공데이터로 확인 가능한 질문을 만들고, 분석 결과를 바탕으로 사람들이 사용할 수 있는 웹앱 또는 AI 서비스 프로토타입을 구현합니다.

⚠️ AI는 팀장이 아니라 도구입니다

프로젝트의 방향은 사람이 먼저 정합니다. 먼저 각자 생각하고, 팀에서 의논하고, 그다음 생성형 AI를 검색·정리·분석·코딩 보조 도구로 사용합니다. AI가 만든 답을 그대로 맡기면 남는 것이 적습니다. 중요한 판단과 검증은 팀이 책임집니다.

1. 이미 가진 관심을 탐구 질문으로 바꾸기

섹션 제목: “1. 이미 가진 관심을 탐구 질문으로 바꾸기”

여러분은 이미 관심 분야가 있습니다. 진로, 사회 문제, 문화, 환경, 학교생활, 기술, 언어, 미디어, 경제, 복지, 교통처럼 출발점은 다양할 수 있습니다. 중요한 것은 관심 자체가 아니라 그 관심을 확인 가능한 질문으로 바꾸는 일입니다.

출발점탐구 질문으로 바꾸는 기준
내가 관심 있는 분야어떤 현상이나 문제가 실제로 있는가?
내가 중요하다고 생각하는 주장어떤 자료로 확인하거나 반박할 수 있는가?
내가 만들고 싶은 서비스어떤 사용자에게 어떤 정보가 필요한가?
내가 예상한 원인데이터만으로 확인 가능한가, 추가 조사가 필요한가?
내가 바꾸고 싶은 상황현재 상태와 목표 상태를 어떻게 비교할 수 있는가?

처음부터 완벽한 문제를 찾으려 하지 않습니다. 관심 분야를 말로 설명한 뒤, 공공데이터와 공식 자료로 확인할 수 있는 부분을 찾습니다.

⚠️ AI는 출처가 아닙니다

생성형 AI의 답변은 탐색과 정리를 돕는 초안입니다. 통계 수치, 정책명, 기관명, 사례, 데이터 항목은 반드시 원자료나 공식 출처에서 다시 확인해야 합니다.

2. 필요한 배경지식 확인하기

섹션 제목: “2. 필요한 배경지식 확인하기”

도메인 지식은 어떤 분야를 이해하는 데 필요한 배경지식입니다. 모든 팀이 처음부터 긴 조사 보고서를 만들 필요는 없습니다. 관심 주제를 말하고 문제를 정하는 과정에서 모르는 용어, 관련 기관, 제도, 이해관계자, 조심할 오해가 나오면 필요한 만큼 찾아봅니다.

중요한 순서는 내 생각 → 팀 의논 → 필요한 배경지식 확인 → AI 도움 → 원자료 검증입니다. AI가 정리한 배경지식은 초안일 뿐이며, 통계 수치·정책명·기관명·사례는 반드시 공식 자료에서 다시 확인합니다.

필요한 배경지식 확인 프롬프트 {{빨간 부분}}을 우리 팀의 내용으로 바꾸세요.

다음 형식으로 답해줘.
1. 핵심 용어와 쉬운 설명
2. 관련된 이해관계자: 영향을 받는 사람, 관리하는 기관, 서비스를 사용할 사람
3. 실제 문제 상황 또는 정책·사회적 맥락
4. 공공데이터나 공식 자료를 찾을 때 사용할 검색어
5. 데이터로 확인 가능한 질문과 데이터만으로 단정할 수 없는 질문
6. 쉽게 생길 수 있는 오해나 편견
7. 반드시 공식 출처로 다시 확인해야 할 내용

확실하지 않은 내용은 단정하지 말고 확인 필요라고 표시해줘. AI의 답변은 출처가 아니라 탐색을 돕는 초안이라는 점을 지켜줘.

섹션 제목: “3. 문제 정의하기”

4. 처리 로직 만들기필터, 계산, 검색, 분류 기준을 코드로 표현한다.
5. 원자료와 비교하기같은 조건에서 원자료의 값과 앱 결과를 대조한다.
6. 오류와 빈 결과 처리잘못된 입력, 데이터 없음, 파일 오류를 안내한다.
7. UI 다듬기사용자가 이해하기 쉬운 문장과 배치를 적용한다.

기본 구현은 HTML, CSS, JavaScript로 시작합니다. 팀의 질문에 필요하고 실행 환경이 준비되어 있다면 Streamlit, API, 지도, 차트 라이브러리 등을 선택 확장할 수 있습니다.

오류를 AI에게 설명하는 방법

섹션 제목: “오류를 AI에게 설명하는 방법”

코드를 공개 저장소에 올릴 때는 API 키, 개인 식별 정보, 비공개 자료가 포함되지 않았는지 확인합니다.

9. 협업과 토론

섹션 제목: “9. 협업과 토론”

이 프로젝트는 역할을 나누되 중요한 판단은 함께 해야 합니다. 도메인 탐색 담당, 데이터 담당, 분석 담당, 구현 담당, 발표 담당이 따로 있어도 문제 정의와 인사이트, 서비스 방향은 팀 전체가 설명할 수 있어야 합니다.

협업 장면함께 결정할 것
도메인 탐색 후어떤 문제를 볼 만한가? 어떤 오해를 피해야 하는가?
데이터 선택 후이 자료로 우리의 질문에 답할 수 있는가?
분석 후결과가 예상과 같았는가? 문제를 수정해야 하는가?
설계 후사용자가 실제로 쓸 이유가 있는가?
구현 후원자료와 결과가 맞는가? 화면이 이해하기 쉬운가?
발표 전사실, 해석, 제안이 구분되어 있는가?

팀 회의에서는 AI에게 바로 결론을 묻기 전에 각자 먼저 판단을 말합니다. 그다음 AI를 사용해 빠진 관점, 반례, 검증 방법을 찾습니다.

10. 검증하고 개선하기

섹션 제목: “10. 검증하고 개선하기”

완성도는 화면의 화려함보다 검증에서 드러납니다. 앱이 실제 데이터와 맞는지, 사용자가 원하는 일을 할 수 있는지 확인합니다.

데이터 검증

섹션 제목: “데이터 검증”
확인 항목방법
원자료 대조원자료에서 직접 계산한 값과 앱 결과를 비교한다.
기준 확인기간, 지역, 단위, 필터 기준이 화면과 코드에서 일치하는지 본다.
예외 입력결과 없음, 잘못된 입력, 빠진 데이터 상황을 확인한다.
반복 실행같은 조건에서 같은 결과가 나오는지 본다.

사용자 검증

섹션 제목: “사용자 검증”

다른 팀에게 앱을 사용하게 하고, 어디에서 막히는지 관찰합니다. 설명이 부족한 부분, 결과를 오해할 수 있는 부분, 더 필요한 기능을 기록한 뒤 수정합니다.

검증 결과 때문에 문제 정의, 데이터 범위, 기능이 바뀔 수 있습니다. 그것은 프로젝트가 흔들린 것이 아니라 더 정확해진 것입니다.

11. 발표하기

섹션 제목: “11. 발표하기”

발표는 앱 소개가 아니라 탐구의 흐름을 설명하는 시간입니다. 문제, 데이터, 분석, 인사이트, 설계, 구현, 검증이 하나로 이어져야 합니다.

3분 발표 구성 프롬프트 {{빨간 부분}}을 우리 팀의 내용으로 바꾸세요.
프롬프트 구조와 각 부분이 필요한 이유 보기

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

과업·필수 기능은 만들어야 할 결과와 빠뜨리면 안 되는 동작을 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

우리 팀의 프로젝트 발표를 준비하려고 한다.
프로젝트 내용: [문제 정의, 데이터, 분석, 인사이트, 서비스 설계, 구현, 검증]
발표 시간: 3분

다음 흐름으로 발표 대본과 슬라이드 구성을 제안해줘.
1. 우리 팀의 관심 분야와 문제를 발견한 이유
2. 필요한 배경지식과 공공데이터 수집 과정
3. 분석 결과와 핵심 인사이트
4. 인사이트가 서비스 기능으로 연결된 과정
5. 구현 화면과 실제 시연 순서
6. 원자료 대조 또는 사용자 테스트로 확인한 내용
7. 한계와 다음 개선 방향
8. AI를 활용하며 팀이 새롭게 할 수 있게 된 것

데이터로 확인한 사실, 팀의 해석, 앞으로 확인해야 할 내용을 구분해줘. 근거 없이 효과를 과장하지 말아줘.

발표에서 반드시 구분할 것

섹션 제목: “발표에서 반드시 구분할 것”
구분발표 문장 예시
사실이 자료에서는 2024년 기준으로 이러한 값이 확인되었습니다.
해석우리는 이 결과가 사용자 상황에서 이런 의미를 가진다고 보았습니다.
한계이 자료만으로 원인을 단정할 수는 없습니다.
구현그래서 앱에서는 이 조건을 선택하면 이 결과를 보여 주도록 만들었습니다.
개선사용자 테스트 후 이 부분을 더 쉽게 바꾸었습니다.

최종 발표에는 실제 화면 시연이 포함되어야 합니다. 실행이 어려운 경우에도 코드, 화면, 데이터, 테스트 결과를 통해 최소 기능이 어떻게 작동하는지 설명할 수 있어야 합니다.
