이 페이지는 **지도 기능이 필요한 팀을 위한 선택 도움말**입니다. 지도 서비스는 정해져 있지 않습니다. 우리 사용자와 자료, 개발 환경에 맞는 것을 비교해 선택합니다.

## 먼저 필요한 기능과 지도 서비스 고르기

**지도 표시, 장소 검색, 길찾기는 서로 다른 기능입니다.** 지도가 보인다고 주변 장소를 검색하거나 이동 경로를 계산할 수 있는 것은 아닙니다. 우리 자료에서 이름을 찾아 마커를 고르는 기능과 외부 서비스에서 새 장소를 검색하는 기능도 구분하세요. 필요한 기능만 선택하고, 별도 서비스가 필요한지 확인합니다.

| 비교할 점 | 확인할 질문 |
| --- | --- |
| 장소 정보 | 우리 지역의 장소·주소·도로 정보가 목적에 맞고 충분한가? |
| 필요한 기능 | 지도·마커, 우리 자료의 필터, 외부 장소 검색, 길찾기 중 무엇을 지원하며 무엇을 따로 연결해야 하는가? |
| 개발 환경과 설정 | 현재 앱에서 사용할 수 있는가? 계정·키·도메인·추가 서버 설정이 필요한가? |
| 이용 조건 | 비용·호출 제한·출처 표시·공개 이용 조건을 지킬 수 있는가? |

카카오 지도와 **OpenStreetMap 기반 지도 구성** 등을 후보로 비교합니다. **OpenStreetMap은 지도 데이터이며, Leaflet 같은 화면 표시 도구나 배경지도 이미지를 제공하는 타일 서비스와는 다릅니다.** OpenStreetMap 데이터를 쓰더라도 선택한 타일·장소 검색·길찾기 서비스의 설정과 이용 조건을 각각 확인합니다. 무료·무제한·키 불필요라고 한꺼번에 가정하지 않습니다.

아래 요청문으로 후보 **두 가지의 장단점과 설정 사항**을 확인한 뒤 팀이 선택하세요. AI가 바로 구현하려 하면 비교 결과부터 확인하고, 선택한 서비스와 기능을 답한 다음 구현을 진행합니다.

### 1. 지도를 넣을 내 파일 준비하기

우리 팀 상황에 맞게 **A 또는 B 중 하나**로 시작합니다. 두 경우 모두 키는 아직 넣지 않고 `YOUR_JAVASCRIPT_KEY`로 남겨 둡니다.

### A. 이미 만드는 프로젝트가 있다면

GitHub의 파일을 읽고 수정할 수 있는 AI 환경을 연결한 팀은 **[참고: GitHub의 내 코드를 GPT와 수정하기 →](/hyfl-ai-lab/data/github-ai/)**의 요청문을 사용합니다. 연결된 저장소의 최신 파일을 읽게 하고, 기존 기능을 유지하면서 지도 기능을 추가하세요. 아래는 파일을 직접 첨부하는 순서입니다.

1. 현재 정상 작동하는 파일을 별도 폴더에 복사해 원본을 보관합니다.
2. AI에게 **현재 프로젝트 파일**을 첨부합니다. HTML이 CSS·JavaScript 파일을 따로 불러온다면 관련 파일도 함께 제공합니다. 사본에 실제 키가 들어 있다면 자리표시자로 바꿉니다.
3. 아래 요청의 빨간 부분을 우리 프로젝트에 맞게 고쳐 전달합니다. **기존 화면과 기능을 유지하면서 지도 영역만 추가**하도록 요청합니다.
4. 수정본을 확인하고 기존 프로젝트의 파일 구조와 이름에 맞게 적용합니다. 이전 버튼·입력·목록도 작동하는지 눌러 봅니다.

현재 프로젝트의 파일 구조와 기능을 유지하며 **지도 영역, SDK 로딩 코드, 가상 마커 기능**을 추가합니다. AI가 현재 코드를 확인하도록 파일을 첨부하거나 저장소를 연결합니다.

### B. 아직 프로젝트가 없다면

아래 **index.html 다운로드**로 시작 파일을 받습니다. 배경 지도와 가상 연습 위치 3개를 표시하는 코드가 들어 있습니다. **키 자리표시자를 유지한 채 2단계에서 배포 주소를 만듭니다.**

<MapStarter />

1. 내려받은 파일을 코드 편집기 또는 메모장에서 엽니다. 브라우저에 열린 화면을 편집하는 것이 아니라 **HTML 파일의 코드**를 수정합니다.
2. 파일 이름이 **`index.html`**인지 확인합니다. 다른 이름으로 내려받았다면 바꿉니다.
3. 코드를 복사해서 새 파일을 만들었다면 메모장의 **다른 이름으로 저장 → 파일 형식: 모든 파일 → 인코딩: UTF-8**을 선택하고 `index.html`로 저장합니다. `index.html.txt`로 저장되지 않았는지 확인합니다. Mac 텍스트 편집기를 쓴다면 일반 텍스트로 저장합니다.
4. `YOUR_JAVASCRIPT_KEY`가 그대로 있는 상태로 저장합니다. 지금은 지도가 안 보여도 됩니다.

### 2. 내 웹앱을 배포하고 실제 주소 확인하기

이미 배포한 프로젝트라면 **기존 배포 방법으로 수정본을 올리고 실제 웹앱 주소**를 엽니다. 새 `index.html`로 시작하는 팀은 다음 순서로 GitHub Pages 주소를 만듭니다.

1. GitHub의 **+ → New repository**에서 공개 가능한 연습용 **Public** 저장소와 README를 만듭니다.
2. **Add file → Upload files**로 `index.html`을 저장소 맨 위에 올리고 **Commit changes**를 누릅니다.
3. **Settings → Pages → Build and deployment → Source**를 **Deploy from a branch**로 선택합니다.
4. **Branch: main / (root)**를 선택하고 **Save**합니다. 파일을 올린 브랜치가 다른 이름이면 그 브랜치를 선택합니다.
5. 배포가 끝나면 **Visit site**로 웹앱을 엽니다. 아직 열리지 않으면 **Actions**의 배포 상태를 확인합니다.

자세한 절차는 [교과서의 GitHub 배포 안내](/hyfl-ai-lab/project1/#github로-웹페이지-배포하기)를 참고하세요. 첫 배포에서 **키 입력 안내와 지도 영역**, 웹앱 주소를 확인합니다.

브라우저 주소창에서 **내 웹앱의 실제 주소**를 복사합니다. GitHub 저장소의 코드 화면 주소나 AI 미리보기 주소와 구분하세요.

| 실제로 지도가 실행될 주소 예시 | 카카오에 등록할 SDK 도메인 |
| --- | --- |
| `https://my-team.github.io/our-map/` | `https://my-team.github.io` |
| `https://my-team-map.vercel.app/` | `https://my-team-map.vercel.app` |
| `http://localhost:3000/index.html` | `http://localhost:3000` |

**표의 예시를 자신의 배포 주소로 바꿔 확인합니다.** 등록값에는 프로토콜과 호스트를 쓰고, `/our-map/` 같은 뒤의 경로는 뺍니다. localhost를 사용하면 실제 포트도 포함합니다. Vercel은 지도를 실행할 배포 주소를 기준으로 설정합니다.

**직접 확인:** 내 웹앱이 열리는 주소와 그 주소에서 뽑은 SDK 도메인을 구분해 적었습니다.

### 3. 카카오 앱을 켜고 내 도메인 등록하기

1. [카카오디벨로퍼스](https://developers.kakao.com)에 카카오 계정으로 로그인합니다. 처음이면 개발자 등록을 진행합니다.
2. **앱**에서 사용할 앱을 선택합니다. 아직 없다면 이름 등 필수 정보를 입력해 만듭니다.
3. 그 앱의 **카카오맵 → 사용 설정 → 상태**를 **ON**으로 바꿉니다.
4. 같은 앱에서 **앱 설정 → 앱 → 플랫폼 키 → JavaScript 키**를 선택합니다.
5. 해당 키의 **JavaScript SDK 도메인**에 2단계에서 확인한 **내 웹앱의 도메인**을 추가하고 저장합니다.
6. 방금 설정한 **JavaScript 키**를 복사합니다. 다음 단계에서 내 코드에 넣습니다.

<Callout kind="caution" title="키 복사와 도메인 등록에 더해, 사용 설정 ON을 확인하세요">
<strong>카카오맵 → 사용 설정 → ON</strong>은 별도 설정입니다. <code>disabled OPEN_MAP_AND_LOCAL service</code> 응답이 나오면, 입력한 키가 속한 앱에서 이 설정부터 확인합니다.
</Callout>

**선택한 JavaScript 키의 SDK 도메인**에 우리 팀 지도가 실행되는 도메인을 등록합니다. 설정 위치는 [공식 웹 준비 안내](https://apis.map.kakao.com/web/guide/)와 [키·도메인 설정](https://developers.kakao.com/docs/ko/app-setting/app)에서 확인합니다.

앱 정보의 **카카오맵 무료 쿼터** 표시와 **통계 → 쿼터**에서 이용량을 확인합니다. 새로 활성화하는 경우 개발자 계정에서 처음 카카오맵 API를 활성화한 앱에 무료 쿼터가 제공됩니다. 추가 앱과 제공량 초과 사용의 조건은 [공식 이용 안내](https://developers.kakao.com/docs/ko/kakaomap/common)에서 확인합니다.

**직접 확인:** 사용할 앱은 카카오맵 ON이며, 그 앱의 JavaScript 키에 내 도메인이 등록되어 있습니다.

### 4. 내 파일의 키 한 줄을 바꾸고 다시 배포하기

1. 코드 편집기에서 **1단계의 내 파일**을 엽니다. 찾기 기능으로 `YOUR_JAVASCRIPT_KEY`를 찾습니다.
2. 시작 예제라면 **파일 아래 `<script>` 안의 `const javascriptKey` 줄**을 찾습니다. 기존 프로젝트라면 지도 초기화 코드가 있는 파일에서 같은 설정 줄을 찾습니다. 아래 줄의 따옴표 안 자리표시자만 복사한 JavaScript 키로 바꾸고, 따옴표와 세미콜론은 유지합니다.

~~~js
const javascriptKey = 'YOUR_JAVASCRIPT_KEY';
~~~

3. 파일을 저장합니다. JavaScript가 별도 파일이라면 그 코드가 들어 있는 파일을 수정합니다.
4. **같은 프로젝트의 같은 파일 위치**에 수정본을 올립니다. GitHub Pages라면 기존 `index.html`을 새 내용으로 교체하고 **Commit changes**합니다. GitHub 파일 편집기로 키 한 줄을 수정하고 커밋할 수도 있습니다.
5. 배포가 완료되면 **2단계에서 확인한 내 웹앱 주소**를 다시 엽니다. 바뀐 내용이 안 보이면 배포 상태와 업로드한 파일을 확인하고 새로고침합니다.

저장소 연동으로 수정한 팀은 커밋 또는 PR의 변경 내역을 확인하고 **배포 브랜치에 반영한 뒤** 같은 주소에서 결과를 점검합니다.

이 실습에는 브라우저 지도용 **JavaScript 키**를 사용하고 SDK 도메인을 설정합니다. AI에게 제공할 사본과 활동지에는 키 값을 자리표시자로 바꿉니다.

**직접 확인:** 수정한 파일이 배포되었고, 자신의 웹앱 주소에서 열립니다.

### 5. 내 프로젝트에서 지도와 기존 기능 확인하기

시작 예제는 **HTTP(S) 웹 서버에서 실행**합니다. **내 배포 주소를 새 탭으로 열고** 다음을 확인합니다.

| 확인할 것 | 직접 볼 결과 |
| --- | --- |
| 배경 지도 | 실제 도로와 지명이 보임 |
| 마커 | 가상 연습 위치 세 곳이 표시됨 |
| 클릭 | 마커를 누르면 이름과 **가상 연습 위치·실제 자료 아님** 안내가 열림 |
| 출처 | 카카오 로고와 저작권 표시가 가려지지 않음 |
| 기존 프로젝트 | 원래 있던 버튼·입력·목록이 계속 작동함 |

**배경의 도로·지명과 마커를 함께 확인합니다.** 배경이 회색이면 Network에서 배경 이미지 요청을, 지도 영역이 보이지 않으면 CSS의 높이를 확인합니다.

**직접 확인:** 내 주소 안에서 배경·세 지점·클릭 설명·출처가 보이고 기존 기능도 작동하면 지도 연결 점검을 마친 것입니다. 이제 아래에서 우리 팀이 선택한 자료를 연결합니다.

### 6. 안 보이면 내 웹앱의 실제 오류 확인하기

먼저 **배포된 파일의 키, 해당 앱의 카카오맵 사용 설정, 현재 주소의 SDK 도메인 등록값**을 확인합니다. 원인은 Network 응답과 Console의 오류 문구를 근거로 확인합니다.

### PC에서 오류 문구 찾기

1. **내 웹앱 주소**를 Chrome·Edge 등으로 엽니다. Windows는 **F12** 또는 **Ctrl+Shift+I**, Mac은 **⌘+⌥+I**, 또는 페이지에서 **우클릭 → 검사**로 개발자도구를 엽니다.
2. **Network(네트워크)**를 누른 상태에서 페이지를 새로고침합니다. 검색·필터 칸에 `sdk.js`를 입력합니다.
3. `dapi.kakao.com`의 `sdk.js` 요청을 선택하고 **Response(응답)**를 봅니다. 오류 JSON의 **`message` 문구**를 확인합니다.
4. **Console(콘솔)**의 실제 오류도 확인합니다. `sdk.js` 요청이 아예 없으면 키 자리표시자·이전 배포본·앞서 발생한 코드 오류를 점검합니다.
5. 도움을 요청할 때는 **키나 토큰을 지운 오류 문구**와 내 웹앱 주소를 전달합니다. 요청 URL의 `appkey=` 뒤 값이나 화면에 나온 실제 키는 가립니다. 응답이 긴 프로그램 코드라면 전체를 복사하지 말고 Console의 실패 문구를 확인합니다.

iPad처럼 개발자도구를 바로 열기 어렵다면 화면에 표시된 오류 문구를 키 없이 기록하고, 선생님과 PC에서 **같은 웹앱 주소**를 확인하세요. 오류를 못 읽었다면 ‘확인하지 못함’이라고 적으면 됩니다.

| 실제 응답 또는 현상 | 다음에 확인할 것 |
| --- | --- |
| `App(우리팀앱) disabled OPEN_MAP_AND_LOCAL service.` | **입력한 키의 앱**에서 **카카오맵 → 사용 설정 → ON**. 이미 ON이면 같은 앱의 키인지 확인 |
| `domain mismatched` | 해당 JavaScript 키의 SDK 도메인에 **현재 내 웹앱의 호스트·사용 중인 포트**가 등록됐는지 |
| `wrong appkey format`·`invalid appkey` | JavaScript 키 전체를 복사했는지, 자리표시자나 불필요한 공백이 남았는지 |
| 쿼터·호출 한도 문구 | 그 앱의 무료 쿼터 적용 여부와 **통계 → 쿼터** |
| 지도 영역이 안 보임·`kakao is not defined` | 영역 높이, SDK 요청, `kakao.maps.load` 이후 초기화하는 순서 |
| 틀·마커만 있고 배경은 회색 | 실패한 배경 요청·네트워크·이용 상태 |

**`disabled OPEN_MAP_AND_LOCAL service` 응답은 해당 앱의 카카오맵 사용 설정을 확인합니다.** 코드나 설정을 수정한 뒤 같은 프로젝트를 배포하고 5단계를 반복합니다.

## 우리 팀의 공공데이터를 지도에 연결하기

**팀이 선택한 공공데이터와 표시 항목을 지도에 연결합니다.** 자료의 예로 CCTV·공공쓰레기통·버스정류장 위치가 있습니다. 배경 지도는 선택한 서비스에서 표시하고, 우리 자료의 위치 정보로 마커를 만듭니다.

### 자료의 위치와 한 항목의 의미 확인하기

원자료와 항목 설명을 열어 아래 내용을 확인합니다. CSV는 열 이름, JSON·API는 필드 이름과 목록이 들어 있는 위치를 확인하세요.

| 확인할 내용 | 우리 자료에서 정할 것 |
| --- | --- |
| 한 행·항목의 의미 | 시설 한 곳, 관측 한 번 등 원자료의 단위. 같은 장소가 여러 행에 나오는지도 확인 |
| 위치를 구분할 이름·ID | 실제로 있는 이름·식별자·주소 중 마커와 원자료를 대조할 값 |
| 위도·경도 | 실제 열·필드 이름과 좌표계. WGS84인지 확인하고 빈 값·문자를 0으로 바꾸지 않기 |
| 설명·분류·수치 | 자료에 있고 프로젝트에 필요한 것만 선택. 필터나 합계가 필요 없는 자료에는 추가하지 않기 |
| 출처·기준일·범위 | 자료 출처, 갱신·조회 시점, 선택한 지역이나 기간 |

**주소만 있는 자료는 위도·경도를 확보한 뒤 연결합니다.** 다른 좌표계의 값은 변환 방법을 확인합니다. 선택한 도구의 좌표 순서를 확인합니다. 예를 들어 카카오의 `new kakao.maps.LatLng(위도, 경도)`는 **위도, 경도**, GeoJSON은 `[경도, 위도]` 순서입니다.

아래는 **가상 연습 위치·실제 자료 아님**을 전제로 한 4행의 좌표 검사입니다. 위도·경도 열을 골라 **좌표 확인하기**를 누른 뒤, 거꾸로 선택하거나 빈칸이 있는 행을 비교해 보세요. 카카오 시작 파일의 가상 위치 3개와는 별도의 자료이며 어떤 지도 서비스를 선택한 팀도 좌표를 살펴볼 수 있습니다.

### 기존 자료 읽기 방식에 지도 연결하기

**우리 앱이 이미 CSV·JSON·API 중 어떤 방식으로 자료를 읽는지 확인하고 그 방식을 유지합니다.** 아래에서 우리 팀에 해당하는 방법을 사용하세요.

| 현재 자료 방식 | 지도에 연결하기 전에 확인할 것 |
| --- | --- |
| CSV 파일 | 실제 열 이름·인코딩·빈 값. 파일 선택 기능을 쓴다면 브라우저에서 선택한 파일을 읽는지 |
| JSON 파일 | 위치 항목이 들어 있는 배열의 경로와 실제 필드 이름 |
| Open API | 응답의 목록 경로, 조회 조건, 페이지별 요청과 받은 범위, 인증·CORS 처리 |

API를 쓰는 팀은 [응답 구조 읽기](/hyfl-ai-lab/data/open-api/)와 [API로 웹앱 만들기](/hyfl-ai-lab/data-lab/)를 참고합니다. 화면에는 실제 읽은 조회 범위를 표시합니다. 인증과 CORS는 기존 연결 방식에 맞게 확인하고, 서버용 비밀키는 서버에서 관리합니다.

1. 현재 프로젝트와 우리 자료의 항목 설명·예시를 AI에 함께 제공합니다. 일부 샘플이면 샘플임을 밝히고 실제 파일·API를 읽는 기존 방법을 설명합니다. 코드 사본의 지도 키·인증값은 자리표시자로 바꿉니다.
2. 아래 요청의 빨간 부분을 실제 열·필드와 팀이 필요한 기능으로 바꿉니다. 없는 항목은 ‘없음’, 확인하지 못한 내용은 ‘확인 필요’로 적습니다.
3. 수정본의 필요한 설정을 기존 방식대로 연결하고 같은 프로젝트에 배포합니다. 기존 화면·기능과 데이터 읽기가 유지되는지 확인합니다.
4. 연결 점검용 가상 마커를 정리하고, **우리 자료의 마커와 설명**을 확인합니다.

**CSV 파일 선택 방식**에서는 웹앱의 파일 선택 버튼으로 자료를 열고, 선택한 파일 전체를 읽어 계산합니다. 한글이 깨지면 인코딩을 확인합니다. JSON·API를 사용하는 팀은 해당 데이터 연결 방식을 이어 사용합니다.

### 원자료 3개 항목과 결과 대조하기

원자료에서 서로 다른 위치의 **3행 또는 3개 항목**을 골라 지도 위치·식별 이름과 **우리 팀이 표시하기로 한 값**을 비교합니다. 다음도 직접 확인합니다.

- 빈 좌표는 잘못된 위치에 점을 만들지 않고 제외한 항목 수에 반영되는가?
- 자료나 조회 조건을 바꾸면 이전 마커가 정리되는가? 분류 필터를 만들었다면 목록과 지도도 같은 조건을 보여 주는가?
- **실제로 읽은 현재 조건의 항목 수 = 유효 좌표 항목 수 + 좌표 문제로 제외한 항목 수**인가? 행·항목 수, 서로 다른 위치 수, 자료 속 수치의 합계를 구분했는가?
- 원자료를 일부만 읽었다면 그 범위를 알리고, 출처·기준일·지도 저작권 표시를 유지했는가?

화면의 설명은 원자료의 값과 기준 시점에 근거해 작성합니다. 확인이 필요한 항목은 ‘확인 필요’로 표시합니다.

## 실습 후 직접 확인하기

- **이 지도 서비스를 선택한 이유는 무엇인가요?** 사용자·목적·설정·이용 조건과 연결해 설명합니다.
- **장소와 마커가 정확한 위치에 표시되나요?** 실제 원자료와 지도 위치를 대조합니다.
- **필요한 기능이 실제로 작동하나요?** 지도 표시와 검색·길찾기를 구분해 선택한 기능만 시험합니다.
- **휴대전화에서도 이용하기 편한가요?** 지도·버튼·마커 설명·글 목록을 읽고 조작해 봅니다.
- **작동하지 않거나 추가 설정이 필요한 부분은 무엇인가요?** 로딩 실패 안내, 미구현 기능과 남은 설정을 구분합니다.

**평가에서는 특정 지도 서비스를 사용했는지보다 선택 이유의 타당성, 목적에 맞는 기능 구현, 실제 작동을 확인하고 수정한 과정을 봅니다.** 지도 기능 자체는 필요한 팀의 선택이며 새 제출물은 없습니다.
