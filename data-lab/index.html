6. 공공데이터로 첫 웹앱 만들기

COMMON LAB · 프로젝트 1~2차시
오늘의 질문급식 자료에서 확인한 내용을, 직접 검색하고 비교할 수 있는 웹앱으로 만들 수 있을까?

🎯 이번 실습의 미션

같은 급식 자료로 질문을 정하고 데이터를 분석합니다. 발견한 내용을 기능으로 연결하여 생성형 AI와 메뉴 탐색기를 만든 뒤, 원자료와 결과를 대조하고 기능 하나를 수정합니다.

1. 우리가 만들 웹앱

섹션 제목: “1. 우리가 만들 웹앱”

사용자: 식단 기록에서 특정 메뉴가 나온 날을 찾아보고 싶은 학생.
문제: 긴 식단표에서 조건에 맞는 날짜를 찾아 비교하기 번거롭다.
첫 기능: 학교·월·검색어를 선택하면 해당 메뉴가 포함된 중식 날짜와 일수를 보여 준다.

먼저 메뉴 검색과 날짜·일수 표시 기능을 구현합니다. 이후 분석에서 발견한 점을 바탕으로 비교 기능 등을 추가합니다.

차시공통 실습남길 기록
1차시실제 자료 확인, 직접 계산, 발견을 기능으로 연결, 첫 버전 실행계산 근거와 기능 설계, 실행본
2차시원자료 대조, 예외 테스트, 기능 하나 수정, 짝과 바꾸어 사용수정 이유와 재검증, 짝의 의견

6번과 7번을 합해 총 12차시로 진행합니다. 공통 실습에서는 같은 질문·자료로 제작 과정을 익히고, 7번에서는 팀이 질문과 기능을 결정하여 서비스를 개발합니다.

실습 준비

섹션 제목: “실습 준비”

수업에서 안내한 실제 급식 CSV와 원자료 주소를 준비하고, 사용할 AI 도구와 파일 실행 환경에 접속할 수 있는지 확인합니다. 첫 실습은 같은 학교·기간의 파일로 진행합니다. 공개 배포가 지연되면 파일 실행과 짝 테스트를 먼저 마치고, 배포는 팀 프로젝트에서 이어 갈 수 있습니다.

급식 메뉴 탐색기 기본 예시 열기 · 기본 index.html 받기 · 가상 점검 CSV 받기

⚠️ 실제 분석 자료와 기능 점검 자료

기본 예시에는 실제 급식 자료가 내장되어 있지 않습니다. ‘가상 점검 데이터’는 정답을 확인하도록 만든 6개 기록이며 공공데이터가 아닙니다. 조작과 테스트를 연습한 뒤, 실제 분석에는 출처를 확인한 공공데이터를 사용합니다.

2. 데이터에서 인사이트까지

섹션 제목: “2. 데이터에서 인사이트까지”

2-1. 출처와 조회 조건 확인

섹션 제목: “2-1. 출처와 조회 조건 확인”

NEIS 교육정보개방포털에서 급식식단정보를 검색합니다. 원하는 학교·기간의 자료인지, 필요한 항목이 있는지 확인합니다. 화면에 표시된 일부 결과나 API 샘플 응답을 전체 자료로 착각하지 않습니다.

직접 확보하거나 수업에서 배부한 파일을 사용하되 출처 페이지와 조회 조건을 직접 확인합니다. 인증키 발급과 API 자동 연결은 첫 실습에 요구하지 않습니다.

  1. 원자료와 사본 분리

    원본은 그대로 보존하고 분석용 사본을 만듭니다.

  2. 필요한 열 확인

    급식일자·학교명·식사명·요리명에 해당하는 열을 찾습니다. 없는 항목은 만들지 않습니다.

  3. CSV로 정리

    필요한 경우 사본의 열 이름을 아래 기준에 맞춥니다. XLSX라면 CSV UTF-8로 내보내거나 다운로드합니다. 확장자만 바꾸지 않습니다.

  4. 정리 전후 대조

    일부 기록의 날짜·메뉴를 원본과 비교합니다. 필터·변환·삭제 기준과 변경한 기록 수를 남깁니다.

날짜급식일자 / MLSV_YMDYYYYMMDD 또는 YYYY-MM-DD. 없는 날짜를 채우지 않는다.

원하는 기간을 확보하지 못하면 분석 범위를 조정합니다. 실제 자료를 열지 못한 상태를 ‘수집 완료’로 표시하지 않습니다.

2-2. 질문을 정하고 직접 분석하기

섹션 제목: “2-2. 질문을 정하고 직접 분석하기”

“카레가 자주 나오는 것 같다”를 다음처럼 바꿉니다.

확보한 [학교·기간]의 중식에서 메뉴에 ‘카레’라는 문자열이 포함된 날짜는 며칠일까?

예상한 일수와 이유를 적습니다. 한 행이 하루인지 학교별 한 끼인지 확인합니다. 같은 날 기록이 여러 줄이라면 행 수와 날짜 수가 다를 수 있습니다.

데이터 구조와 계산 기준 확인 프롬프트 {{빨간 부분}}을 우리 팀의 내용으로 바꾸세요.
프롬프트 구조와 각 부분이 필요한 이유 보기

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

과업·필수 기능은 만들어야 할 결과와 빠뜨리면 안 되는 동작을 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

첨부한 급식 CSV를 이해하려고 해. 아직 앱 코드는 만들지 마.
1. 실제 열 이름, 한 행의 의미, 학교와 기간, 식사 종류를 확인해줘.
2. 중복·결측·잘못된 날짜가 있는지 확인하고 원자료의 어느 기록인지 보여줘.
3. '중식에서 카레라는 문자열이 들어간 날짜는 며칠인가?'를 계산하는 방법을 설명해줘.
4. 같은 학교·날짜에 기록이 여러 개면 하루로 세는 기준을 적용해줘.
5. 내가 직접 대조할 원자료 기록을 짚어줘. 자료에 없는 수치나 메뉴는 만들지 마.
6. 이 데이터로 알 수 없는 내용도 설명해줘.
실제 파일을 읽을 수 없다면 읽었다고 하지 말고 그 사실을 먼저 알려줘.

일부 기간을 정해 전체 중식일과 검색어가 포함된 중식일을 직접 셉니다. 해당 날짜도 기록합니다. 필요한 경우 필터와 간단한 표를 사용합니다.

‘카레’를 포함한 메뉴가 나온 일수이지, 학생의 선호도가 아닙니다. 자료에 없는 날짜도 ‘급식이 없었다’고 단정하지 않습니다.

섹션 제목: “3. 생성형 AI와 첫 버전 만들기”

3-1. 요구사항 설명하기

섹션 제목: “3-1. 요구사항 설명하기”

실제 데이터의 구조, 사용자의 입력, 계산 기준, 결과, 예외 상황을 함께 설명합니다. 아래 프롬프트를 읽고 우리가 확인한 자료·기준과 맞는지 점검한 뒤 사용합니다. 사용할 수 있도록 승인된 AI 도구를 이용하고 개인정보와 인증키는 입력하지 않습니다.

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

과업·필수 기능은 만들어야 할 결과와 빠뜨리면 안 되는 동작을 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

급식 CSV를 읽는 한국어 웹앱을 만들어줘. HTML·CSS·JavaScript를 index.html 한 파일에 넣어줘.
외부 라이브러리, 서버, 로그인, 유료 API는 사용하지 마.

[사용자와 목적]
학생이 파일에 포함된 기간에서 특정 메뉴가 나온 중식 날짜를 찾는다.

[데이터]
내가 확인한 열: 날짜, 학교명, 식사명, 메뉴.
날짜는 YYYY-MM-DD 또는 YYYYMMDD 형식이다.
CSV 파일 선택으로 읽고 데이터는 브라우저에서만 처리한다. 업로드·저장·외부 전송은 하지 않는다.
파일에 없는 날짜와 메뉴를 생성하지 않는다. UTF-8 BOM, 따옴표 안의 쉼표·줄바꿈을 처리한다.

[기능]
1. 파일 선택, 학교 선택, 월 선택, 메뉴 검색어 입력.
2. 선택한 학교·월의 중식 기록만 사용한다.
3. 메뉴에 검색어 문자열이 포함된 날짜 목록과 일수를 표시한다.
4. 같은 학교·날짜의 중복 기록은 메뉴를 합쳐 하루로 센다.
5. 검색어가 비면 전체 기록을 보여주고, 결과가 없으면 안내한다.
6. 누락·잘못된 날짜·중식이 아닌 기록은 제외 이유를 표시한다.
7. 필수 열이 없거나 파일을 읽지 못하면 기존 결과를 지우고 오류를 설명한다.
8. 데이터 출처·조회 조건·확인일을 적는 칸, 파일의 날짜 범위, 자동 갱신 없음 안내를 둔다.
9. 메뉴 원문과 알레르기 표시는 보존한다. 선호도나 알레르기 안전 여부는 판단하지 않는다.
10. 모바일에서도 읽기 편하게 만들고, 파일의 내용은 HTML로 실행하지 말고 텍스트로 표시한다.

[설명]
코드에서 데이터 읽기·조건 처리·계산·결과 표시 부분에 주석을 달아줘.
전체 코드와 함께 실행 방법, 내가 원자료와 대조할 테스트를 설명해줘.

3-2. 코드 받아 실행하기

섹션 제목: “3-2. 코드 받아 실행하기”

  1. 첫 파일 저장

    생성된 전체 HTML 코드를 일반 텍스트 파일로 저장합니다. 코드 블록 표시인 세 개의 백틱은 넣지 않습니다. 이름은 index.html, 인코딩은 UTF-8로 정합니다.

  2. 확장자 확인

    index.html.txt로 저장되지 않았는지 확인합니다. PC에서는 웹브라우저로 파일을 엽니다.

  3. 실제 CSV 선택

    준비한 CSV를 불러오고 출처·조회 조건·확인일을 입력합니다. 출처 칸을 채웠다고 자동으로 검증되는 것은 아닙니다.

  4. 같은 질문으로 실행

    직접 센 것과 같은 학교·월·검색어를 선택합니다. 일수뿐 아니라 날짜와 메뉴 원문을 대조합니다.

  5. 코드의 네 부분 찾기

    데이터 읽기·조건 처리·계산·결과 표시 부분을 AI에게 설명하게 한 뒤, 각각의 역할을 내 말로 정리합니다.

실행이 막히면 기본 index.html로 같은 CSV를 사용해 봅니다. AI가 작성한 첫 버전은 보존하고, 기본 예시로 돌아온 이유를 적습니다. 모든 코드를 외우기보다 데이터가 어떤 처리를 거쳐 결과가 되는지 설명합니다.

3-3. GitHub Pages로 공유하기

섹션 제목: “3-3. GitHub Pages로 공유하기”

기존 작업을 덮어쓰지 않도록 이번 실습용 저장소를 새로 만듭니다. 배포가 지연되어도 파일 실행과 데이터 검증은 이어 갑니다.

  1. 새 저장소 만들기

    GitHub의 New repository에서 meal-data-lab 같은 이름으로 저장소를 만듭니다. 학교가 허용한 계정과 공개 범위를 확인합니다.

  2. index.html 올리기

    Add file → Upload files 또는 Create new file로 최상위에 index.html을 저장하고 Commit changes를 누릅니다. 파일 선택 방식이면 실제 CSV를 저장소에 올리지 않아도 됩니다.

  3. 게시 위치 설정

    Settings → Pages → Build and deployment에서 Source를 Deploy from a branch로 정합니다. Branch는 main, 폴더는 /(root)를 선택하고 Save를 누릅니다.

  4. 배포 확인

    Actions에서 배포 상태를 확인한 뒤 Pages에 표시된 주소를 엽니다. iPad에서는 배포된 주소를 Safari에서 열어 확인합니다.

공개되는 사이트와 저장소에는 개인정보·인증키·재배포할 수 없는 파일을 올리지 않습니다. 학교 네트워크에서 로그인이 막히면 임의로 우회하지 않고 수업에서 정한 실행 방식으로 테스트합니다.

섹션 제목: “4. 결과 검증하기”

실제 CSV에서 직접 센 결과를 기준으로 삼습니다. 정상 사례와 예외 상황을 모두 확인합니다.

5. 개인·짝 미션 · 기능 하나 바꾸기

섹션 제목: “5. 개인·짝 미션 · 기능 하나 바꾸기”

정상 실행본을 별도 파일로 보관합니다. 분석이나 사용 과정에서 발견한 점을 근거로 기능 하나를 수정합니다.

수정 후보결정할 기준
검색된 중식일의 비율분모는 검색 전 선택 범위의 전체 중식일. 분모가 0이면 자료 없음으로 표시한다.
월별 비교 표·막대그래프월별 전체 중식일 수를 함께 보여 준다.
사용 중 발견한 불편 개선불편한 장면과 입력·처리·출력의 변화를 설명한다.
기능 하나 수정하는 프롬프트 {{빨간 부분}}을 우리 팀의 내용으로 바꾸세요.
프롬프트 구조와 각 부분이 필요한 이유 보기

역할·프로젝트 맥락은 AI가 어떤 관점에서 어느 팀의 문제를 다루는지 정합니다.

과업·필수 기능은 만들어야 할 결과와 빠뜨리면 안 되는 동작을 정합니다.

화면·디자인·기술 조건은 실제 사용자와 실행 환경의 제약을 전달합니다.

오류 처리·검증 기준은 실패했을 때의 안내와 완성 여부를 판단하는 기준입니다.

현재 정상 작동하는 index.html과 검증 기록을 바탕으로 기능 하나만 추가해줘.
바꿀 기능: [월별 비교 표 / 검색된 중식일의 비율 / 그 밖의 기능 하나]
바꾸는 이유와 데이터에서 확인한 근거: [내용]
유지할 것: 파일 읽기, 중식 필터, 중복 날짜 처리, 출처 표시, 오류 안내.
먼저 변경 계획과 계산 기준을 설명하고, 수정 후 전체 파일을 제공해줘.
비율을 추가한다면 분모는 검색 전 선택한 학교·월의 유효한 전체 중식일 수로 해줘.
분모가 0이면 비율을 계산하지 말고 자료 없음으로 표시해줘.
수정한 곳과 다시 점검할 테스트를 설명해줘. 확인하지 않은 결과를 성공했다고 단정하지 마.

새 기능과 기존의 검색·중복·오류 테스트를 다시 실행합니다. 짝에게 검색 조건 하나를 정해 주고 앱으로 결과를 찾게 합니다. 짝이 설명 없이 할 수 있었던 일과 막혔던 장면을 기록합니다.

6. 실습 기록과 팀 프로젝트 준비

☑️ 공통 실습 완료 기준

  • 실제 자료의 출처·기간과 한 행·열의 의미를 설명했다.
  • 일부 기록을 직접 분석하고 발견을 기능으로 연결했다.
  • 실제 CSV로 앱을 실행하고 원자료와 결과를 대조했다.
  • 예외 상황을 테스트하고 기능 하나를 수정·재검증했다.
  • AI의 제안을 그대로 사용하지 않고 내가 확인한 근거를 남겼다.
  • 데이터 읽기·처리·계산·출력 과정을 내 말로 설명했다.

다음 3~12차시에는 팀별로 해결할 문제를 정의하고 프로젝트를 진행합니다. 데이터 읽기·처리·출력 구조는 재사용할 수 있습니다. 팀은 문제에 맞는 자료를 선택하고 분석에서 얻은 인사이트를 근거로 필요한 기능을 연결·확장합니다.

공공데이터를 우선 검토하되, 출처와 사용 범위를 확인한 학습 자료·직접 만든 자료·연습 기록도 선택할 수 있습니다. 자료의 종류는 달라도 분석·인사이트·기능·검증의 연결은 유지합니다. 자세한 진행 과정과 평가 기준은 7번에서 확인합니다.
