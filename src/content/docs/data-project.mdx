## 1. 주제는 세 가지 생활 영역에서 선택하기

먼저 아래 영역 중 하나를 고릅니다. 자료와 주제를 끝없이 넓히기보다 **사용자 한 집단, 이용 상황 하나, 처음 분석할 범위**를 정합니다. 같은 영역이나 데이터를 여러 팀이 선택해도 됩니다. 팀마다 질문·해석·사용 흐름을 다르게 설계할 수 있습니다.

| 선택 영역 | 다룰 사용자 상황 | 분석 질문 후보 | 개발 방향 후보 |
| --- | --- | --- | --- |
| 급식 기록 | 특정 메뉴가 나온 날과 기간별 빈도를 확인하고 싶다. | 메뉴가 포함된 일수와 전체 중식일 대비 비율은 월별로 어떻게 다른가? | 기간별 검색·비교, 날짜 목록, 빈도·비율 시각화 |
| 공공도서관 | 원하는 지역에서 이용할 도서관을 비교하고 싶다. | 선택한 지역의 도서관 운영시간·정기휴관일에는 어떤 차이가 있는가? | 지역별 후보 탐색, 운영정보 비교, 원문 확인 |
| 문화행사 | 날짜·지역·비용 조건에 맞는 문화생활을 찾고 싶다. | 확보한 기간에서 지역·분야·유무료 조건별 행사 수는 어떻게 다른가? | 조건 검색, 행사 비교, 기간별 보기, 상세 정보 |

위 내용은 출발점이며 분석 결과가 아닙니다. 실제 자료의 항목과 범위를 확인한 뒤 질문과 기능을 결정합니다. 도서관을 실시간 빈자리 서비스로, 급식 기록을 학생 선호도 예측으로, 등록된 행사를 지역의 모든 행사로 확대 해석하지 않습니다.

### 원자료 탐색 출발점

| 영역 | 공식 데이터 페이지 | 실제 자료에서 확인할 것 |
| --- | --- | --- |
| 급식 | [NEIS 교육정보개방포털](https://open.neis.go.kr/)의 급식식단정보 | 학교·날짜·식사명·메뉴와 확보한 기간 |
| 도서관 | [서울시 공공도서관 현황정보](https://data.seoul.go.kr/dataList/OA-15480/S/1/datasetView.do) | 지역·주소·운영시간·정기휴관일의 표기와 누락 |
| 문화행사 | [서울시 문화행사 정보](https://data.seoul.go.kr/dataList/OA-15486/S/1/datasetView.do) | 기간·지역·분류·유무료·이용대상과 중복 기준 |

위 링크는 탐색할 원자료 페이지입니다. 교과서에 팀별 분석용 파일이 모두 준비되어 있다는 뜻은 아닙니다. 사용할 파일이나 응답을 직접 열어 보고 출처·이용 조건·확보 범위를 확인합니다. 첫 탐색 범위는 학교 한 곳 또는 선택한 지역과 기간으로 정하고, 비교에 필요할 때 확대합니다.

<Callout kind="concept" title="주제의 범위는 정하되, 서비스의 발전 가능성은 열어 둡니다">핵심 사용 흐름을 먼저 완성한 뒤 관련 기능을 연결·확장합니다. 최종 기능 수를 하나로 제한하지 않습니다. 검색·비교·시각화·상세 정보 등을 결합하되, 각 기능이 사용자의 문제와 어떻게 연결되는지 설명합니다.</Callout>

## 2. 이번 프로젝트에서 보여 줄 세 가지 역량

| 역량 | 프로젝트에서 하는 일 | 설명할 수 있어야 하는 것 |
| --- | --- | --- |
| 문제 해결력 | 사용자의 불편을 구체화하고, 발견을 기능으로 연결하며, 피드백으로 개선한다. | 왜 이 문제와 기능을 선택했고 무엇을 바꾸었는가? |
| 데이터 리터러시 | 출처·범위를 확인하고, 기준을 정해 분석하며, 수치·해석·한계를 검증한다. | 무엇을 근거로 어디까지 말할 수 있는가? |
| AI 활용 역량 | 목적·자료·제약을 설명해 AI와 협업하고, 결과를 검토·수정한다. | AI의 제안 중 무엇을 받아들이거나 바꾸었고, 어떻게 확인했는가? |

앱을 실행하는 것과 데이터를 정확히 이해하는 것을 함께 확인합니다. AI를 많이 사용한 횟수보다 **요구사항을 명확히 하고, 결과를 근거로 판단한 과정**을 기록합니다. 생성형 AI는 탐색·분석·기획·개발·오류 수정에 활용합니다.

## 3. 12차시 진행 계획

총 12차시에는 6번의 공통 실습 2차시가 포함됩니다. 이 팀 프로젝트는 3~12차시입니다. 차시는 진행 상황에 따라 조정하되 분석·검증·개선 과정은 남깁니다.

| 차시 | 중심 활동 | 확인할 결과 |
| --- | --- | --- |
| 1~2차시 · 6번 | 공통 데이터 분석, 앱 제작, 기능 수정과 검증 | 공통 실행본·계산 근거·수정 기록 |
| 3차시 | 팀 구성, 사용자 상황과 문제 정의 | 문제 정의·탐구 질문 |
| 4차시 | 데이터 후보 확인, 실제 자료 확보, 범위 결정 | 데이터 카드·열어 본 자료 |
| 5차시 | 정리 기준 수립, 비교·계산·시각화 | 핵심 표·그래프·수치 대조 |
| 6차시 | 인사이트 도출, 필요하면 문제 재정의 | 발견 → 의미 → 해결 방향 |
| 7차시 | 서비스 기획, 화면·사용 흐름·개발 순서 설계 | 기획서·기능 우선순위·테스트 기준 |
| 8~9차시 | 생성형 AI와 개발, 기능 연결·확장 | 실제 데이터로 작동하는 첫 완성본 |
| 10차시 | 데이터·기능 검증과 오류 수정 | 기대 결과와 실제 결과·재검증 |
| 11차시 | 다른 팀의 사용, 피드백 반영 | 사용 중 막힌 장면·개선본 |
| 12차시 | 앱 체험·시연·발표·개인 성찰 | 최종 서비스·프로젝트 기록 |

중간 점검은 세 번 합니다. **4차시에는 실제 데이터를 열었는지, 6차시에는 무엇을 발견했는지, 9차시에는 핵심 사용 흐름이 작동하는지** 확인합니다. 개발이 늦어지면 기능 우선순위를 조정하고, 데이터 해석이나 테스트를 생략하지 않습니다.

### 팀 구성과 공동 책임

3인 내외로 팀을 구성하여 질문·데이터, 분석·검증, 구현·사용성을 나누어 주도합니다. 역할은 고정된 독점 업무가 아닙니다. 팀원 모두 실제 자료를 읽고, AI 요청 또는 수정 작업에 참여하며, 하나 이상의 결과 대조나 기능 테스트를 직접 수행합니다. 중요한 문제·데이터·기능 결정은 함께 내립니다.

## STEP 1 · 사용자의 상황에서 문제 정의하기

선택한 영역에서 누가 언제 어떤 정보를 찾거나 비교하는지 정합니다. 사용할 것 같은 친구에게 현재 어떻게 정보를 찾는지, 어디서 불편한지 물어보거나 실제 사용 장면을 관찰합니다. 소수의 의견을 모든 학생의 의견으로 일반화하지 않습니다.

> **[사용자]**는 **[상황]**에서 **[필요한 정보·선택]**을 확인하려고 한다. 현재 **[불편]**이 있다. 우리는 먼저 **[기간·지역·지표가 드러나는 질문]**을 데이터로 확인한다.

문제 정의는 처음의 가설입니다. 실제 자료나 사용자의 반응이 예상과 다르면 수정합니다. 이 단계에서 서비스 이름이나 화면을 먼저 확정하지 않습니다.

```text
우리의 선택 영역은 [급식 / 도서관 / 문화행사]야.
사용자는 [누구], 상황은 [언제 무엇을 하는지], 확인한 불편은 [내용]이야.
아직 코드를 만들지 말고, 데이터로 확인할 질문 후보 세 개를 제안해줘.
각 질문에 필요한 항목·비교 기준과 아직 확인하지 못한 가정을 알려줘.
실제 데이터로 확인할 수 없는 질문은 따로 표시해줘.
```

## STEP 2 · 실제 자료를 확보하고 범위 정하기

같은 영역의 데이터 후보를 우선 두 개 이내로 살펴보고, 질문에 적합한 자료부터 사용합니다. 출처 페이지가 있다는 사실과 원하는 내용이 실제 파일에 있다는 사실을 구분합니다.

<Steps>
<Step title="원자료 열기">파일 또는 API 응답을 열어 항목과 실제 기록을 확인합니다. 샘플·화면 일부·전체 자료를 구분합니다.</Step>
<Step title="질문과 맞추기">필요한 기간·지역·단위가 있는지 확인합니다. 없는 항목은 생성하지 않고 질문이나 기능을 조정합니다.</Step>
<Step title="분석 범위 고정">처음 분석할 학교·지역·기간과 사용할 열을 정합니다. 자료를 확장할 때는 이유를 남깁니다.</Step>
<Step title="원본 보존">원자료와 분석 사본을 분리하고 조회 조건·확보일·이용 조건을 기록합니다.</Step>
</Steps>

| 데이터 카드 | 우리 팀 기록 |
| --- | --- |
| 데이터 이름·기관·원문 주소 |  |
| 이용 조건·공유 가능한 범위 |  |
| 조회 조건·자료 기준 시점·확보일 |  |
| 한 행의 의미·사용할 열·단위 |  |
| 전체 자료인지, 일부 기간·샘플인지 |  |
| 누락·중복·표기 차이 |  |
| 답할 수 있는 질문·답할 수 없는 질문 |  |

첫 버전은 실제 자료를 담은 파일로 제작할 수 있습니다. API 자동 갱신이 필요하면 자료의 이용 조건과 키 관리·갱신 방식을 별도로 확인합니다. 자료를 확보하지 못하면 수업에서 사용이 확인된 공통 자료로 돌아가 다른 질문을 정할 수 있습니다.

## STEP 3 · 기준을 정해 분석하기

질문에 필요한 행·열을 선택하고 정리 기준을 정합니다. **원본의 값을 바꾸는 정리와, 그 값으로 새로운 결과를 구하는 계산을 구분**하여 기록합니다.

| 점검할 문제 | 결정할 기준 |
| --- | --- |
| 누락된 값 | 0·무료·휴관 등으로 자동 해석하지 않고 확인 필요 또는 분석 제외로 표시한다. |
| 중복 기록 | 같은 날짜·시설·행사를 무엇으로 구분할지 정한다. |
| 표기 차이 | 날짜·운영시간·비용 등의 원문을 보존하고 변환 기준을 기록한다. |
| 비교 기준 | 같은 기간·지역 단위로 비교하는지, 합계와 비율 중 무엇이 질문에 맞는지 판단한다. |
| 자료 범위 | 확보한 기록의 결과를 전체 학교·지역·행사로 일반화하지 않는다. |

질문에 답하는 핵심 표나 그래프를 만들고 **중요한 값 두 개 이상을 원자료와 직접 대조**합니다. 비율은 분자·분모를, 평균은 포함한 기록을, 개수는 중복 처리 기준을 설명합니다. 도서관 운영시간처럼 모호한 문장이 있으면 억지로 수치로 바꾸지 않고 원문 확인 대상으로 남깁니다.

```text
실제 데이터로 [우리 질문]을 분석하려고 해.
사용할 열·필터·단위·중복·누락 처리와 계산식부터 설명해줘.
질문에 맞는 표나 그래프를 만들고, 원자료 값과 계산 결과를 구분해줘.
내가 다시 계산할 수 있도록 사용한 기록과 절차를 알려줘.
확인한 사실·가능한 해석·알 수 없는 것을 구분해줘.
원자료를 읽지 못하거나 항목이 부족하면 그대로 알려줘. 없는 값을 채우지 마.
```

## STEP 4 · 인사이트를 도출하고 문제 다시 보기

인사이트는 이 프로젝트에서 **분석한 내용이 사용자의 상황과 서비스 설계에 어떤 의미가 있는지 판단한 결과**입니다. “그래프가 높다”에서 끝내지 않고 어떤 정보를 함께 보여 주어야 오해가 줄어드는지, 어떤 조건이 선택에 중요한지 설명합니다.

### 발견에서 기능으로 연결하는 예

다음은 설명을 위한 가상의 급식 자료이며 실제 학교의 분석 결과가 아닙니다.

| 단계 | 예시 |
| --- | --- |
| 분석 결과 | A월은 전체 중식 20일 중 카레 포함 4일, B월은 15일 중 3일이다. |
| 인사이트 | 횟수는 다르지만 비율은 모두 20%다. 반복 정도를 비교하려면 전체 중식일 수를 함께 보아야 한다. |
| 설계 판단 | 메뉴 등장 횟수와 비율, 비교에 사용한 전체 중식일 수를 함께 표시한다. |
| 검증 기준 | A월 4/20, B월 3/15를 앱에서 각각 20%로 계산하는지 확인한다. |

사용자가 겪는 불편은 사용자 확인으로, 기록의 차이는 데이터로 확인합니다. 데이터의 차이만으로 불편의 원인이나 서비스 효과를 증명했다고 말하지 않습니다.

| 인사이트 카드 | 우리 팀 기록 |
| --- | --- |
| 처음 예상과 질문 |  |
| 직접 확인한 사실·수치 |  |
| 예상과 다른 점·예외 |  |
| 사용자에게 갖는 의미와 그 판단의 근거 |  |
| 지금 자료로 단정할 수 없는 것 |  |
| 그래서 유지하거나 수정한 문제 |  |
| 발견과 연결할 핵심 기능 |  |

> 우리는 **[자료와 조건]**에서 **[사실]**을 확인했다. 이는 **[사용자 상황]**에서 **[의미]**가 있다고 판단했다. 따라서 **[기능·표시 기준]**을 설계한다. 다만 **[한계]**는 남는다.

## STEP 5 · 서비스 기획과 개발 순서 정하기

화면보다 먼저 **사용자의 행동이 시작되어 결과 확인까지 이어지는 흐름**을 설계합니다. 예를 들어 조건 선택 → 후보 찾기 → 비교 → 상세 정보 확인이 하나의 사용 흐름이 될 수 있습니다.

| 한 장 기획서 | 작성할 내용 |
| --- | --- |
| 사용자와 문제 | 누가 어떤 상황에서 무엇을 해결하려는가? |
| 분석과 인사이트 | 어떤 발견이 문제나 기능의 판단을 바꾸었는가? |
| 사용할 데이터 | 실제로 확보한 출처·항목·범위는 무엇인가? |
| 핵심 사용 흐름 | 사용자가 무엇을 입력하고 어떤 처리를 거쳐 무엇을 보는가? |
| 기능 우선순위 | 먼저 완성할 기능과 이후 연결할 기능은 무엇인가? |
| 검증 기준 | 어떤 입력에서 어떤 결과가 나와야 하는가? |
| 한계·안전 | 자료 기준일·누락·오류·갱신 여부를 어떻게 알리는가? |

기능마다 **필요한 이유 → 필요한 데이터 → 구현 순서 → 확인 방법**을 적습니다. 핵심 기능 한 가지 이상은 분석에서 어떤 발견을 했기 때문에 설계했는지 설명해야 합니다. 모든 화면 요소에 별도의 통계 근거를 억지로 붙일 필요는 없습니다.

<Callout kind="checklist" title="개발 전 점검">
- 실제 데이터를 열고 질문에 맞는 분석을 했다.
- 핵심 값을 직접 대조하고 인사이트를 설명했다.
- 발견과 서비스의 핵심 기능이 연결된다.
- 입력·처리·출력과 기능의 개발 순서를 정했다.
- 테스트할 입력과 기대 결과를 준비했다.
</Callout>

## STEP 6 · 생성형 AI와 개발하고 기능 연결하기

[공통 실습](/hyfl-ai-lab/data-lab/)의 데이터 읽기·조건 처리·계산·출력 구조를 재사용할 수 있습니다. 새 자료의 항목과 의미에 맞게 수정합니다. 먼저 핵심 사용 흐름을 완성하고, 그다음 비교·시각화·상세 정보 등 필요한 기능을 연결합니다.

```text
공공데이터를 활용한 웹 서비스를 개발하려고 해.
사용자와 상황: [내용]
확인한 문제와 인사이트: [내용]
실제 데이터 구조·출처·범위: [내용]
전체 사용 흐름: [내용]
이번에 구현할 부분: [우선순위에 따른 기능]
입력·처리·출력 기준: [내용]
테스트 입력과 기대 결과: [내용]

현재 데이터와 환경에서 가능한지 먼저 점검하고 개발 계획을 설명해줘.
공통 실습의 HTML·CSS·JavaScript 구조를 바탕으로 코드를 작성해줘.
없는 데이터로 결과를 꾸미지 말고, 누락·빈 결과·오류를 안내해줘.
변경한 부분과 내가 확인해야 할 테스트를 설명해줘.
이미 정상인 기능을 유지하고, 확인하지 않은 결과를 성공했다고 말하지 마.
```

정상 실행본을 보관한 뒤 한 번에 변경할 부분을 정합니다. 오류가 나면 입력 조건·기대 결과·실제 결과·오류 메시지를 제시하여 수정을 요청합니다. AI가 제안한 변경이 왜 필요한지 확인하고, 수정 후 같은 조건으로 다시 테스트합니다.

자료는 합법적으로 공유 가능한 파일을 선택하는 방식 또는 이용 조건을 확인한 자료를 포함하는 방식으로 사용합니다. 공개 코드에 개인정보나 인증키를 넣지 않습니다. 로그인·개인정보 저장·유료 API가 필요한 기능은 사전 확인 없이 추가하지 않습니다. 추가 모델 학습은 공통 요구사항이 아닙니다.

## STEP 7 · 원자료와 사용자로 검증·개선하기

**데이터 검증은 결과가 맞는지, 사용자 테스트는 원하는 일을 수행할 수 있는지** 확인합니다. 서로 다른 두 과정을 모두 진행합니다.

| 테스트 | 입력·상황 | 기대 결과와 근거 | 실제 결과 | 수정·재검증 |
| --- | --- | --- | --- | --- |
| 핵심 기능 정상 조건 1 |  |  |  |  |
| 핵심 기능 정상 조건 2 |  |  |  |  |
| 결과가 없는 조건 |  |  |  |  |
| 누락·중복·잘못된 자료 |  |  |  |  |
| 기능을 연결한 전체 사용 흐름 |  |  |  |  |
| 다른 팀의 사용 | 수행할 과제 | 완료 기준 | 막힌 장면 |  |

### 다른 팀이 우리 앱을 사용한다면?

원자료만 보고 준비한 검색·비교 과제를 다른 팀에게 줍니다. 다른 팀은 조건을 바꾸어 결과를 찾고 설명이 부족하거나 예상과 다른 장면을 알려 줍니다. 버그를 발견하면 재현 조건과 근거를 함께 전달합니다.

사용자의 이름이나 개인정보 대신 **과제, 실제 행동, 완료 여부, 막힌 장면, 의견**을 기록합니다. 가능한 경우 수정한 앱에서 같은 과제를 다시 수행하게 하여 달라진 점을 확인합니다. 소수의 사용 결과만으로 모든 사용자에게 효과가 있다고 단정하지 않습니다.

오류나 의견을 바탕으로 한 가지 이상 수정합니다. 새 기능과 함께 기존 기능도 다시 검사합니다. 확인하지 못한 기능은 완료로 표시하지 않고 한계로 남깁니다.

## STEP 8 · 앱 체험회·발표·성찰로 마무리하기

발표는 완성 화면만 보여 주는 시간이 아닙니다. 문제와 데이터, 인사이트와 기능, 테스트와 개선이 이어지도록 설명합니다.

> 우리는 **[사용자·문제]**에서 출발했다. **[자료]**를 분석하여 **[사실과 인사이트]**를 얻었고, 이를 **[기능]**으로 구현했다. 지금 **[입력]**으로 시연하겠다. 결과를 **[원자료·테스트]**로 확인했고, **[오류·의견]** 때문에 **[내용]**을 개선했다. 아직 **[한계]**가 남아 있다.

### 제출물은 한 프로젝트 기록으로 묶기

| 구성 | 포함할 것 |
| --- | --- |
| 웹 서비스와 실행 안내 | URL 또는 실행 파일, 필요한 자료와 준비 방법, 사용 순서 |
| 문제·데이터·분석·기획 | 문제 정의, 출처·조회 조건, 정리 기준, 핵심 표·그래프, 인사이트, 기능 설계 |
| 검증·개선·AI 협업 | 기대·실제 결과, 사용자 의견, 수정 전후·재검증, 중요한 AI 협업 판단 |

별도의 보고서를 여러 개 만들기보다 차시별 기록을 이어 붙입니다. 공개 배포 범위와 데이터 공유는 이용 조건과 학교 운영 기준을 따릅니다.

### AI 협업 기록

| 장면 | AI에게 준 목적·조건 | AI의 제안 | 내가 채택·수정·거절한 이유 | 직접 확인한 근거 |
| --- | --- | --- | --- | --- |
| 데이터 탐색·분석 |  |  |  |  |
| 기획·개발 |  |  |  |  |

### 평가에서 확인할 세 가지

| 역량 | 충분히 드러나는 모습 | 보완이 필요한 모습 |
| --- | --- | --- |
| 문제 해결력 | 구체적인 사용자 상황을 확인하고, 인사이트를 기능으로 연결하며, 사용 결과를 바탕으로 개선했다. | 만들고 싶은 기능만 나열하고 누구의 무엇을 돕는지 또는 개선 근거를 설명하지 못한다. |
| 데이터 리터러시 | 출처·범위·단위를 이해하고, 처리·계산 기준과 수치 대조를 설명하며, 사실·해석·한계를 구분한다. | 출처나 집계 기준이 불명확하고, AI의 그래프·숫자를 확인 없이 사용한다. |
| AI 활용 역량 | 목적·자료·제약을 구체적으로 전달하고, 결과를 판단·수정하여 다시 검증했다. | 생성된 결과를 그대로 제출하고 요청 조건·변경 이유·확인 방법을 설명하지 못한다. |

기능 수나 화면의 화려함만으로 평가하지 않습니다. 사용하기 쉬운 화면은 사용자의 과제 수행과 연결하여 설명합니다. 팀원 각자는 다음 세 문장을 실제 사례와 함께 완성합니다.

> **문제 해결:** 내가 바꾼 문제 정의나 기능은 ___이며, 이유와 확인 결과는 ___이다.<br />
> **데이터:** 내가 직접 확인한 수치·처리 기준은 ___이며, 이 자료로 말할 수 없는 것은 ___이다.<br />
> **AI 활용:** AI에게 ___을 요청했고, ___을 수정하거나 거절했다. 근거는 ___이다.

<Callout kind="think" title="프로젝트를 마치며">데이터와 AI를 활용한 뒤, 나는 어떤 문제를 더 정확하게 이해하고 어떤 결과를 스스로 확인할 수 있게 되었는가?</Callout>

이 프로젝트는 최종 시연과 성찰로 마칩니다. 실제 학교 서비스로 운영하려면 보안·유지보수·자료 갱신을 별도로 검토해야 하며, 운영까지가 이번 제출 의무는 아닙니다.
